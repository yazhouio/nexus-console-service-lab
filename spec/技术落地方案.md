# 前端插件系统 V1 技术落地方案（最终版）

## 0. 文档状态

本文是前端插件系统 V1 的规范性设计。

2026-09-04 后续设计：跨插件 UI 组合按 [首期 UI 组合契约](../apps/docs/docs/cross-plugin-ui-composition-contract.md) 与 [实现及作者 API](../apps/docs/docs/cross-plugin-ui-composition-implementation.md) 执行，对应 ADR 0007–0015。下文早期 UI Extension 的 `slot: string`、同 Slot 内 ID 唯一、直接 target / mount options 和 UI relation 错误拒绝整插件等设计已被 owner-scoped Extension Point / Contribution、结构化 Context、Host Scope / Attempt 模型及分层隔离取代。Route / Navigation 与其他 V1 约束保持各自契约，不为原型 slot string 建立兼容映射。

设计结论来自 [V1 消融实验报告](<./V1 消融实验报告.md>)。如果本文与早期技术调研或消融前方案冲突，V1 以本文为准。

V1 只为当前已经存在的两条执行路径建模：

```text
Builtin Plugin
  -> 与 Kernel 同包构建
  -> Direct activate

Restricted External Plugin
  -> Installed Manifest
  -> Bootstrap accepts declarations
  -> On-demand Surface mount
  -> Wujie
  -> Plugin Bridge
```

本文中的“必须”是 V1 不变量；“建议”允许实现阶段在不改变外部行为的前提下调整。

## 0.1 冻结边界

本版已完成 `HostApiId`、Restricted 能力边界、`CAPABILITY_NOT_BRIDGE_EXPOSED` 错误阶段与 `BridgeBootstrapDescriptor` 四项 Contract 修正，架构方案由此冻结。

Contribution 冲突细则、staged Capability 可见性、Provider 失败的单遍传播与 `mountPointId` 属于实现期规范补强，不引入新的一级架构概念。

V1 明确不将 `SandboxPluginSDK` 或通用 RPC Framework 提升为核心抽象。后续直接按第 19 章进入 Phase 1 / 2 实现；除非第 1.2 节的现实前提失效，不再进行架构层面的“最终修复”。

# 1. 目标与前提

## 1.1 设计目标

V1 必须解决：

1. Host 提供稳定的 UI 扩展点；
2. Plugin 通过 Capability 共享能力，不依赖彼此内部实现；
3. 根据声明自动计算确定性的依赖处理顺序；
4. Capability Major 不兼容时在执行代码前失败；
5. Descriptor / Manifest 与 Runtime 注册行为保持一致；
6. Contribution 顺序稳定且可预测；
7. Core 启动失败 fail-fast，Non-core Builtin 与 Restricted Surface 失败 fail-soft；
8. Restricted Plugin 通过按需挂载的 Wujie Surface 获得 cooperative-isolation 和集成治理；
9. Bridge Action 与 Subscription 具备 Schema、Permission、资源上限和诊断；
10. Plugin、Surface Instance 与 BridgeSession 的 Runtime 事实可以被低成本检查。

核心约束：

> **Plugin Set 可以变化，但单次页面 Runtime 生命周期内保持不变。**

安装、升级、启用、禁用和卸载只修改下一次 Runtime 的输入：

```text
Plugin Configuration Change
          ↓
      Reload Required
          ↓
Rebuild Plugin Runtime
```

## 1.2 V1 成立的现实前提

本设计依赖三个前提：

1. Restricted Plugin 当前主要来自官方或合作方，不开放任意第三方 JavaScript 市场；
2. Builtin Plugin 与 Kernel 属于同一个 Console 构建产物；
3. 当前不存在真实的 Trusted External Direct Plugin。

任何前提失效时，必须重新评估对应消融结论，不能继续向当前模型硬塞分支。

## 1.3 非目标

V1 不实现：

```text
Hot Install / Hot Unload / Hot Upgrade

Plugin-level deactivate() / General Effect Rollback

Runtime Dependency Reconcile

Capability Provider Watch / Provider Switching

Trusted External Direct Plugin

External ESM / Module Federation Loader

Generic RuntimeLoader / PluginAdapter

First-class SandboxPluginSDK

Generic RPC Framework

Native Sandboxed iframe

Independent Plugin Origin

Hostile-code Containment

Generic EventBus

SemVer Solver / Multiple Provider Negotiation

Parallel Builtin Activation
```

# 2. 最终核心原则

```text
1. Runtime 生命周期内 Plugin Set immutable

2. Plugin Set 变化统一通过 Reload 生效

3. Builtin 与 Kernel 同包构建并直接 activate

4. External Plugin 在 V1 统一为 Restricted + Wujie

5. Plugin Dependency 只通过 Capability

6. Capability 使用 name@major

7. requires / provides 只在 Bootstrap 解析一次

8. Host Core Roots 的传递性依赖闭包必须全部是 Builtin

9. UI 扩展统一通过 Contribution

10. Contribution 顺序显式且 deterministic

11. Restricted Contribution 必须 Manifest-first

12. Restricted Plugin 不能提供 Global Capability

13. 只有 Bridge-exposed Capability 需要
    Action / Schema / Permission Contract

14. Permission 在每次 Bridge Action 调用时检查

15. Wujie 只承诺 cooperative-isolation

16. Backend Authorization 仍是真正的数据安全边界

17. Core Closure Failure fail-fast

18. Non-core Builtin / Restricted Surface Failure fail-soft

19. Inspector 只投影 Runtime Facts

20. 不为未来变化提前建立通用框架

21. Restricted Plugin ACTIVE 只表示 Bootstrap 已接受，
    不表示 Wujie Instance 已运行

22. Restricted Plugin Code 只在 Surface 被访问时按需执行
```

# 3. 规范术语

| 术语 | 含义 |
|---|---|
| Plugin Kernel | 最小不可插件化 Runtime，负责 Bootstrap、Resolver 和两个 Registry |
| Builtin Plugin | 与 Kernel 同包构建、直接获得 PluginContext 的可信代码 |
| Restricted Plugin | 平台不向其提供 Direct `PluginContext`、Host Runtime Object 或 Raw Host API；平台支持的正式集成路径固定为 Wujie + `PluginBridge` 的外部插件 |
| PluginDescriptor | Resolver 需要的最小依赖声明 |
| PluginDefinition | Builtin Plugin 的静态定义与 activate 实现 |
| RestrictedPluginManifest | Restricted Plugin 在代码执行前可验证的完整声明 |
| InstalledPluginConfig | 平台保存的安装版本、启用状态和 Granted Permissions |
| Capability | Plugin 之间共享行为的版本化 Contract |
| BridgeCapabilityContract | Host 为可跨 Bridge 使用的 Capability 定义的 Action Contract |
| Contribution | Route、Navigation 或 UI Extension 的声明与 Registry Record |
| Surface Definition | Restricted Plugin 在 Manifest 中声明的可挂载 UI 资源，不是 UI Contribution |
| Surface Instance | Host 为一次具体 Surface 挂载创建的浏览器运行实例 |
| BridgeSession | Host 在 Handshake 成功后绑定到一个 Surface Instance 与 MessagePort 的通信会话 |
| Subscription | 由 Bridge Capability Action 创建、只在所属 BridgeSession 内有效的定向事件流 |
| Core Root | Host 源码中显式指定、Console Ready 必须依赖的 Builtin Plugin |
| Core Closure | 从 Core Roots 沿 Capability Provider 反向展开得到的传递性 Plugin 集合 |
| Plugin Runtime State | Plugin 在 Bootstrap 完成后的最终事实：ACTIVE、SKIPPED 或 FAILED |

`Restricted` 描述的是平台提供的能力与正式集成边界，不是浏览器安全隔离承诺，也不代表 Host 可以安全执行任意恶意 JavaScript。同源 Wujie 的实际安全边界以第 11 章为准。

V1 不存在 `trusted` 外部类型，也不保存通用的 `trustLevel`、`executionMode`、`securityPosture` 或 `critical` 字段。

这些展示信息全部由来源和 Core Closure 派生：

| Runtime 事实 | Execution | Security Posture | Core |
|---|---|---|---|
| Builtin | direct | full-trust | 由 Core Closure 决定 |
| Restricted | wujie | cooperative-isolation | 永远否 |

# 5. 核心数据模型

## 5.1 基础标识

```ts
type PluginId = string;

type CapabilityId =
  `${string}@${number}`;

type HostApiId =
  `${string}@${number}`;

type PermissionId = string;

type JsonValue =
  | null
  | boolean
  | number
  | string
  | JsonValue[]
  | { [key: string]: JsonValue };
```

约束：

- Plugin ID 在一个 Runtime 内唯一；
- Builtin Plugin ID 是保留命名空间，Restricted Plugin 不能覆盖同名 Builtin；
- Capability ID 必须包含一个显式 Major；
- Host API ID 必须包含一个显式 Major；
- V1 不接受版本范围；
- 同一 `CapabilityId` 只能有一个 Provider；
- Route ID 与 Navigation ID 在 Runtime 内分别唯一；
- UI Extension ID 在同一个 Slot 内唯一；
- Restricted `SandboxSurfaceDefinition.id` 在当前 Plugin Manifest 内唯一。

## 5.2 PluginDescriptor

```ts
interface PluginDescriptor {
  id: PluginId;

  version: string;

  requires: readonly CapabilityId[];

  provides: readonly CapabilityId[];
}
```

`PluginDescriptor` 是 Resolver 的唯一输入 Contract。

它不包含：

```text
entry

permissions

contributions

activate implementation

execution mode

runtime state
```

## 5.3 Builtin PluginDefinition

```ts
interface PluginDefinition
  extends PluginDescriptor {

  activate(
    context: PluginContext,
  ): void | Promise<void>;
}
```

Builtin Definitions 通过静态 import 收集：

```ts
import consoleShell
  from "./plugins/console-shell";

import cluster
  from "./plugins/cluster";

export const builtinDefinitions = [
  consoleShell,
  cluster,
];
```

Builtin 不生成仅为形式统一而存在的 `plugin-manifest.json`，也不经过动态 Loader。

## 5.4 RestrictedPluginManifest

```ts
interface RestrictedPluginManifest
  extends PluginDescriptor {

  // Restricted V1 固定不能 provide。
  provides: readonly [];

  // V1 必须是平台允许的同源入口。
  entry: string;

  // 例如 kubesphere.console@1。
  hostApi: HostApiId;

  // Requested Permissions。
  permissions: readonly PermissionId[];

  // 可被 Route / Extension 引用的 UI 资源。
  surfaces:
    readonly SandboxSurfaceDefinition[];

  contributions: {
    routes?:
      readonly RestrictedRouteContribution[];

    navigation?:
      readonly NavigationContribution[];

    extensions?:
      readonly RestrictedUiExtensionContribution[];
  };
}
```

示例：

```json
{
  "id": "kubeeye",
  "version": "1.2.0",
  "entry": "/plugins/kubeeye/1.2.0/",
  "hostApi": "kubesphere.console@1",
  "requires": [
    "kubesphere.cluster@2"
  ],
  "provides": [],
  "permissions": [
    "cluster.read",
    "workload.read"
  ],
  "surfaces": [
    {
      "id": "workload-detail"
    },
    {
      "id": "overview"
    }
  ],
  "contributions": {
    "routes": [
      {
        "id": "overview-route",
        "path": "/kubeeye",
        "surfaceId": "overview"
      }
    ],
    "navigation": [
      {
        "id": "overview-nav",
        "label": "KubeEye",
        "routeId": "overview-route",
        "order": 200
      }
    ],
    "extensions": [
      {
        "id": "workload-detail-tab",
        "slot": "workload.detail.tabs",
        "surfaceId": "workload-detail",
        "order": 200
      }
    ]
  }
}
```

Manifest 不允许声明：

```text
trustLevel

runtime.type

requested direct / iframe

critical

Bridge Action

Action Schema

Action -> Permission mapping
```

`hostApi` 同样只比较显式 Major。Host 不支持该 Major 时，Plugin 在 Manifest 阶段 SKIPPED，且不得加载 `entry`。

## 5.5 InstalledPluginConfig

```ts
interface InstalledPluginConfig {
  id: PluginId;

  version: string;

  enabled: boolean;

  grantedPermissions:
    readonly PermissionId[];
}
```

必须满足：

```text
Config.id = Manifest.id

Config.version = Manifest.version

Granted Permissions
  ⊆ Manifest Requested Permissions

```

### 5.5.1 Restricted 校验分层

Restricted 校验必须按“先局部，再全局”分两层执行，不得把所有错误都模糊归因为 Resolver 或 Runtime 错误。

`Local Validation` 只依赖当前 Manifest 与 Config，可在安装期和 Runtime Bootstrap 复用：

```text
Manifest / Config schema

ID uniqueness inside the Manifest

Route / Extension surfaceId
  -> exists in the same Manifest surfaces

Permission ID format

HostApiId format

provides = []

Config.id / version match Manifest

Granted Permissions
  ⊆ Manifest Requested Permissions
```

`Runtime Validation` 依赖当前 Host Catalog、待构建的 Plugin Set 或 Registry：

```text
Plugin ID collision

HostApiId Major supported by Host

Capability provider existence

Every Manifest requires
  -> has Host-owned BridgeCapabilityContract

Requested Permissions
  ⊆ permissions known by required Bridge Contracts

Contribution global collision and cross-reference

Dependency cycle
```

当 Restricted Plugin 的 `requires` 指向 Direct-only Capability，或 Host 未为该 Capability 定义 `BridgeCapabilityContract` 时，必须在 Manifest 阶段返回：

```ts
{
  code: "CAPABILITY_NOT_BRIDGE_EXPOSED",
  validationStage: "manifest",
  pluginId,
  capability,
}
```

该错误发生在 Plugin Code 执行和 BridgeSession 创建之前，不是运行期 RPC 错误。

Artifact Entry、Surface Definition、Requested Permissions 和 Contribution 属于版本化 Manifest；管理员决策只保存在 Installed Config。

安装存储交给 Bootstrap 的记录是一个简单配对：

```ts
interface InstalledPluginRecord {
  manifest: RestrictedPluginManifest;

  config: InstalledPluginConfig;
}
```

## 5.6 Bootstrap 内部输入

Bootstrap 可以使用一个局部 discriminated union：

```ts
type PluginInput =
  | {
      kind: "builtin";
      definition: PluginDefinition;
    }
  | {
      kind: "restricted";
      manifest: RestrictedPluginManifest;
      config: InstalledPluginConfig;
    };
```

`kind` 是从来源得到的 Runtime Fact，不是可由 Plugin 请求的 Trust Policy。

# 6. Runtime 与生命周期

## 6.1 Runtime Immutable

一次页面加载只构建一次 Runtime：

```text
Page Load
   ↓
Collect Inputs
   ↓
Validate
   ↓
Resolve
   ↓
Activate Builtins
   ↓
Commit Restricted Declarations
   ↓
Runtime Ready
```

Ready 后不再：

```text
增加或删除 Plugin

重算 Dependency DAG

替换 Capability Provider

动态注册 Restricted Contribution

重新激活 Consumer
```

Runtime Immutable 约束的是 Plugin Set、Dependency、Capability Provider、Surface Definition 与 Contribution。Ready 后创建或销毁 Surface Instance、BridgeSession 和 Subscription 属于声明资源的按需运行，不会重建或修改上述集合。

## 6.2 Plugin 与 Surface 生命周期入口

Builtin 只有：

```ts
activate(context)
```

Restricted 没有 Plugin 级 `activate()`。它在 Bootstrap 中只提交经过验证的 Surface Definition 与 Contribution，并进入 `ACTIVE`。

当 UI Host 实际渲染一个 Restricted Route 或 Extension 时，才调用具体的：

```ts
wujiePluginAdapter.mount({
  pluginId,
  surfaceId,
  mountPointId,
  container,
  initialParameters,
})
```

V1 没有通用 `PluginAdapter` Interface，也没有 Plugin 级 `deactivate()`。

`mount()` 发生在 Runtime Ready 之后；它不得增加 Plugin、注册 Contribution、重算依赖或替换 Capability Provider。

Route 或 Extension 离开页面时，Wujie Adapter 必须 dispose 对应 BridgeSession 并清理它创建的浏览器资源。这是 Surface Instance Lifecycle，不是 Plugin Set 的动态变更。

## 6.3 激活期注册原子性

为了让 Non-core Plugin 可以 fail-soft，Builtin 激活不能向全局 Registry 留下半完成状态。

Bootstrap 为每个 Builtin 创建绑定 owner 与 descriptor 的 `PluginContext`。该 Context 在激活期间暂存 Capability 和 Contribution 注册：

```text
begin activation
      ↓
PluginContext 暂存注册
      ↓
activate() success
      ↓
validate declared provides
      ↓
atomic commit to Registries
```

Commit 必须先校验 Capability 与 Contribution 两组 staged records，再一次性写入；不能先提交一个 Registry、随后在另一个 Registry 冲突。

Activation-local staged registrations 只对其 owner 的绑定 Context 与 Bootstrap 提交逻辑可见，不得通过 Global Registry 暴露给其他 Plugin。`PluginContext.capabilities.require()` 始终只读取已经成功 commit 的 Global Capability，不得读取任何 Plugin 的 staging area。

任何 throw 或 assertion failure：

```text
discard staged records
```

这只是 Registry 写入缓冲，不是通用 EffectScope、Disposer 或任意副作用 rollback。

Builtin `activate()` 必须只通过 `PluginContext` 修改 Host Plugin Runtime，不应直接修改全局 DOM、全局 Store 或其他 Plugin 内部状态。

# 7. DependencyResolver

## 7.1 输入与输出

输入：

```text
PluginDescriptor[]
+
Plugin kind
+
Core Root IDs
```

输出至少包含：

```ts
interface Resolution {
  order: readonly PluginId[];

  coreClosure: ReadonlySet<PluginId>;

  dependencies: readonly {
    consumer: PluginId;
    capability: CapabilityId;
    provider: PluginId;
  }[];

  skipped: ReadonlyMap<
    PluginId,
    string
  >;
}
```

Resolver 是纯计算 Module，不加载 Artifact、不执行 Plugin Code、不写 Registry。

`Resolution.order` 是稳定的 Bootstrap Order：对 Builtin 它决定串行 activate 顺序；对 Restricted 它只决定 Declaration commit 的处理顺序，不表示或触发 Wujie 执行。

## 7.2 Resolve 算法

```text
Validate unique Plugin IDs
        ↓
Build capability -> provider index
        ↓
Reject duplicate providers
        ↓
Resolve every requires edge
        ↓
Detect missing capability
        ↓
Build dependency DAG
        ↓
Detect cycles
        ↓
Compute Core Closure
        ↓
Validate Core Closure is all Builtin
        ↓
Stable topological sort
```

稳定拓扑排序的 tie-breaker 使用：

```text
pluginId ASC
```

配置数组顺序不能表达依赖处理或 Builtin 激活优先级。

如果 Restricted ID 与 Builtin ID 冲突，只将 Restricted Plugin 标记为 SKIPPED，Builtin 永远不会被安装记录覆盖。重复 Builtin ID 属于 Host 构建错误；涉及 Core 时 Runtime Bootstrap Failed。

## 7.3 Capability Provider 规则

V1 不做 Multiple Provider Negotiation。

同一 `CapabilityId` 出现多个 Provider 时：

```text
DUPLICATE_CAPABILITY_PROVIDER
```

Resolver 不选择“第一个”、最高版本或配置优先级。

如果冲突 Provider 或该 Capability 影响 Core Closure，Runtime Bootstrap Failed；否则冲突 Provider 全部 SKIPPED，并递归 Skip Consumer。

Major 不兼容等价于 Missing：

```text
requires kubesphere.cluster@2

only provides kubesphere.cluster@1

=> MISSING_CAPABILITY
```

## 7.4 Core Roots 与 Core Closure

V1 不在 Plugin 上保存 `critical: boolean`。

Host 源码定义 Core Roots：

```ts
const CORE_PLUGIN_IDS = [
  "console-shell",
] as const;
```

Resolver 从 Core Roots 沿实际 Capability Provider 展开传递依赖，得到 Core Closure。

必须满足：

```text
∀ plugin ∈ Core Closure:
  plugin.kind = builtin
```

如果 Core Root 缺失、Core 依赖缺失、Core 依赖形成环，或 Core Closure 包含 Restricted Plugin：

```text
Runtime Bootstrap Failed
```

Resolver 必须输出完整依赖路径，例如：

```text
console-shell
  -> kubesphere.cluster@2
  -> external-cluster-provider
```

## 7.5 Non-core Skip 传播

Descriptor / Manifest 或 Dependency 错误只影响 Non-core 时：

```text
Invalid Provider
      ↓
Provider SKIPPED
      ↓
Consumers recursively SKIPPED
```

如果 Builtin Provider 在 Activation 阶段失败，Bootstrap 不需要在全部激活后再运行一次递归传播。它必须在稳定拓扑顺序中，在执行每个尚未执行的 Builtin 前检查 Provider 终态：

```text
for plugin in bootstrapOrder:
  if plugin is not an executable Builtin:
    continue

  if any dependency provider != ACTIVE:
    plugin = SKIPPED
  else:
    activate plugin
    validate declarations
    atomically commit registrations
```

因为 Provider 一定排在 Consumer 之前，单次顺序执行就会自然把失败传给所有后续 Consumer。Restricted Declaration commit 也必须在提交前检查所有 Provider 均为 `ACTIVE`。

Restricted Plugin 的 `provides` 固定为空，因此：

- Builtin 不会依赖 Restricted；
- Restricted 之间不会产生 Provider 依赖；
- Restricted 只能消费已成功激活的 Builtin Capability。

# 8. Capability

## 8.1 Capability Contract

Plugin 应依赖：

```text
Capability Contract
```

而不是：

```text
Provider Plugin Implementation

Provider Store

Provider React Context
```

Capability 使用：

```text
capability-name@major
```

只表达 Major Compatibility，不实现 SemVer Range。

## 8.2 CapabilityRegistry

```ts
interface CapabilityRecord<T = unknown> {
  id: CapabilityId;

  providerPluginId: PluginId;

  value: T;
}

type CapabilityMetadata =
  Omit<CapabilityRecord, "value">;

interface CapabilityRegistry {
  get<T>(
    id: CapabilityId,
  ): T | undefined;

  require<T>(
    id: CapabilityId,
  ): T;

  list():
    readonly CapabilityMetadata[];
}
```

`list()` 只返回不可变 Metadata，不暴露 Capability Value。

Global Registry 的写接口仅供 Bootstrap 绑定后的 Context 使用，Plugin 不传入 owner：

```ts
interface PluginCapabilityContext {
  register<T>(
    id: CapabilityId,
    value: T,
  ): void;

  require<T>(
    id: CapabilityId,
  ): T;
}
```

Context 自动使用当前 `pluginId`，并立即执行声明校验：

```text
register(id)
  -> id ∈ descriptor.provides

require(id)
  -> id ∈ descriptor.requires
```

`require(id)` 的查找范围仅为 Global Registry 中已提交的 Capability Record。上游 Provider 的 activate 未成功 commit 时，Consumer 不能观察到其 staged value。

Builtin activate 成功后还必须检查：

```text
descriptor.provides
        ⊆
staged registered capabilities
```

## 8.3 Direct-only Capability

仅供 Builtin 使用的 Capability 只需要 TypeScript Contract：

```ts
interface ClusterInternalCapability {
  getCurrentCluster(): Cluster;
}
```

它不需要：

```text
Action Table

JSON Schema

Permission Mapping
```

## 8.4 Bridge-exposed Capability

只有允许 Restricted Plugin 使用的 Capability 才需要 `BridgeCapabilityContract`：

```ts
interface RuntimeSchema<T> {
  parse(value: unknown): T;
}

interface BridgeInvocationContext {
  pluginId: PluginId;

  surfaceId: string;

  surfaceInstanceId: string;

  mountPointId: string;

  signal: AbortSignal;
}

interface BridgeUnaryActionContract<
  Request extends JsonValue = JsonValue,
  Result extends JsonValue = JsonValue,
> {
  kind: "request";

  requestSchema:
    RuntimeSchema<Request>;

  resultSchema:
    RuntimeSchema<Result>;

  requiredPermissions:
    readonly PermissionId[];

  invoke(
    capability: unknown,
    payload: Request,
    context: BridgeInvocationContext,
  ): Result | Promise<Result>;
}

interface OpenedBridgeSubscription<
  Snapshot extends JsonValue = JsonValue,
> {
  snapshot: Snapshot;

  dispose(): void | Promise<void>;
}

interface BridgeSubscriptionActionContract<
  Request extends JsonValue = JsonValue,
  Snapshot extends JsonValue = JsonValue,
  Event extends JsonValue = JsonValue,
> {
  kind: "subscription";

  requestSchema:
    RuntimeSchema<Request>;

  snapshotSchema:
    RuntimeSchema<Snapshot>;

  eventSchema:
    RuntimeSchema<Event>;

  requiredPermissions:
    readonly PermissionId[];

  open(
    capability: unknown,
    payload: Request,
    context: BridgeInvocationContext,
    emit: (event: Event) => void,
  ):
    | OpenedBridgeSubscription<Snapshot>
    | Promise<
        OpenedBridgeSubscription<Snapshot>
      >;
}

type BridgeActionContract =
  | BridgeUnaryActionContract
  | BridgeSubscriptionActionContract;

interface BridgeCapabilityContract {
  id: CapabilityId;

  actions:
    Readonly<
      Record<
        string,
        BridgeActionContract
      >
    >;
}
```

`BridgeCapabilityContract` 由 Host 定义并随 Host 发布。

它只描述跨 Bridge 的调用方式，不是 Capability Provider；对应 `CapabilityId` 仍必须由成功激活的 Builtin 注册到 `CapabilityRegistry`。

Restricted Manifest 只声明：

```text
requires capability@major

requested permissions
```

Manifest 和 Plugin Runtime 都不能新增 Action、替换 Schema 或改变 Action 所需 Permission。

`BridgeCapabilityContract` 只支持 Host 显式定义的 Unary Action 与 Subscription Action。V1 不增加任意方法调用、动态服务发现、反射或 Plugin-defined Service Registration，也不将它抽象成通用 RPC Framework。

Subscription Action 仍然是 Host Capability Contract 的一部分，不是 Plugin 可以自定义的 Event Topic。`PluginBridge` 负责生成 `subscriptionId`、验证 Snapshot 与 Event、持有 disposer，并保证 Snapshot Response 发送前不会向 Plugin 投递后续 Event。

## 8.5 不提供 Generic EventBus

跨 Plugin 状态变化通过 Capability 表达：

```ts
interface ScopeCapability {
  getCurrent(): Scope;

  subscribe(
    listener: (scope: Scope) => void,
  ): () => void;
}
```

Bridge-exposed 版本把订阅映射为：

```text
Host-defined Subscription Action
        ↓
Atomic Initial Snapshot
        +
BridgeSession-scoped Event Stream
```

订阅不使用全局 Topic；它只能由声明在 `manifest.requires` 中的 Bridge-exposed Capability 创建。V1 不提供可以绕过 Capability Ownership 的全局 EventBus。

Theme、Locale、Cluster Scope 和 Workspace Scope 等动态 Host 状态都必须分别归属于对应 Capability，并使用同一套 Snapshot + Subscription 语义。

# 9. Contribution

## 9.1 三种业务 Contract

```ts
interface BuiltinRenderTarget {
  kind: "builtin";

  render: unknown;
}

interface SandboxSurfaceDefinition {
  id: string;
}

interface SandboxRenderTarget {
  kind: "sandbox-surface";

  surfaceId: string;

  layout?: JsonValue;

  initialParameters?: JsonValue;
}

type HostRenderTarget =
  | BuiltinRenderTarget
  | SandboxRenderTarget;

interface RouteContribution {
  id: string;

  path: string;

  target: HostRenderTarget;
}

interface RestrictedRouteContribution {
  id: string;

  path: string;

  surfaceId: string;

  layout?: JsonValue;

  initialParameters?: JsonValue;
}

interface NavigationContribution {
  id: string;

  label: string;

  parentId?: string;

  routeId?: string;

  order?: number;
}

interface UiExtensionContribution {
  id: string;

  slot: string;

  order?: number;

  target: HostRenderTarget;
}

interface RestrictedUiExtensionContribution {
  id: string;

  slot: string;

  surfaceId: string;

  order?: number;

  layout?: JsonValue;

  initialParameters?: JsonValue;
}
```

Route、Navigation 与 UI Extension 的业务语义不同，不能粗暴退化成一个万能 Slot Contract。

`SandboxSurfaceDefinition` 只定义 Plugin 可以渲染的 UI 资源；Restricted Route 与 Extension 才定义该资源在 Host 中的挂载位置。同一个 Surface Definition 可以被多个 Contribution 引用，每次实际挂载仍创建独立的 Surface Instance。

`layout` 与 `initialParameters` 属于本次 Route / Extension 挂载。如果未来出现对所有挂载都相同的 Surface 固有属性，再将该属性加入 `SandboxSurfaceDefinition`，V1 不提前建立默认值覆盖规则。

## 9.2 ContributionRegistry

底层统一：

```text
Ownership

Indexing

Stable Ordering

Conflict Diagnostics

Inspection
```

对外保留 typed interface：

```ts
interface ContributionRegistry {
  registerRoute(
    ownerPluginId: PluginId,
    contribution: RouteContribution,
  ): void;

  registerNavigation(
    ownerPluginId: PluginId,
    contribution:
      NavigationContribution,
  ): void;

  registerExtension(
    ownerPluginId: PluginId,
    contribution:
      UiExtensionContribution,
  ): void;

  listRoutes():
    readonly OwnedContribution<
      RouteContribution
    >[];

  listNavigation():
    readonly OwnedContribution<
      NavigationContribution
    >[];

  listExtensions(
    slot: string,
  ): readonly OwnedContribution<
    UiExtensionContribution
  >[];
}
```

Builtin 使用的 `PluginContributionContext` 不暴露 `ownerPluginId` 参数，Ownership 由绑定 Context 自动补充。

```ts
interface OwnedContribution<T> {
  ownerPluginId: PluginId;

  contribution: T;
}

interface PluginContributionContext {
  registerRoute(
    contribution: RouteContribution,
  ): void;

  registerNavigation(
    contribution:
      NavigationContribution,
  ): void;

  registerExtension(
    contribution:
      UiExtensionContribution,
  ): void;
}

interface PluginContext {
  capabilities:
    PluginCapabilityContext;

  contributions:
    PluginContributionContext;
}
```

`listRoutes`、`listNavigation` 和 `listExtensions` 返回不可变、已经稳定排序的 Snapshot，不暴露 Registry 内部可变集合。

Contribution 冲突与引用必须按以下规则归因：

| 字段 | V1 规则 |
|---|---|
| `RouteContribution.id` | Runtime 全局唯一 |
| `NavigationContribution.id` | Runtime 全局唯一 |
| `UiExtensionContribution.id` | 在同一 `slot` 内唯一 |
| `RouteContribution.path` | 由 Host Router Contract 决定是否允许重复与如何匹配；Registry 不强制 path 全局唯一，也不把 path 冲突报成 ID collision |
| `NavigationContribution.routeId` | 可引用任意 owner 最终为 `ACTIVE` 的 Route ID，允许跨 Plugin 引用 |
| `NavigationContribution.parentId` | 可引用任意 owner 最终为 `ACTIVE` 的 Navigation ID，允许跨 Plugin 引用 |

跨 Plugin 引用必须对本次 Bootstrap 最终 eligible 的全量 Contribution 集合校验，不能受 Restricted Declaration 提交先后顺序影响。这类引用只是 Contribution 完整性约束，不建立 Capability Dependency Edge，也不影响 Bootstrap Order。

Restricted Manifest 不直接声明 `HostRenderTarget`。它的 Route 与 Extension 只引用 Manifest 中的 `surfaceId`，Host 再将其规范化为 `{ kind: "sandbox-surface", surfaceId, ...mountOptions }`；因此 Restricted 数据不能包含 Host-local render value。Builtin Context 可以直接注册 `{ kind: "builtin", render }`。UI Host 根据显式 `kind` 渲染，不猜测来源。

## 9.3 排序

所有有视觉顺序的 Contribution 使用：

```text
order ASC
    ↓
ownerPluginId ASC
    ↓
contributionId ASC
```

默认 `order` 必须是固定常量，不能使用注册时刻或 Bootstrap Order。

Route 匹配优先级继续由 Host Router Contract 决定；Registry 插入顺序不得改变 Route 语义。Inspector 中的 Route 列表使用稳定 Metadata 排序即可。

## 9.4 Contribution 不产生 Dependency

```text
kubeeye contributes
  -> workload.detail.tabs
```

不等于：

```text
kubeeye requires
  -> workload plugin
```

如果当前 Runtime 没有对应 Slot，Contribution 保持未使用即可。

只有 Capability `requires` 形成 Dependency DAG Edge。

## 9.5 Restricted Manifest-first

Restricted Plugin 的 Surface Definition、Route、Navigation 和 UI Extension 必须全部由 Manifest 静态声明。

Bootstrap 在执行 Restricted Plugin Code 前：

```text
Validate Surface Definitions
        ↓
Validate IDs and collisions
        ↓
Validate Route / Extension -> surfaceId
        ↓
Validate Navigation -> routeId when present
        ↓
Validate Navigation -> parentId when present
        ↓
Normalize Route / Extension render targets
        ↓
Atomically register Contributions
and commit Plugin ACTIVE
```

PluginBridge 不提供：

```text
registerRoute

registerNavigation

registerExtension

replaceContribution
```

Host 将 Restricted Route 和 Extension 规范化为带 `SandboxRenderTarget` 的 Registry Record；Navigation 保留对 Route ID 的引用。Surface Definition 由 Runtime 保存，不能作为 Contribution 注册。

同一个 Restricted Manifest 的 Surface Definition 与 Contribution 必须先全部验证，再原子提交 Surface Definition、Contribution 和 `ACTIVE` 状态；任一冲突都丢弃该 Plugin 的整组记录，不能留下部分 Route、Navigation 或 Extension。

Restricted Runtime 只能在 Host 已声明并分配的 `surfaceId` 中渲染和交换结构化状态。

如果需要条件显隐，只能使用 Host 可解释的声明式条件；V1 不接受 Plugin JavaScript Callback 作为 Host Contribution 条件。

Manifest 或 Dependency 阶段已经 SKIPPED 的 Restricted Plugin 不注册 Contribution。

UI Host 使用 Plugin Runtime State 投影，只消费 owner 状态为 `ACTIVE` 的 Contribution。Restricted Plugin 的 `ACTIVE` 不要求任何 Surface 已经挂载；Surface Instance 随后失败时，Contribution 与 Plugin `ACTIVE` 状态保持不变，由 Host Error Boundary 替换该实例的内容。

# 10. 两条执行路径

## 10.1 Builtin Direct

Builtin：

- 静态 import；
- 不读取 JSON Manifest；
- 不经过 Loader；
- 不经过 Adapter；
- 按 Resolver 顺序串行调用 `definition.activate(context)`。

Builtin 与 Kernel 同包构建，因此它是 full-trust 代码。PluginContext 是组织依赖和 Ownership 的 Interface，不是 Security Sandbox。

## 10.2 Restricted Wujie

Restricted Plugin 的浏览器执行固定发生在按需 Surface Mount：

```text
Runtime Ready
        +
ACTIVE Restricted Plugin
        +
SandboxRenderTarget / Container
        ↓
WujiePluginAdapter.mount(surfaceId)
        ↓
Artifact Loading + Wujie startApp
        ↓
Bridge Handshake + BridgeSession
```

Bootstrap 不调用 `startApp`，也不为了让 Plugin 进入 `ACTIVE` 而创建隐藏容器、Wujie Instance 或 MessagePort。

`WujiePluginAdapter` 是具体 Browser Adapter，负责：

```text
Artifact Loading

Wujie App Bootstrap

Stable Instance Naming

Surface Mount / Unmount

Bridge Handshake

Host Loading / Error Boundary

MessagePort and Listener Cleanup
```

V1 建议默认：

```text
sync = false

alive = false

fiber = true

degrade = false

V1 不调用 preloadApp
```

含义：

- Host 持有顶层 Route；
- Surface 离开后清理实例资源；
- 不建立并行预加载或预执行阶段；
- Runtime Ready 且 UI Host 请求挂载后，才允许通过 `startApp` 执行 Plugin Code；
- `fiber` 只改善调度，不提供 CPU 隔离；
- Wujie degrade 模式不作为第三条 Runtime 路径，必须由 Console Browser Support Matrix 单独约束。

这些参数语义以 Wujie 官方 [`startApp`](https://wujie-micro.github.io/doc/api/startApp.html) 文档为准。

Wujie `name` 由 Adapter 统一生成，必须在一个 Surface Instance 生命周期内稳定、在当前 Host 中唯一，并且不能被不同 Surface Instance 复用。

每次 `mount()` 创建新的 Surface Instance；即使同一个 Surface Definition 同时被 Route 与 Extension 使用，也不得共享 DOM Container、Wujie Instance、MessagePort 或 BridgeSession。

每个 Surface Instance 必须保存以下 Host-side Runtime Identity：

```ts
interface SurfaceInstanceIdentity {
  pluginId: PluginId;

  pluginVersion: string;

  surfaceId: string;

  surfaceInstanceId: string;

  mountPointId: string;
}
```

`mountPointId` 由 UI Host 根据实际挂载位置生成，例如 `route:overview-route` 或 `extension:workload.detail.tabs/workload-detail-tab`。它是用于 Inspector、Audit 和错误归因的 Runtime Fact，不进入 Manifest Contract。

Mount 的最小顺序是：

```text
Resolve ACTIVE owner and Surface Definition
        ↓
Create Surface Instance as MOUNTING
        ↓
startApp in the provided container
        ↓
Complete Bridge Handshake
        ↓
Surface Instance MOUNTED
```

Artifact、Wujie Bootstrap、Handshake、Render 或持续 Bridge 错误只使当前 Surface Instance 进入 `FAILED`，并由当前 Host mount point 保留该事实供 Error Boundary 与 Inspector 使用。Unmount 必须先 dispose BridgeSession，再销毁 Wujie Instance 和 Listener；完成后从当前实例集合移除该记录。

Bridge Bootstrap Descriptor 是 Host 传给当前 Wujie Surface 的最小连接数据：

```ts
interface BridgeBootstrapDescriptor {
  protocolVersion: number;

  surfaceInstanceId: string;

  nonce: string;
}
```

该 Descriptor 使用拒绝未知字段的 closed schema，不得包含 `pluginId`、Permissions、Capability List 或 Token。真实的 Plugin Identity、Manifest `requires` 与 Granted Permissions 由 Host 在 Handshake 成功后根据 `surfaceInstanceId` 绑定到 MessagePort，不信任 Plugin 回传的同名数据。

传给 Wujie Plugin 的 props 只能包含：

```text
Non-sensitive Plugin Metadata

Bridge Bootstrap Descriptor
```

Non-sensitive Plugin Metadata 只用于展示或调试，不作为 BridgeSession Identity、Permission 或 Capability 选择的输入。

不得包含：

```text
Host Store

React Context

DOM Node

Function Reference

Access Token

Raw API Client
```

Restricted `entry` 必须通过 Host Artifact Allowlist，并且 V1 只支持平台允许的同源部署路径。

# 11. 信任与安全边界

## 11.1 Threat Model

| 目标 | Restricted Wujie V1 |
|---|---|
| 减少全局变量、样式、路由和生命周期的意外冲突 | 支持 |
| 约束正式 Bridge 可以执行的操作 | 支持 |
| 限制 Buggy Plugin 的重复调用和 RPC 风暴 | 支持 |
| Plugin 主动绕过 Bridge 后仍保护 Host | 不支持 |
| 执行任意敌对 JavaScript | 不支持 |

Wujie 同源模式不能可靠阻止 Plugin 主动访问：

```text
window.parent

Host DOM

Host JavaScript Object

JavaScript-readable Cookie

localStorage / sessionStorage

同源 API
```

Wujie 官方运行原理也明确说明子应用 iframe 与主应用同源，并可直接使用 `window.parent` 通信，参见 [Wujie 运行机制](https://wujie-micro.github.io/doc/guide/)。

因此 UI、文档和 Inspector 必须使用：

```text
cooperative-isolation
```

不能使用：

```text
secure sandbox

malicious-code safe
```

## 11.2 Network 与 Backend Authorization

Wujie custom fetch 可以用于：

```text
Artifact Allowlist

Resource Observability

Loading Error Attribution

Caching
```

它不是 Network Security Boundary。同源 Plugin 仍可能直接使用浏览器原生 `fetch`、XHR、Image 等接口。

后端必须继续执行：

```text
Authentication

Kubernetes / KubeSphere RBAC

Resource Authorization
```

前端 Permission 只约束正式 Bridge，不能替代后端授权。

# 12. Permission 与 PluginBridge

## 12.1 Permission Model

安装阶段：

```text
Manifest Requested Permissions
              +
Platform / Admin Decision
              ↓
       Granted Permissions
```

Runtime 不再计算或保存 `EffectivePermissions`。

每次 Bridge Action 调用检查：

```text
Action.requiredPermissions
          ⊆
Config.grantedPermissions
```

同时必须保证：

```text
Granted Permissions
  ⊆ Requested Permissions
```

Requested Permission 必须是该 Manifest 所需 `BridgeCapabilityContract` 中已知的 Permission；Manifest 不能创造新的 Permission 语义。

## 12.2 Handshake

Handshake 由 Host 发起。Host 必须在创建 BridgeSession 前校验一次：

```text
Surface Instance exists and is MOUNTING

Bridge Protocol Version is supported

Runtime Nonce is valid, unused,
and bound to this Surface Instance
```

Nonce 成功校验后立即失效；它只用于关联本次 Handshake，不是同源 Wujie 下的 Hostile-code Authentication Boundary。

Handshake 成功后，Host 创建 BridgeSession，并把以下事实不可变地绑定到专用 MessagePort：

```text
Plugin ID

Plugin Version

Surface ID

Surface Instance ID

Mount Point ID

Negotiated Bridge Protocol Version

Manifest requires

Granted Permissions

MessagePort
```

Plugin 不能自行声明或切换 Identity、Granted Permissions、Capability Contract 或所属 Surface Instance。BridgeSession 只有 `ACTIVE` 与 `DISPOSED` 两个持久事实；Handshake 过程只是 Adapter 的瞬时状态，不保存为 Session State。

Privileged Capability 调用只使用 Host 创建的 MessagePort。Wujie 全局 EventBus 不作为 Capability、Permission 或 Extension Channel。

## 12.3 Bridge Message Envelope

```ts
interface BridgeRequest {
  type: "request";

  requestId: string;

  capability: CapabilityId;

  action: string;

  payload: JsonValue;
}

interface BridgeUnsubscribeRequest {
  type: "unsubscribe";

  requestId: string;

  subscriptionId: string;
}

type BridgeResponse =
  | {
      type: "response";
      requestId: string;
      ok: true;
      result: JsonValue;
    }
  | {
      type: "response";
      requestId: string;
      ok: false;
      error: {
        code: string;
        message?: string;
      };
    };

interface BridgeSubscriptionResult {
  subscriptionId: string;

  snapshot: JsonValue;
}

interface BridgeEvent {
  type: "event";

  subscriptionId: string;

  payload: JsonValue;
}

type PluginToHostBridgeMessage =
  | BridgeRequest
  | BridgeUnsubscribeRequest;

type HostToPluginBridgeMessage =
  | BridgeResponse
  | BridgeEvent;
```

Message 必须是结构化、可序列化数据。Envelope 使用拒绝未知字段的 closed schema，不能静默接受身份或协议字段。

可以向 Restricted Plugin 开发者发布 `@kubesphere/plugin-bridge`，提供 `bridge.request(...)` 与 `bridge.subscribe(...)` 等 client API。该包只是 `PluginBridge` 协议的 client implementation，不引入 `SandboxPluginSDK` 一级架构概念，也不进入 Kernel 架构图。

Plugin-to-Host Message 不携带用于授权或选择协议的 `pluginId`、Permission、nonce 或 protocolVersion；Dispatcher 只使用 MessagePort 绑定的 Host-side BridgeSession。

调用 `kind: "subscription"` 的 Capability Action 时，成功的 `BridgeResponse.result` 必须符合 `BridgeSubscriptionResult`。其中 `subscriptionId` 由 Host 生成，只在当前 BridgeSession 内唯一；`snapshot` 与订阅建立属于同一个操作，避免 `getCurrent()` 与 `subscribe()` 之间丢失变化。

`BridgeEvent` 只能由 Host 发往 Plugin，其 payload 必须通过对应 Action 的 `eventSchema`。`BridgeUnsubscribeRequest` 是 Bridge 控制消息，不是 Capability Action；它只能释放当前 Session 自己的订阅，重复释放或释放未知 ID 都返回 `result: null`，以保持幂等。Host 返回成功 Response 后，不得再投递该订阅的新 Event。

## 12.4 Dispatcher Pipeline

```text
Receive Message on Host-owned MessagePort
      ↓
Resolve the MessagePort-bound BridgeSession
      ↓
Validate BridgeSession is ACTIVE
      ↓
Check message size
      ↓
Reject duplicate requestId
      ↓
Dispatch by message type
      ├── Unsubscribe
      │     ↓
      │   Dispose Session-owned subscription
      │     ↓
      │   Record audit + return response
      │
      └── Request
            ↓
Check capability ∈ manifest.requires
      ↓
Lookup BridgeCapabilityContract
      ↓
Lookup action
      ↓
Validate request schema
      ↓
Check required permissions
      ↓
Check concurrency / rate / subscription limit
      ↓
Create timeout / cancellation scope
      ↓
Invoke active Capability Provider through Action Contract
      ↓
Unary: validate result schema
Subscription: validate snapshot, allocate subscriptionId,
store disposer and release buffered events
      ↓
Record audit
      ↓
Return response
```

成功与失败的每个出口都必须记录 Audit；不能只记录已经调用 Provider 的请求。`requestId` 去重范围是单个 BridgeSession，不能跨 Session 共享去重集合。

Subscription Action 的 `emit` 在 Snapshot Response 发送前产生的 Event 必须由 `PluginBridge` 有界暂存；Response 发送后再按 MessagePort 顺序释放。`open()` reject 或 Snapshot 校验失败时，不向 Plugin 暴露 `subscriptionId`，并丢弃缓冲 Event、调用已经取得的 disposer。每个 Event 在发送前检查 `eventSchema`、message size 与 Event rate；任一检查失败时关闭该 Subscription、调用 disposer 并记录 Host-side Contract Error，不把违规数据发给 Plugin。

这些步骤属于 `PluginBridge` 的实现，不拆成 PermissionBroker、Limiter、AuditService 或 ProtocolEngine 等一级 Module。

## 12.5 必须保留的保护

```text
requestId

duplicate rejection

timeout / cancellation

message size limit

concurrency limit

rate limit

request schema validation

result schema validation

snapshot / event schema validation

per-call permission check

per-session subscription limit

event buffer / rate limit

session-owned subscription cleanup

structured audit
```

Surface unmount 或 BridgeSession failure 必须先把 Session 标记为 `DISPOSED`，中止 Pending Request，并调用其所有 Subscription disposer。每个 disposer 至多调用一次；dispose 后的 `emit` 不再发送 Event。单个 disposer 失败不能阻止其余资源继续清理。这些机制主要提供 Bug Containment，不代表 Hostile-code Containment。

## 12.6 Bridge Error Code

V1 至少稳定定义：

```text
BRIDGE_PROTOCOL_MISMATCH

BRIDGE_NONCE_INVALID

UNKNOWN_SURFACE_INSTANCE

BRIDGE_SESSION_INACTIVE

UNDECLARED_CAPABILITY_REQUIRE

UNKNOWN_ACTION

INVALID_REQUEST

INVALID_RESULT

INVALID_EVENT

PERMISSION_DENIED

DUPLICATE_REQUEST

MESSAGE_TOO_LARGE

RATE_LIMITED

CONCURRENCY_LIMITED

SUBSCRIPTION_LIMITED

TIMEOUT

CAPABILITY_UNAVAILABLE
```

`CAPABILITY_NOT_BRIDGE_EXPOSED` 不在这个运行期 Bridge Error Code 列表中；它是 `validationStage: "manifest"` 的 Bootstrap 稳定错误，正常进入 Runtime Ready 的 Restricted Plugin 不会在 RPC 阶段再触发它。

普通 BridgeRequest 的单次错误默认只拒绝当前 Request；Handshake、Event 与持续协议违规分别遵循上文的 Session / Subscription 失败规则。

持续、严重协议违规可以 dispose 当前 BridgeSession，并把所属 Surface Instance 标记为 `FAILED`；Restricted Plugin 仍保持 `ACTIVE`，V1 不自动重启该实例。

# 13. Bootstrap

## 13.1 完整流程

```text
Static Builtin Definitions
          +
Enabled Installed Configs
          +
Restricted Manifests
          ↓
Pair Config with exact Manifest version
          ↓
Local Validation
(schema, manifest-local IDs / references,
permission format, HostApiId format)
          ↓
Normalize Descriptor and Contributions
          ↓
Build plugin / provider / contribution indexes
          ↓
Runtime Validation
(plugin collision, HostApiId support,
provider and Bridge Contract existence,
global contribution collision / reference,
missing / duplicate / dependency cycle)
          ↓
Compute and validate Core Closure
          ↓
Stable Topological Order
          ↓
For each Core Closure Builtin serially:
check providers ACTIVE, then activate + commit
          ↓
For each remaining Builtin serially:
check providers ACTIVE, then activate + commit;
otherwise SKIPPED
          ↓
Atomically commit eligible Restricted
Surface Definitions + Contributions + ACTIVE
          ↓
ACTIVE / FAILED / SKIPPED
          ↓
Runtime Ready
```

## 13.2 顺序不变量

必须满足：

1. Restricted Plugin Code 只能在 Runtime Ready 后，由 UI Host 的显式 Surface Mount 执行；
2. Core Closure 必须先于所有 Non-core Builtin 激活；
3. Builtin 必须在自身激活前检查所有 Provider 已为 `ACTIVE`，该单次顺序检查同时完成 failure propagation，并且先于 Restricted Declaration commit；
4. 每个 Builtin 的 Registry 写入只在 activate 与 provides assertion 成功后提交；
5. Restricted Surface Definition 与 Contribution 必须由 Host 静态接受，不能等待 Runtime RPC；
6. Restricted Surface 只能在 owner 为 `ACTIVE` 时挂载，其 Bridge 只能消费已经成功提交的 Capability；
7. Runtime Ready 不要求任何 Restricted Surface 已挂载，但要求 Core Closure 全部成功。

## 13.3 伪代码

```ts
async function bootstrapPluginRuntime(
  builtins: readonly PluginDefinition[],
  installed:
    readonly InstalledPluginRecord[],
) {
  const inputs = collectInputs(
    builtins,
    installed,
  );

  const locallyValidInputs =
    validateLocalInputs(inputs);

  const resolution =
    resolveAndValidateRuntime(
    locallyValidInputs,
    ["console-shell"],
  );

  assertCoreClosureIsBuiltin(
    resolution,
    locallyValidInputs,
  );

  for (const plugin of
    orderedBuiltins(resolution)) {
    if (!allDependencyProvidersActive(
      plugin,
      resolution,
    )) {
      if (resolution.coreClosure.has(
        plugin.id,
      )) {
        throwRuntimeBootstrapFailure(
          plugin,
        );
      }

      markSkippedBecauseProviderInactive(
        plugin,
        resolution,
      );
      continue;
    }

    await activateAndCommitBuiltin(
      plugin,
    );
  }

  commitEligibleRestrictedDeclarations(
    resolution,
  );

  return createRuntime(
    resolution,
  );
}
```

`orderedBuiltins` 先返回 Core Closure，再返回其他 Builtin，两组内部都保持 Resolver 的稳定拓扑顺序。Core Builtin 未能进入 `ACTIVE` 时立即使 Runtime Bootstrap Failed；Non-core Builtin 则按上述规则在后续顺序中自然传播 `SKIPPED`。

`commitEligibleRestrictedDeclarations` 仅处理所有 Provider 均为 `ACTIVE` 的 Restricted Plugin，并对每个 Plugin 原子提交 Surface Definition、规范化 Contribution 与 `ACTIVE` 状态，不执行 `entry`。这里的函数名表达职责，不要求每一步成为独立 class 或文件。

# 14. Runtime State 与失败语义

## 14.1 最小状态

```ts
type PluginRuntimeState =
  | {
      state: "ACTIVE";
    }
  | {
      state: "SKIPPED";

      stage:
        | "manifest"
        | "resolve";

      reason: string;
    }
  | {
      state: "FAILED";

      stage:
        | "activate"
        | "assertion";

      error: unknown;
    };
```

语义：

- `SKIPPED`：Plugin Code 从未执行；
- `FAILED`：Builtin 已经尝试执行，但 activate 或声明断言失败；
- Builtin `ACTIVE`：activate、声明断言和 Registry commit 全部成功；
- Restricted `ACTIVE`：Manifest 与依赖验证成功，Surface Definition、Contribution 和状态已经原子提交，可以响应声明的 Surface Mount。

因此 V1 中 Restricted Plugin 的 Plugin-level 终态只有 `ACTIVE` 或 `SKIPPED`；执行期故障记录在 Surface Instance，不复用 Plugin `FAILED`。

`DISCOVERED`、`VALIDATED`、`LOADING` 只允许作为瞬时 Bootstrap Log，不保存为 Runtime 生命周期状态。

Plugin Runtime State 在 Bootstrap 完成后不再变化。Restricted `ACTIVE` 不表示 Artifact 已加载、Wujie Instance 已运行或 Bridge 已连接；这些是 Surface Instance 与 BridgeSession 的事实。

## 14.2 Surface Instance 与 BridgeSession 事实

```ts
type SurfaceInstanceState =
  | {
      state: "MOUNTING";
    }
  | {
      state: "MOUNTED";

      bridgeSessionState: "ACTIVE";
    }
  | {
      state: "FAILED";

      stage:
        | "artifact"
        | "wujie-bootstrap"
        | "handshake"
        | "render"
        | "bridge";

      error: unknown;
    };

type BridgeSessionState =
  | "ACTIVE"
  | "DISPOSED";

```

```text
No live instance (Inspector: UNMOUNTED)
        ↓ mount
     MOUNTING
        ├── mount failure ──→ FAILED
        └── Handshake success ──→ MOUNTED
                                      │
                               runtime failure
                                      ↓
                                   FAILED

MOUNTED / FAILED ── unmount ──→ no live instance

Handshake success ──→ BridgeSession ACTIVE
                              │
                       unmount / failure
                              ↓
                    BridgeSession DISPOSED
```

一个 Surface Definition 没有活动实例时，Inspector 可以将它投影为 `UNMOUNTED`；这表示实例不存在，不是 Plugin State，也不需要创建空的 Wujie Instance。`MOUNTING` 是 `startApp` 与 Handshake 期间的 Surface Instance 事实。

每次 mount 都生成新的 `surfaceInstanceId`。成功 Handshake 后，该实例拥有且只拥有一个 `ACTIVE` BridgeSession。失败时必须 dispose 已经创建的 Session 和浏览器资源，但在 mount point 仍存在时保留 `FAILED` 事实；unmount 完成清理后才移除实例记录。一个 Surface Instance 失败不会改变所属 Plugin 的 `ACTIVE` 状态。

Surface Instance Runtime Record 在整个 mount 生命周期中保留 `SurfaceInstanceIdentity` 与当前 `SurfaceInstanceState`。同一 Surface 的两次挂载即使其他字段相同，也使用各自的 `surfaceInstanceId` 和 `mountPointId` 做诊断归因。

Subscription 只作为 BridgeSession 内部拥有的活动记录存在：Subscription Action 成功后加入 Session，显式 Unsubscribe 或 Session dispose 后移除。V1 不为 Subscription 再建立独立 Runtime State Machine。

## 14.3 错误处理矩阵

| 阶段 | 典型错误 | Core Closure | Non-core |
|---|---|---|---|
| Descriptor / Manifest | Invalid Descriptor、Host API Incompatible、Missing Bridge Contract、Invalid Permission、Invalid Contribution | Runtime Bootstrap Failed | Plugin SKIPPED |
| Restricted Manifest | Required Capability 没有 Bridge Contract（`CAPABILITY_NOT_BRIDGE_EXPOSED`，`validationStage: "manifest"`） | 不适用 | Plugin SKIPPED，Plugin Code 不执行 |
| Resolve | Missing、Duplicate Provider、Circular、Core Closure Contains Restricted | Runtime Bootstrap Failed | Plugin SKIPPED，并递归 Skip Consumer |
| Builtin Activate | Builtin throw | Runtime Bootstrap Failed | Plugin FAILED |
| Builtin Assertion | Undeclared Require、Undeclared Provide、Declared Provide Missing | Runtime Bootstrap Failed | Plugin FAILED |
| Surface Mount | Wujie Resource Failed、Bridge Bootstrap Failed、Render Failed | 不适用 | 当前 Surface Instance FAILED；Plugin 保持 ACTIVE |
| Bridge Request | Unknown Action、Invalid Payload、Permission Denied、Rate Limited | 不适用 | 默认 Reject Request |
| Persistent Bridge Failure | 重复严重协议违规、disposed 后持续发送 | 不适用 | 当前 BridgeSession DISPOSED、Surface Instance FAILED；Plugin 保持 ACTIVE |

Core Closure 失败后 Runtime 不进入 Ready。

Non-core Builtin 失败后 Runtime 可以 Ready；Restricted Surface Failure 发生在 Ready 后，只影响对应挂载。Inspector 必须把 Plugin、Surface Instance 与 BridgeSession 的事实分别投影，不能根据一个 Surface Failure 推断 Plugin FAILED。

## 14.4 稳定错误标识

Bootstrap、Registry 与 Surface Adapter 至少稳定定义：

```text
INVALID_PLUGIN_DESCRIPTOR

INVALID_RESTRICTED_MANIFEST

PLUGIN_ID_COLLISION

HOST_API_INCOMPATIBLE

INVALID_CONTRIBUTION

MISSING_CAPABILITY

DUPLICATE_CAPABILITY_PROVIDER

CIRCULAR_DEPENDENCY

CORE_DEPENDENCY_NOT_BUILTIN

CAPABILITY_NOT_BRIDGE_EXPOSED

UNDECLARED_CAPABILITY_REQUIRE

UNDECLARED_CAPABILITY_PROVIDE

DECLARED_CAPABILITY_MISSING

PLUGIN_ACTIVATION_FAILED

WUJIE_RESOURCE_FAILED

BRIDGE_BOOTSTRAP_FAILED
```

错误对象必须包含 `pluginId`、稳定的阶段字段和可用的 Dependency / Contribution 路径；Validation Error 使用 `validationStage`，执行期错误使用 `stage`。Surface 错误还必须包含 `surfaceId`、`surfaceInstanceId` 与 `mountPointId`，不能只返回自由文本。`CAPABILITY_NOT_BRIDGE_EXPOSED` 必须额外包含 `capability` 且固定使用 `validationStage: "manifest"`。

## 14.5 不做通用 Rollback

V1 只保证：

- Builtin Registry 写入在 commit 前可丢弃；
- Wujie Adapter 清理自己创建的 Surface、BridgeSession、Subscription、MessagePort、Pending RPC 和 Listener；
- Reload 可以重建整个 Runtime。

V1 不尝试撤销 Plugin 私自执行的任意外部副作用，因此 Builtin activate 必须遵守 PluginContext 写入约束。

## 15.1 inspect 是事实投影

```text
plugins

capabilities + provider ownership

dependencies

contributions + owner ownership

core closure

surface definitions + current instance facts

bridge session state + subscription count
```

Plugin 记录示例：

```json
{
  "id": "kubeeye",
  "version": "1.2.0",
  "kind": "restricted",
  "executionMode": "wujie",
  "securityPosture": "cooperative-isolation",
  "core": false,
  "state": "ACTIVE",
  "requestedPermissions": [
    "cluster.read",

  "grantedPermissions": [
```

每条 Privileged Bridge Action 至少记录：

```text

surfaceId

surfaceInstanceId

mountPointId

capability

action

resultCode

duration

timestamp
```

Subscription Action 与 Unsubscribe 在 ID 已分配时还应记录 `subscriptionId`；Event payload 不进入 Audit。Audit 由 PluginBridge 写入现有日志或观测出口；V1 不为它建立独立 Audit Subsystem。

# 18. 验收矩阵

## 18.1 Resolver 与 Core

| 场景 | 预期 |
|---|---|
| Capability Major 匹配 | 建立正确 Provider Edge |
| Major 不匹配 | Consumer SKIPPED；涉及 Core 时 Runtime Bootstrap Failed |
| Duplicate Provider | 不选择任一 Provider，返回明确错误 |
| Circular Dependency | 输出完整 Cycle；Non-core Cycle SKIPPED |
| Core Root 缺失 | Runtime Bootstrap Failed |
| Core Closure 包含 Restricted | Plugin Code 不执行，Runtime Bootstrap Failed |
| 相同 DAG、不同输入数组顺序 | 得到相同 Bootstrap Order |
| Provider Activation 失败 | 后续顺序中每个 Consumer 在执行前检查 Provider 状态并自然 `SKIPPED`，不执行二次递归传播 |
| `hostApi` 缺少显式 Major | Local Validation 返回 `INVALID_RESTRICTED_MANIFEST` |

## 18.2 Builtin Registry 一致性

| 场景 | 预期 |
|---|---|
| require 未声明 Capability | 立即返回 UNDECLARED_CAPABILITY_REQUIRE |
| register 未声明 Capability | 立即返回 UNDECLARED_CAPABILITY_PROVIDE |
| activate 后缺少 declared provide | Assertion Failed |
| activate 中途 throw | 暂存 Registry Record 全部丢弃 |
| activate 成功 | Capability 与 Contribution 一次性提交并带正确 owner |
| Consumer activate 时 Provider 仅有 staged Capability | `require()` 不可见该值；只有 Provider commit 后才可解析 |

## 18.3 Contribution

| 场景 | 预期 |
|---|---|
| order 相同 | 按 ownerPluginId、contributionId 稳定排序 |
| Slot 不存在 | Contribution 保持未使用，不形成 Dependency |
| Route ID / Navigation ID 冲突 | Runtime 全局校验返回可归因的 ID collision |
| Extension ID 冲突 | 仅在同一 Slot 内报 ID collision |
| Route path 重复 | Registry 不报 ID collision；交由 Router Contract 校验和匹配 |
| Route 引用未知 surfaceId | Restricted Manifest Invalid，代码不执行 |
| Extension 引用未知 surfaceId | Restricted Manifest Invalid，代码不执行 |
| Navigation 引用未知 routeId | Restricted Manifest Invalid，代码不执行 |
| Navigation 跨 Plugin 引用 ACTIVE routeId | 引用有效，不建立 Capability Dependency Edge |
| Navigation 跨 Plugin 引用 ACTIVE parentId | 引用有效，不建立 Capability Dependency Edge |
| 同一 Manifest 任一声明冲突 | Surface Definition、全部 Contribution 与 ACTIVE commit 一起丢弃，Plugin SKIPPED |
| Restricted 通过 RPC 注册 UI | UNKNOWN_ACTION，Registry 不变 |
| 同一 Surface 被 Route 与 Extension 引用 | 两个 Contribution 都有效；实际挂载时创建独立实例 |
| Restricted ACTIVE、Surface 未访问 | Contribution 可见，`entry` 未加载，Surface 投影为 UNMOUNTED |

## 18.4 Bridge

| 场景 | 预期 |
|---|---|
| Handshake protocol 不兼容 | BRIDGE_PROTOCOL_MISMATCH，不创建 BridgeSession |
| Handshake nonce 无效或复用 | BRIDGE_NONCE_INVALID，不创建 BridgeSession |
| Bridge Bootstrap Descriptor 携带 Identity / Permission / Capability / Token | Descriptor Schema 拒绝；这些事实仅由 Host 绑定 |
| Request 伪造 pluginId / nonce / protocolVersion | 字段不属于 Envelope，消息 INVALID_REQUEST；不改变 Session Identity |
| Capability 未列入 requires | UNDECLARED_CAPABILITY_REQUIRE |
| Restricted requires Direct-only Capability | Manifest 阶段 `CAPABILITY_NOT_BRIDGE_EXPOSED`，`validationStage = manifest`，Plugin Code 不执行 |
| Unknown Action | UNKNOWN_ACTION |
| Invalid payload | INVALID_REQUEST |
| Host 返回不合 Schema 结果 | INVALID_RESULT 并记录 Host-side error |
| 缺少 Granted Permission | PERMISSION_DENIED |
| 重复 requestId | DUPLICATE_REQUEST |
| 超大消息 | MESSAGE_TOO_LARGE |
| 超过并发或频率 | CONCURRENCY_LIMITED / RATE_LIMITED |
| 超时 | TIMEOUT，并触发 AbortSignal |
| Subscription Action | 原子返回 Host 生成的 subscriptionId 与初始 snapshot |
| Subscription Event 不合 Schema | 不向 Plugin 发送，释放 Subscription 并记录 INVALID_EVENT |
| 重复或未知 unsubscribe | 幂等成功，不影响其他 Session 的 Subscription |
| unsubscribe 后再 unmount | disposer 总计只调用一次，后续 emit 被丢弃 |
| Surface unmount | Pending Request 中止，全部 Subscription disposer 被调用，Session DISPOSED |
| Surface 销毁后请求 | BRIDGE_SESSION_INACTIVE |
| 持续严重协议违规 | 当前 BridgeSession DISPOSED、Surface Instance FAILED；Plugin 保持 ACTIVE |

## 18.5 Wujie 与安全边界

这些场景必须在真实浏览器中验证：

| 场景 | 预期 |
|---|---|
| Runtime Ready、尚未访问 Surface | 不调用 startApp，不创建 Wujie Instance 或 MessagePort |
| 首次访问合法 Restricted Surface | 创建 MOUNTING 实例；Wujie 与 Handshake 成功后进入 MOUNTED |
| Host Object 注入检查 | props 不包含 Store、DOM、Token、Raw Client |
| Wujie Bootstrap throw | 当前 Surface Instance FAILED，Plugin 保持 ACTIVE，Runtime 继续 Ready |
| 同一 Surface 同时挂载两次 | 使用不同 surfaceInstanceId、Wujie name、MessagePort 与 BridgeSession |
| 同一 Surface 挂载到 Route 与 Extension | 两个实例分别记录 `route:...` 与 `extension:...` 形式的 mountPointId |
| Surface unmount | BridgeSession、Subscription、MessagePort、Pending RPC、Listener 被清理 |
| Plugin 访问 window.parent | 测试明确暴露同源可访问事实，不产生错误安全断言 |
| Plugin 绕过 Bridge 请求 API | Backend Authorization 仍拒绝无权请求 |
| 安装后未 Reload | 当前 Runtime Plugin Set 不变化 |
| Reload 后 | 根据新 Installation Store 重建 Runtime |

测试的最高 seam 是：

```text
PluginDefinition / Restricted Manifest
                 +
Installed Config / Bridge Contract
                 ↓
          Plugin Runtime
                 ↕
            Test Plugin
                 ↓
Registry / UI / RPC / Snapshot / Audit
```

Resolver 使用纯输入输出测试；PluginBridge 通过同一个 Dispatcher Interface 测试；Wujie 隔离结论必须使用 Browser Integration Test，不以 Mock Context 代替。

# 20. 重新引入抽象的触发条件

| 抽象 | 只有出现以下真实需求时重新引入 |
|---|---|
| RuntimeLoader / Generic PluginAdapter | 出现第二种真实 External Runtime |
| PluginExecutionPolicy | 同一个 External Plugin 可以被选择为 Direct 或 Sandbox |
| Trusted External | 出现 External Artifact + Direct Host Realm 的正式需求 |
| External ESM / Module Federation | Trusted External 需要远程 Direct 加载或 Shared Dependency Negotiation |
| Native iframe | 产品开始执行 Hostile Third-party Code |
| Independent Origin | 需要真正的浏览器 Origin Security Boundary |
| Artifact Signature / Marketplace Trust | 开放第三方发布、分发和安装来源 |
| Generic Discovery | 来源扩展为 Marketplace、Remote Repository、Workspace 或 Cluster Scope |
| PermissionBroker | 多个独立 Transport 都需要共享同一套 Permission Enforcement |
| Plugin Runtime State Machine | 出现 Restart、Hot Unload、Provider Rebinding 或 Reconcile |

未来安全路径不是在同源 Wujie 上继续增加 Permission，而是：

```text
Hostile Third-party Code
          ↓
Independent Plugin Origin
          +
Production-ready Sandboxed iframe
```

# 21. 最终核心对象

V1 一级 Module / Interface 只有：

```text
PluginDefinition

RestrictedPluginManifest

DependencyResolver

CapabilityRegistry

BridgeCapabilityContract

ContributionRegistry

WujiePluginAdapter

PluginBridge
```

以及三类普通输入或 Runtime Fact：

```text
InstalledPluginConfig

SandboxSurfaceDefinition

BridgeBootstrapDescriptor

Plugin / Surface / Session Runtime Facts
```

Surface Instance 与 BridgeSession 是分别由 `WujiePluginAdapter`、`PluginBridge` 拥有的内部运行记录，不提升为新的 Kernel Module 或公共生命周期 Interface。

最终模型可以概括为：

> **Builtin 以静态 PluginDefinition 参与统一依赖解析并直接执行；External Plugin 以 Restricted Manifest 参与同一依赖模型，在 Bootstrap 中只提交 Surface Definition、Contribution 与 ACTIVE 事实，并在 Surface 被访问时通过 Wujie + Bridge 按需运行；Capability 负责插件间能力与 Session-scoped Subscription，Contribution 负责 UI 扩展，requires / provides 在 Bootstrap 阶段一次性解析，Core Builtin 失败 fail-fast，Non-core Builtin 与 Restricted Surface 失败 fail-soft，Plugin Set 变化统一通过 Reload 重建。**

这套 V1 保留了依赖确定性、版本兼容、声明一致性、稳定 UI 扩展、权限治理、失败边界和线上诊断，同时不为尚未存在的 Runtime、Trust 或 Security 变化提前建立框架。
