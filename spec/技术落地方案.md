# 前端插件系统设计（Reload 模型 V1）

## 1. 设计目标

第一版插件系统不追求完整的 Hot Plug 或动态依赖编排能力，而是优先解决几个最实际的问题：

1. Host 如何提供稳定扩展点，插件如何扩展 UI
2. 插件之间如何共享能力，又不直接依赖彼此内部实现
3. 如何避免人工维护插件加载顺序
4. 如何在 Capability 接口发生不兼容变化时 fail-fast
5. 如何保证 Manifest 声明与插件运行时行为一致
6. 如何保证 Extension 渲染顺序稳定
7. 如何提供最低成本但足够实用的运行时诊断能力

第一版采用一个重要约束：

> **Plugin Set 可以变化，但单次页面 Runtime 生命周期内保持不变。**

插件安装、升级、启用、禁用、卸载之后，通过 Reload 创建新的 Plugin Runtime。

```text
Plugin Configuration Change
          ↓
        Reload
          ↓
Rebuild Plugin Runtime
```

因此第一版不实现：

```text
Plugin Hot Unload

Plugin Hot Upgrade

Disposer Stack

deactivate()

PENDING / ACTIVE 状态机

Capability Watch

Capability Rebinding

Provider 动态切换

Consumer 自动重新激活

Runtime Dependency Reconciliation
```

---

# 2. 核心原则

第一版遵循以下原则：

```text
1. Kernel 尽可能薄

2. KS Console 本身也是 Plugin
   只是 Builtin Plugin

3. UI 通过 Extension Point 扩展

4. 插件间能力通过 Capability 共享

5. Plugin 不直接依赖另一个 Plugin 的内部实现

6. Capability 使用显式 Major Version

7. requires / provides 用于启动依赖声明

8. Manifest 与运行时注册行为必须一致

9. Module Loading 可以并行

10. Plugin Activation 默认串行

11. Extension 顺序由 metadata 决定
    不依赖 Plugin Activation Order

12. 单次 Runtime 内 Plugin Set immutable

13. Plugin Set 变化统一通过 Reload 生效

14. Kernel 提供最小但完整的 inspect 能力
```

```text
Browser
  │
  ▼

  │
  ├── Plugin Registry
  ├── Plugin Discovery
  ├── Dependency Resolver
  ├── Runtime Loader
  ├── Capability Registry
```

Kernel 负责的是：

```text
Plugin Discovery

Plugin Manifest

Dependency Resolution

Runtime Loading

Capability Registration
```

```text
Console Layout
```

# 4. KS Console 本身也是 Plugin

不再把：

```text
Host = KS Console
```

而是：

```text
Host = Plugin Kernel
```

KS Console UI 本身由一组 Builtin Plugin 构成：

```text
console-shell

cluster

workspace

users

settings
```

例如 `console-shell` 可以负责：

```text
Global Layout

Global Navigation

Page Container

Global Header

Global Extension Slots
```

最终关系：

```text
Plugin Kernel
      │
      ▼
Builtin Plugins
      │
      ▼
External Plugins
```

Kernel 是最小不可插件化部分。

# 5. Runtime Immutable 模型

一次页面加载产生一个固定的 Plugin Runtime。

```text
Page Load
   ↓
Discover Plugins
   ↓
Resolve Dependencies
   ↓
Load Plugins
   ↓
Activate Plugins
   ↓
Runtime Ready
```

例如本次 Runtime：

```text
console-shell

cluster

workspace

kubeeye
```

那么直到页面 Reload 之前：

```text
Plugin Set = Immutable
```

运行期间不会因为后台安装了新的插件而动态修改当前 Runtime。

例如：

```text
Runtime Ready
     │
     │ 后台安装 observability
     ▼
Plugin Configuration Changed
     │
     ▼
Reload Required
     │
     ▼
Page Reload
     │
     ▼
重新 Discovery
     │
     ▼
新 Runtime
```

这样不需要维护：

```text
Runtime A
   ↓
如何增量变成
   ↓
Runtime B
```

而只是：

```text
Runtime A
   ↓ reload
Runtime B
```

# 6. Plugin 生命周期

第一版 Plugin 接口只有：

```ts
export interface Plugin {
  activate(
    context: PluginContext,
  ): void | Promise<void>;
}
```

不存在：

```ts
deactivate()
```

也不存在：

```text
PluginScope

Disposer Stack

Runtime Reconcile
```

因为：

```text
Disable

Uninstall

Upgrade
```

都会通过：

```text
Reload
```

重建整个浏览器 Runtime。

# 7. Plugin Manifest

第一版 Manifest 负责声明：

```text
Plugin Identity

Runtime Entry

requires

provides
```

例如：

```json
{
  "name": "kubeeye",
  "version": "1.0.0",

  "runtime": {
    "type": "module-federation",
    "entry": "/plugins/kubeeye/mf-manifest.json"
  },

  "requires": [
    "kubesphere.cluster@2"
  ],

  "provides": [
    "kubesphere.kubeeye@1"
  ]
}
```

其中：

```text
requires
```

代表：

> Plugin activate 前必须已经存在的 Capability。

```text
provides
```

代表：

> Plugin activate 完成后承诺提供的 Capability。

---

# 8. Capability

Capability 解决：

> Plugin 如何使用其他 Plugin 提供的能力，而不依赖具体实现。

不要：

```ts
import {
  clusterStore
} from "@plugins/cluster";
```

也不要：

```ts
ctx.plugins
  .get("cluster")
  .internalStore;
```

而应该：

```ts
const cluster =
  ctx.capabilities.require(
    "kubesphere.cluster@2",
  );
```

关系从：

```text
KubeEye
   ↓
Cluster Plugin
```

变成：

```text
KubeEye
   ↓
Cluster Capability Contract
   ↑
Cluster Plugin
```

---

# 9. Capability 必须带 Major Version

Capability ID 不使用无版本字符串：

```text
kubesphere.cluster
```

而使用：

```text
kubesphere.cluster@1

kubesphere.cluster@2
```

版本号只表达：

> Capability Contract 的 Major Compatibility。

例如：

```ts
interface ClusterCapabilityV1 {
  listClusters(): Cluster[];
}
```

如果未来变成不兼容接口：

```ts
interface ClusterCapabilityV2 {
  listClusters(
    options: ListOptions
  ): Promise<Cluster[]>;
}
```

则必须发布：

```text
kubesphere.cluster@2
```

而不是继续覆盖：

```text
kubesphere.cluster@1
```

---

## 9.1 为什么只用 Major Version

第一版不实现：

```text
^2.3.0

>=2 <3

SemVer Solver

Version Negotiation
```

只使用：

```text
capability-name@major
```

例如：

```json
{
  "requires": [
    "kubesphere.cluster@2"
  ]
}
```

如果 Runtime 只有：

```text
kubesphere.cluster@1
```

Resolver 直接：

```text
Missing capability:

kubesphere.cluster@2
```

这样已经可以在 Bootstrap 阶段 fail-fast。

---

# 10. Capability Contract

Capability 应该是稳定的公开接口。

例如：

```ts
export interface ClusterCapabilityV2 {
  listClusters(): Promise<Cluster[]>;

  getCurrentCluster():
    Cluster | undefined;
}
```

Provider：

```ts
ctx.capabilities.register<
  ClusterCapabilityV2
>(
  "kubesphere.cluster@2",
  {
    listClusters,
    getCurrentCluster,
  },
);
```

Consumer：

```ts
const cluster =
  ctx.capabilities.require<
    ClusterCapabilityV2
  >(
    "kubesphere.cluster@2",
  );
```

插件依赖的是：

```text
Capability Contract
```

而不是：

```text
Provider Plugin Implementation
```

---

# 11. Capability Registry

第一版 API 可以保持非常简单：

```ts
export interface CapabilityRegistry {
  register<T>(
    name: string,
    value: T,
  ): void;

  get<T>(
    name: string,
  ): T | undefined;

  require<T>(
    name: string,
  ): T;
}
```

内部除了 Capability Value，还应记录 Provider Ownership：

```ts
interface CapabilityRecord {
  name: string;

  providerPluginId: string;

  value: unknown;
}
```

因此 Registry 实际可以回答：

```text
Capability 是什么？

当前有没有？

是谁提供的？
```

---

# 12. Manifest 是 Dependency Contract

Dependency Resolver 的拓扑排序由 Manifest 驱动。

因此必须保证：

> Manifest 中声明的 requires / provides 和 Plugin 在 activate() 中的实际行为一致。

例如下面是不允许的：

```json
{
  "provides": [
    "kubesphere.cluster@2"
  ]
}
```

但：

```ts
async activate(ctx) {
  // 忘记 register cluster@2
}
```

否则 Resolver 会认为 Dependency 已满足，但运行时实际不存在。

---

# 13. Plugin Definition 尽量成为单一事实来源

避免手工维护：

```text
plugin.ts
```

和：

```text
plugin-manifest.json
```

两套独立信息。

推荐：

```ts
export default definePlugin({
  name: "cluster",

  version: "1.0.0",

  requires: [],

  provides: [
    "kubesphere.cluster@2",
  ],

  async activate(ctx) {
    ctx.capabilities.register(
      "kubesphere.cluster@2",
      clusterCapability,
    );
  },
});
```

构建阶段：

```text
plugin.ts
   │
   ▼
Plugin Build
   │
   ├── Plugin Runtime Bundle
   │
   └── plugin-manifest.json
```

Manifest 尽可能由 Plugin Definition 自动生成。

这样可以减少：

```text
Manifest 和源码 metadata 漂移
```

---

# 14. Runtime 一致性校验

即便 Manifest 从 Plugin Definition 生成，Kernel 仍应做 Runtime Assertion。

## provides 校验

Plugin：

```json
{
  "provides": [
    "kubesphere.cluster@2"
  ]
}
```

activate 完成后，Kernel 检查：

```text
Capability Registry
```

是否真的存在：

```text
kubesphere.cluster@2
```

如果没有：

```text
Plugin "cluster" declared capability
"kubesphere.cluster@2"
but did not register it.
```

Runtime 不进入 Ready。

---

## 未声明 provide

如果 Plugin：

```ts
ctx.capabilities.register(
  "kubesphere.foo@1",
  foo,
);
```

但 Manifest 没有：

```text
kubesphere.foo@1
```

则直接报错：

```text
Plugin "cluster" registered undeclared capability:

kubesphere.foo@1
```

第一版建议直接禁止这种行为。

---

## 未声明 require

如果：

```ts
ctx.capabilities.require(
  "kubesphere.metrics@1",
);
```

但 Manifest 没有声明：

```json
{
  "requires": [
    "kubesphere.metrics@1"
  ]
}
```

则报：

```text
Plugin "kubeeye" required undeclared capability:

kubesphere.metrics@1
```

这样：

```text
Manifest
```

才真正是可用于 Dependency Resolve 的可信契约。

---

# 15. PluginContext

第一版 PluginContext 可以保持很小：

```ts
export interface PluginContext {
  capabilities: CapabilityRegistry;

  extensions: ExtensionRegistry;

  routes: RouteRegistry;

  navigation: NavigationRegistry;

  events: EventBus;
}
```

Kernel 创建 Context 时绑定当前：

```text
pluginId
```

因此 Plugin 调用：

```ts
ctx.capabilities.register(...)
```

内部实际上知道：

```text
providerPluginId = currentPluginId
```

Extension：

```ts
ctx.extensions.register(...)
```

内部同样记录：

```text
contributorPluginId
```

---

# 16. requires / provides

Capability Registry 本身不能解决：

```text
Provider 和 Consumer
谁先 activate
```

所以 Manifest 需要：

```text
requires

provides
```

Provider：

```json
{
  "name": "cluster",

  "provides": [
    "kubesphere.cluster@2"
  ]
}
```

Consumer：

```json
{
  "name": "kubeeye",

  "requires": [
    "kubesphere.cluster@2"
  ]
}
```

Resolver 建立关系：

```text
cluster
   │
   │ provides
   ▼
kubesphere.cluster@2
   ▲
   │ requires
kubeeye
```

因此：

```text
cluster
   ↓
kubeeye
```

---

# 17. Dependency Resolver

第一版 Dependency Resolver 只在 Runtime Bootstrap 阶段运行。

流程：

```text
Plugin Discovery
       ↓
读取所有 Manifest
       ↓
Collect provides
       ↓
Resolve requires
       ↓
Build Dependency DAG
       ↓
Detect Missing Capability
       ↓
Detect Circular Dependency
       ↓
Topological Sort
       ↓
Activation Order
```

它不负责：

```text
动态 reconcile

provider watch

pending plugin

runtime dependency update

provider replacement
```

---

# 18. Missing Capability

如果：

```text
kubeeye requires:

kubesphere.cluster@2
```

当前 Plugin Set 中不存在任何：

```text
provides:

kubesphere.cluster@2
```

则在加载插件代码之前即可报错：

```text
Cannot activate plugin "kubeeye".

Missing capability:

kubesphere.cluster@2
```

不进入：

```text
PENDING
```

不等待未来 Provider。

---

# 19. 循环依赖

例如：

```text
Plugin A
requires x@1
provides y@1

Plugin B
requires y@1
provides x@1
```

形成：

```text
A → B
↑   ↓
└───┘
```

Resolver 直接报错：

```text
Circular capability dependency:

plugin-a
  → plugin-b
  → plugin-a
```

不猜测启动顺序。

---

# 20. Module Loading 与 Plugin Activation 分离

这一点需要明确区分：

```text
Module Loading
```

和：

```text
Plugin Activation
```

Module Loading 可以：

```text
并行
```

Plugin Activation 第一版默认：

```text
按照 Dependency Resolver 得到的顺序串行
```

---

# 21. Module Loading 可以并行

例如：

```text
console-shell

cluster

workspace

kubeeye
```

这些 Plugin Module 可以提前：

```ts
await Promise.all([
  load(consoleShell),
  load(cluster),
  load(workspace),
  load(kubeeye),
]);
```

因为：

```text
加载 JS Module
```

本身不应该产生业务级注册副作用。

Runtime Loader 的职责只是：

```text
URL / Manifest
      ↓
Plugin Module
```

---

# 22. Plugin Activation 默认串行

不采用：

```ts
await Promise.all([
  activate(cluster),
  activate(workspace),
]);
```

即使两个 Plugin 在 Dependency DAG 中处于同一层。

原因是：

> 第一版没有 disposer、deactivate 和 rollback state machine。

如果并行 activate：

```text
cluster activate
      ↓
     fail

workspace activate
      ↓
仍然在运行
```

`Promise.all()` reject 并不能停止另一个异步任务。

这会产生不清晰的部分失败状态。

因此第一版明确：

```text
Module Load
    → 可以并行

Plugin Activate
    → 串行
```

例如：

```text
load all modules
      ↓
activate console-shell
      ↓
activate cluster
      ↓
activate workspace
      ↓
activate kubeeye
      ↓
Runtime Ready
```

---

# 23. Activation 失败语义

如果：

```text
Plugin A
  ↓ success

Plugin B
  ↓ success

Plugin C
  ↓ failure

Plugin D
  ↓ not started
```

则：

```text
立即停止后续 Plugin Activation
```

Runtime 不进入：

```text
Ready
```

Kernel 应报告：

```text
Activation failed:

plugin-c
```

以及：

```text
Already activated:

plugin-a
plugin-b

Not activated:

plugin-d
```

第一版不尝试：

```text
自动 deactivate A/B

自动 rollback 整个 Runtime

自动 retry
```

因为当前 Runtime 已经被认为初始化失败。

最安全的恢复路径仍然是：

```text
修复问题
   ↓
Reload
```

---

# 24. Extension Point

Extension Point 用于解决：

> 一个 Plugin 如何扩展另一个 Plugin 的 UI。

例如 Workload Plugin 提供：

```text
workload.detail.tabs
```

页面中：

```tsx
<ExtensionSlot
  name="workload.detail.tabs"
/>
```

KubeEye：

```ts
ctx.extensions.register(
  "workload.detail.tabs",
  {
    id: "kubeeye",
    order: 200,
    component: KubeEyeTab,
  },
);
```

---

# 25. Extension 不产生 Dependency

KubeEye：

```text
contributes
    ↓
workload.detail.tabs
```

不应该意味着：

```text
KubeEye requires Workload Plugin
```

Extension Registry 可以先保存：

```text
workload.detail.tabs
    └── kubeeye
```

如果本次 Runtime 没有任何 Plugin 消费：

```text
workload.detail.tabs
```

则该 contribution：

```text
保持未使用
```

即可。

因此：

```text
Extension Contribution
```

不会参与：

```text
Dependency DAG
```

只有：

```text
Capability requires
```

才会产生 Activation Dependency。

---

# 26. Extension 顺序必须显式声明

Extension Registry 不能使用：

```text
Plugin Activation Order
```

作为 UI 顺序。

因为：

```text
Extension 不产生 Dependency
```

而插件 Activation Order 可能由于其他 Capability Dependency 改变。

因此 Extension Metadata 至少包含：

```ts
export interface Extension {
  id: string;

  order?: number;
}
```

例如：

```ts
ctx.extensions.register(
  "workload.detail.tabs",
  {
    id: "kubeeye",
    order: 200,
    component: KubeEyeTab,
  },
);
```

---

# 27. Extension 排序规则

ExtensionSlot 获取到多个 Contribution 时：

```text
首先按 order ASC

order 相同时
按 contributorPluginId ASC

仍相同时
按 extensionId ASC
```

例如：

```text
100 overview

200 kubeeye

200 monitoring

300 events
```

这样 Extension 顺序是：

```text
Deterministic
```

而不是依赖：

```text
哪个 Plugin 先 activate
```

原则：

> **Extension 的视觉顺序由 Extension Metadata 决定，不能由 Runtime Activation Order 隐式决定。**

---

# 28. Extension Registry

可以定义：

```ts
interface ExtensionRecord<T = unknown> {
  slot: string;

  id: string;

  order: number;

  contributorPluginId: string;

  value: T;
}
```

API：

```ts
interface ExtensionRegistry {
  register<T>(
    slot: string,
    extension: {
      id: string;
      order?: number;
      value: T;
    },
  ): void;

  get<T>(
    slot: string,
  ): ExtensionRecord<T>[];
}
```

Registry 内部统一补：

```text
pluginId

default order
```

并执行稳定排序。

---

# 29. Registry Ownership

虽然第一版不支持动态卸载，但所有 Registry 都应该记录 Ownership。

例如 Capability：

```text
kubesphere.cluster@2
  providerPluginId: cluster
```

Extension：

```text
workload.detail.tabs
  id: kubeeye
  contributorPluginId: kubeeye
```

Route：

```text
/workloads
  ownerPluginId: workload
```

Navigation：

```text
cluster.workloads
  ownerPluginId: workload
```

这不会增加运行时复杂度，却对：

```text
debug

冲突诊断

日志

错误报告

未来 Hot Unload
```

非常有价值。

# 30. Kernel Inspector

第一版提供：

```ts
kernel.inspect()
```

它只负责：

> 将当前 Runtime Registry 状态以只读数据结构暴露出来。

不做：

```text
复杂 Runtime UI

Fiber Inspector

Dependency Visualization Platform

动态调试控制器
```

只需要 dump 当前事实。

# 32. Inspector 不引入 Runtime 状态机

Inspector 只是：

```text
Read-only Snapshot
```

它不会维护：

```text
PENDING

ACTIVE

DEACTIVATING

RECONCILING
```

可以理解为：

```text
Registry Dump
```

而不是：

```text
Runtime Orchestrator
```

因此成本很低。

# 33. Runtime Loader

Runtime Loader 只负责：

```text
Plugin Manifest
      ↓
加载代码
      ↓
Plugin Module
```

统一接口：

```ts
interface RuntimeLoader {
  load(
    manifest: PluginManifest,
  ): Promise<Plugin>;
}
```

例如：

```ts
const plugin =
  await runtimeLoader.load(manifest);
```

支持的 Runtime 可以包括：

```text
Builtin

ESM

Module Federation
```

Runtime Loader 不负责：

```text
Dependency Resolve

Capability Negotiation

Extension Ordering

Plugin Lifecycle
```

---

# 34. Module Federation 的定位

Module Federation 只负责：

> Plugin JavaScript 如何被动态加载，以及部分 Shared Dependency 如何共享。

关系：

```text
Plugin Manifest
      ↓
Runtime Loader
      ↓
Module Federation
      ↓
Plugin Module
```

而不是：

```text
Module Federation
      =
Plugin System
```

插件协议仍然由：

```text
Manifest

PluginContext

Capability

Extension
```

定义。

# 45. 设计结论

第一版不把浏览器 Runtime 设计成一个持续变化、需要不断 reconcile 的插件操作系统。

而是：

> **一次页面加载构建一个稳定、可验证、可诊断的 Plugin Runtime。**

Plugin Set 变化：

```text
Runtime A
   ↓
Reload
   ↓
Runtime B
```

UI 扩展通过：

```text
Extension Point
```

完成。

插件间能力共享通过：

```text
Capability Contract
```

完成。

Capability 使用：

```text
name@major
```

表达粗粒度 ABI 兼容性。

插件依赖通过：

```text
requires / provides
```

在 Bootstrap 阶段完成一次性解析。

Module Loading：

```text
允许并行
```

Plugin Activation：

```text
默认串行
```

避免在没有 disposer / rollback 机制的情况下制造部分并发失败状态。

Extension 顺序：

```text
由 order + stable tie-breaker 决定
```

绝不依赖 Activation Order。

Manifest 与 Runtime：

```text
必须做双向一致性校验
```

避免 Resolver 基于错误声明构建依赖图。

Kernel 最后提供：

```text
kernel.inspect()
```

用于查看当前：

```text
Plugins

Capabilities

Extensions

Routes

Dependencies
```

因此 V1 最终可以浓缩成：

> **Plugin Set 动态、Runtime 静态；Manifest 描述依赖，Capability 描述能力，Extension 描述 UI 扩展，Reload 重建 Runtime，Inspector 提供事实诊断。**

这套模型保持了足够小的实现复杂度，同时补齐了版本兼容、声明一致性、失败确定性、扩展排序和线上诊断这些真正会影响工程质量的基础能力。
