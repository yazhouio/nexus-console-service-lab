# 前端插件系统设计（Reload + Trust Model V1）

## 1. 设计目标

第一版插件系统不追求完整的 Hot Plug 或动态依赖编排能力，而是优先解决几个最实际的问题：

1. Host 如何提供稳定扩展点，插件如何扩展 UI
2. 插件之间如何共享能力，又不直接依赖彼此内部实现
3. 如何避免人工维护插件加载顺序
4. 如何在 Capability 接口发生不兼容变化时 fail-fast
5. 如何保证 Manifest 声明与插件运行时行为一致
6. 如何保证 Extension 渲染顺序稳定
7. 如何提供最低成本但足够实用的运行时诊断能力
8. 如何根据 Plugin Trust Level 选择不同的执行方式
9. 如何在不支持独立 Origin 的前提下运行 Restricted Plugin
10. 如何明确 Wujie 的隔离能力与安全边界，避免错误安全承诺

第一版采用一个重要约束：

> **Plugin Set 可以变化，但单次页面 Runtime 生命周期内保持不变。**

插件安装、升级、启用、禁用、卸载之后，通过 Reload 创建新的 Plugin Runtime。

```text
Plugin Configuration Change
          ↓
        Reload
          ↓
Rebuild Plugin Runtime
```

因此第一版不实现：

```text
Plugin Hot Unload

Plugin Hot Upgrade

Disposer Stack

deactivate()

PENDING / ACTIVE 状态机

Capability Watch

Capability Rebinding

Provider 动态切换

Consumer 自动重新激活

Runtime Dependency Reconciliation
```

---

# 2. 核心原则

第一版遵循以下原则：

```text
1. Kernel 尽可能薄

2. KS Console 本身也是 Plugin
   只是 Builtin Plugin

3. UI 通过 Extension Point 扩展

4. 插件间能力通过 Capability 共享

5. Plugin 不直接依赖另一个 Plugin 的内部实现

6. Capability 使用显式 Major Version

7. requires / provides 用于启动依赖声明

8. Direct Plugin 的 Manifest 与运行时注册行为必须一致
   Restricted UI Contribution 由 Host 直接从 Manifest 注册

9. Module Loading 可以并行

10. Plugin Activation 默认串行

11. Extension 顺序由 metadata 决定
    不依赖 Plugin Activation Order

12. 单次 Runtime 内 Plugin Set immutable

13. Plugin Set 变化统一通过 Reload 生效

14. Kernel 提供最小但完整的 inspect 能力

15. Trust Level、Execution Mode、Permission Grant 相互独立

16. Restricted Plugin 默认使用 Wujie

17. Wujie 是 Cooperative Isolation
    不是恶意代码 Security Sandbox

18. 原生 Sandboxed iframe 是可选增强
    V1 不要求独立 Plugin Origin

19. V1 只有 Builtin Plugin 可以成为 Runtime Critical
    Restricted Plugin 永远不是 Runtime Critical

20. Backend Authorization 仍是数据安全边界

21. Critical Plugin 的传递性 Plugin 依赖闭包
    只能包含 Critical Builtin Plugin
```

不再把：

```text
Host = KS Console
```

而是：

```text
Host = Plugin Kernel
```

KS Console UI 本身由一组 Builtin Plugin 构成：

```text
console-shell

cluster

workspace

users

settings
```

例如 `console-shell` 可以负责：

```text
Global Layout

Global Navigation

Page Container

Global Header

Global Extension Slots
```

最终关系：

```text
Plugin Kernel
      │
      ▼
Builtin Plugins
      │
      ▼
External Plugins
```

# 5. Runtime Immutable 模型

一次页面加载产生一个固定的 Plugin Runtime。

```text
Page Load
   ↓
Discover Plugins
   ↓
Resolve Dependencies
   ↓
Load Plugins
   ↓
Activate Plugins
   ↓
Runtime Ready
```

例如本次 Runtime：

```text
console-shell

cluster

workspace

kubeeye
```

那么直到页面 Reload 之前：

```text
Plugin Set = Immutable
```

运行期间不会因为后台安装了新的插件而动态修改当前 Runtime。

例如：

```text
Runtime Ready
     │
     │ 后台安装 observability
     ▼
Plugin Configuration Changed
     │
     ▼
Reload Required
     │
     ▼
Page Reload
     │
     ▼
重新 Discovery
     │
     ▼
新 Runtime
```

这样不需要维护：

```text
Runtime A
   ↓
如何增量变成
   ↓
Runtime B
```

而只是：

```text
Runtime A
   ↓ reload
Runtime B
```

# 6. Plugin 生命周期

第一版 Direct Plugin 接口只有：

```ts
export interface Plugin {
  activate(
    context: PluginContext,
  ): void | Promise<void>;
}
```

Kernel 实际激活的是：

```text
PluginAdapter
```

其中：

```text
DirectPluginAdapter
  -> plugin.activate(context)

WujiePluginAdapter
  -> start Wujie App
  -> establish Bridge

IframePluginAdapter（optional）
  -> create sandboxed iframe
  -> establish Bridge
```

不存在：

```ts
deactivate()
```

也不存在：

```text
PluginScope

Disposer Stack

Runtime Reconcile
```

因为：

```text
Disable

Uninstall

Upgrade
```

都会通过：

```text
Reload
```

重建整个浏览器 Runtime。

这里不增加 Plugin 级 Hot Lifecycle。

Wujie / iframe 的 Route 或 Extension Surface 挂载与卸载由对应 Adapter 管理，不等价于动态改变 Plugin Set。

# 7. Plugin Manifest

第一版 Manifest 负责声明：

```text
Plugin Identity

Runtime Entry

Host API Compatibility

requires

provides

requested permissions

contributions
```

例如 Direct Plugin：

```json
{
  "name": "monitoring",
  "version": "1.0.0",

  "runtime": {
    "type": "module-federation",
    "entry": "/plugins/monitoring/mf-manifest.json"
  },

  "hostApi": "kubesphere.console@1",

  "requires": [
    "kubesphere.cluster@2"
  ],

  "provides": [
    "kubesphere.metrics@1"
  ],

  "permissions": [
    "cluster.read"
  ]
}
```

其中：

```text
requires
```

代表：

> Plugin activate 前必须已经存在的 Capability。

`requires` 只声明：

```text
capability-name@major
```

Manifest 不声明该 Capability 内有哪些 Action，也不声明 Action 的 Schema 或 Permission 映射。

```text
provides
```

代表：

> Plugin activate 完成后承诺提供的 Capability。

Manifest 中的：

```text
runtime.type

permissions
```

分别表示：

```text
requested execution mode

requested permissions
```

它们不是最终授权结果。

真正生效的：

```text
Trust Level

Execution Mode

Granted Permissions
```

由平台保存的 Plugin Installation Policy 决定。

Plugin 不能通过 Manifest 把自己声明为 Trusted，也不能自行扩大权限。

其中 `permissions` 只是 Plugin 请求的 Permission 集合。

某个 Action 实际需要哪些 Permission，由 Host Capability Contract 定义，Manifest 不是该映射的事实来源。

对于 Restricted Plugin，以下 UI Contribution 必须完整、静态地写入 Manifest：

```text
Route

Navigation

Sandbox Surface
```

Host 在执行 Plugin Code 前校验并注册这些 Contribution；Restricted Plugin 不能在运行时通过 Bridge 新增、删除或改写 Extension。

# 8. Capability

Capability 解决：

> Plugin 如何使用其他 Plugin 提供的能力，而不依赖具体实现。

不要：

```ts
import {
  clusterStore
} from "@plugins/cluster";
```

也不要：

```ts
ctx.plugins
  .get("cluster")
  .internalStore;
```

而应该：

```ts
const cluster =
  ctx.capabilities.require(
    "kubesphere.cluster@2",
  );
```

关系从：

```text
KubeEye
   ↓
Cluster Plugin
```

变成：

```text
KubeEye
   ↓
Cluster Capability Contract
   ↑
Cluster Plugin
```

---

# 9. Capability 必须带 Major Version

Capability ID 不使用无版本字符串：

```text
kubesphere.cluster
```

而使用：

```text
kubesphere.cluster@1

kubesphere.cluster@2
```

版本号只表达：

> Capability Contract 的 Major Compatibility。

例如：

```ts
interface ClusterCapabilityV1 {
  listClusters(): Cluster[];
}
```

如果未来变成不兼容接口：

```ts
interface ClusterCapabilityV2 {
  listClusters(
    options: ListOptions
  ): Promise<Cluster[]>;
}
```

则必须发布：

```text
kubesphere.cluster@2
```

而不是继续覆盖：

```text
kubesphere.cluster@1
```

---

## 9.1 为什么只用 Major Version

第一版不实现：

```text
^2.3.0

>=2 <3

SemVer Solver

Version Negotiation
```

只使用：

```text
capability-name@major
```

例如：

```json
{
  "requires": [
    "kubesphere.cluster@2"
  ]
}
```

如果 Runtime 只有：

```text
kubesphere.cluster@1
```

Resolver 直接：

```text
Missing capability:

kubesphere.cluster@2
```

这样已经可以在 Bootstrap 阶段 fail-fast。

# 10. Capability Contract

Capability 应该是由 Host 定义并发布的稳定公开接口。

例如：

```ts
export interface ClusterCapabilityV2 {
  listClusters(): Promise<Cluster[]>;

  getCurrentCluster():
    Cluster | undefined;
}
```

Provider：

```ts
ctx.capabilities.register<
  ClusterCapabilityV2
>(
  "kubesphere.cluster@2",
  {
    listClusters,
    getCurrentCluster,
  },
);
```

Consumer：

```ts
const cluster =
  ctx.capabilities.require<
    ClusterCapabilityV2
  >(
    "kubesphere.cluster@2",
  );
```

插件依赖的是：

```text
Capability Contract
```

而不是：

```text
Provider Plugin Implementation
```

同一个 Capability Contract 还必须定义 Bridge Transport 使用的：

```text
Capability ID + Major Version

Action Name

Request Schema

Result Schema

Required Permissions
```

概念上：

```ts
interface HostCapabilityContract {
  id: `${string}@${number}`;

  actions: Record<string, {
    requestSchema: unknown;
    resultSchema: unknown;
    requiredPermissions: string[];
  }>;
}
```

因此 Action 到 Permission 的映射方向固定为：

```text
Host Capability Contract
          ↓
Action / Schema / Required Permissions
```

而不是：

```text
Plugin Manifest
          ↓
Action / Permission Definition
```

Direct Transport 的 TypeScript Interface 与 Bridge Transport 的 Action Contract 必须表达同一套 Host-owned 语义，不能各自演进。

---

# 11. Capability Registry

第一版 API 可以保持非常简单：

```ts
export interface CapabilityRegistry {
  register<T>(
    name: string,
    value: T,
  ): void;

  get<T>(
    name: string,
  ): T | undefined;

  require<T>(
    name: string,
  ): T;
}
```

内部除了 Capability Value，还应记录 Provider Ownership：

```ts
interface CapabilityRecord {
  name: string;

  providerPluginId: string;

  value: unknown;
}
```

因此 Registry 实际可以回答：

```text
Capability 是什么？

当前有没有？

是谁提供的？
```

# 12. Manifest 是 Dependency Contract

Dependency Resolver 的拓扑排序由 Manifest 驱动。

因此必须保证：

> Manifest 中声明的 requires / provides 和 Plugin 在 activate() 中的实际行为一致。

例如下面是不允许的：

```json
{
  "provides": [
    "kubesphere.cluster@2"
  ]
}
```

但：

```ts
async activate(ctx) {
  // 忘记 register cluster@2
}
```

否则 Resolver 会认为 Dependency 已满足，但运行时实际不存在。

V1 中 Restricted Plugin 不允许向 Global Capability Registry 提供 Capability。

因此它的 `provides` 必须为空；它只能通过 Bridge 消费 Manifest 中声明的 `requires`。

---

# 13. Plugin Definition 尽量成为单一事实来源

避免手工维护：

```text
plugin.ts
```

和：

```text
plugin-manifest.json
```

两套独立信息。

推荐：

```ts
export default definePlugin({
  name: "cluster",

  version: "1.0.0",

  requires: [],

  provides: [
    "kubesphere.cluster@2",
  ],

  async activate(ctx) {
    ctx.capabilities.register(
      "kubesphere.cluster@2",
      clusterCapability,
    );
  },
});
```

构建阶段：

```text
plugin.ts
   │
   ▼
Plugin Build
   │
   ├── Plugin Runtime Bundle
   │
   └── plugin-manifest.json
```

Manifest 尽可能由 Plugin Definition 自动生成。

这样可以减少：

```text
Manifest 和源码 metadata 漂移
```

对于 Wujie Plugin，同样应由 Plugin Build 生成 Manifest 与 Bridge Contract Metadata。

区别是 Host 不直接 import 它的 `PluginDefinition`。Host 先读取 Manifest，注册其中声明的 Route、Navigation 与 Sandbox Surface，再通过 Wujie Adapter 加载子应用。

Bridge 握手只校验 Plugin Identity、Protocol Version 与 Host-owned Capability Contract，不接收运行时 Extension 声明。

无论 Direct 还是 Wujie，Trust Level 与 Granted Permissions 都不从 Plugin Definition 生成，而由平台 Installation Policy 保存。

# 14. Runtime 一致性校验

即便 Manifest 从 Plugin Definition 生成，Kernel 仍应做 Runtime Assertion。

## provides 校验

Plugin：

```json
{
  "provides": [
    "kubesphere.cluster@2"
  ]
}
```

activate 完成后，Kernel 检查：

```text
Capability Registry
```

是否真的存在：

```text
kubesphere.cluster@2
```

如果没有：

```text
Plugin "cluster" declared capability
"kubesphere.cluster@2"
but did not register it.
```

如果这是 Critical Plugin，Runtime 不进入 Ready。

如果这是 Non-critical Plugin，则当前 Plugin 进入 FAILED，Runtime 可以继续进入 Ready。

---

## 未声明 provide

如果 Plugin：

```ts
ctx.capabilities.register(
  "kubesphere.foo@1",
  foo,
);
```

但 Manifest 没有：

```text
kubesphere.foo@1
```

则直接报错：

```text
Plugin "cluster" registered undeclared capability:

kubesphere.foo@1
```

第一版建议直接禁止这种行为。

---

## 未声明 require

如果：

```ts
ctx.capabilities.require(
  "kubesphere.metrics@1",
);
```

但 Manifest 没有声明：

```json
{
  "requires": [
    "kubesphere.metrics@1"
  ]
}
```

则报：

```text
Plugin "kubeeye" required undeclared capability:

kubesphere.metrics@1
```

这样：

```text
Manifest
```

才真正是可用于 Dependency Resolve 的可信契约。

Runtime Assertion 的失败范围统一由 Plugin Criticality 决定：

```text
Critical
  -> Runtime Bootstrap Failed

Non-critical / Restricted
  -> Plugin FAILED
  -> Runtime Continues
```

# 15. PluginContext

第一版 PluginContext 可以保持很小：

```ts
export interface PluginContext {
  capabilities: CapabilityRegistry;

  extensions: ExtensionRegistry;

  routes: RouteRegistry;

  navigation: NavigationRegistry;

  events: EventBus;
}
```

Kernel 创建 Context 时绑定当前：

```text
pluginId
```

因此 Plugin 调用：

```ts
ctx.capabilities.register(...)
```

内部实际上知道：

```text
providerPluginId = currentPluginId
```

Extension：

```ts
ctx.extensions.register(...)
```

内部同样记录：

```text
contributorPluginId
```

上述 `PluginContext` 是 Direct Transport。

适用于：

```text
Builtin Plugin

Trusted Plugin
```

Restricted Plugin 不直接获得这些 Host JavaScript Object。

它通过 Wujie 中的 Bridge / RPC SDK 使用相同的 Capability Contract：

```text
Plugin SDK Contract
├── Direct Transport
│   └── Builtin / Trusted
└── Bridge Transport
    └── Restricted / Wujie
```

跨 Bridge 只允许结构化、可序列化的数据。

禁止传递：

```text
Host Store

React Context

React Component

DOM Node

Function Reference

Access Token

Raw API Client
```

# 16. requires / provides

Capability Registry 本身不能解决：

```text
Provider 和 Consumer
谁先 activate
```

所以 Manifest 需要：

```text
requires

provides
```

Provider：

```json
{
  "name": "cluster",

  "provides": [
    "kubesphere.cluster@2"
  ]
}
```

Consumer：

```json
{
  "name": "kubeeye",

  "requires": [
    "kubesphere.cluster@2"
  ]
}
```

Resolver 建立关系：

```text
cluster
   │
   │ provides
   ▼
kubesphere.cluster@2
   ▲
   │ requires
kubeeye
```

因此：

```text
cluster
   ↓
kubeeye
```

# 17. Dependency Resolver

第一版 Dependency Resolver 只在 Runtime Bootstrap 阶段运行。

流程：

```text
Plugin Discovery
       ↓
读取所有 Manifest
       ↓
Collect provides
       ↓
Resolve requires
       ↓
Build Dependency DAG
       ↓
Detect Missing Capability
       ↓
Detect Circular Dependency
       ↓
Topological Sort
       ↓
Activation Order
```

## 17.1 Critical Plugin 依赖闭包

Critical Activation 阶段必须能够在任何 Non-critical Plugin 启动前独立完成。

V1 中 Critical Plugin 自身必须满足：

```text
trustLevel = builtin
```

因此，对于每个 Critical Plugin，Resolver 沿实际选中的 Capability Provider 继续展开后得到的传递性 Plugin 依赖闭包，必须全部满足：

```text
trustLevel = builtin

critical = true
```

Host 原生提供、无需 Plugin 激活的 Capability 是依赖图根节点，不属于 Plugin 依赖闭包，可直接使用。

以下关系全部非法：

```text
Critical Builtin -> Non-critical Builtin

Critical Builtin -> Trusted Plugin

Critical Builtin -> Restricted Plugin
```

如果 Critical Builtin 依赖某个 Non-critical Builtin，必须显式把 Provider 纳入 Critical 集合，或者重新设计依赖；Resolver 不做静默提升。

该约束在加载任何 Plugin Code 前校验。违反时直接判定 Runtime Bootstrap Failed，并输出完整依赖路径。

Dependency Resolver 不负责：

```text
动态 reconcile

provider watch

pending plugin

runtime dependency update

provider replacement
```

# 18. Missing Capability

如果：

```text
kubeeye requires:

kubesphere.cluster@2
```

当前 Plugin Set 中不存在任何：

```text
provides:

kubesphere.cluster@2
```

则在加载插件代码之前即可报错：

```text
Cannot activate plugin "kubeeye".

Missing capability:

kubesphere.cluster@2
```

不进入：

```text
PENDING
```

不等待未来 Provider。

# 19. 循环依赖

例如：

```text
Plugin A
requires x@1
provides y@1

Plugin B
requires y@1
provides x@1
```

形成：

```text
A → B
↑   ↓
└───┘
```

Resolver 直接报错：

```text
Circular capability dependency:

plugin-a
  → plugin-b
  → plugin-a
```

不猜测启动顺序。

# 20. Module Loading 与 Plugin Activation 分离

这一点需要明确区分：

```text
Module Loading
```

和：

```text
Plugin Activation
```

Direct Module Loading 可以：

```text
并行
```

PluginAdapter Activation 第一版默认：

```text
按照 Dependency Resolver 得到的顺序串行
```

---

# 21. Module Loading 可以并行

例如：

```text
console-shell

cluster

workspace
```

这些 Direct Plugin Module 可以提前：

```ts
await Promise.all([
  load(consoleShell),
  load(cluster),
  load(workspace),
]);
```

因为：

```text
加载 JS Module
```

本身不应该产生业务级注册副作用。

Wujie / iframe 只允许提前准备 Manifest 与 Adapter Metadata。

在 Effective Execution Policy 产生之前：

```text
不得 preload

不得 pre-execute

不得执行 Plugin Script
```

Runtime Loader 的职责只是：

```text
URL / Manifest
      ↓
Direct Plugin Module
```

---

# 22. Plugin Activation 默认串行

不采用：

```ts
await Promise.all([
  activate(cluster),
  activate(workspace),
]);
```

即使两个 Plugin 在 Dependency DAG 中处于同一层。

原因是：

> 第一版没有 disposer、deactivate 和 rollback state machine。

如果并行 activate：

```text
cluster activate
      ↓
     fail

workspace activate
      ↓
仍然在运行
```

`Promise.all()` reject 并不能停止另一个异步任务。

这会产生不清晰的部分失败状态。

因此第一版明确：

```text
Module Load
    → 可以并行

PluginAdapter Activate
    → 串行
```

例如：

```text
load all modules
      ↓
activate console-shell
      ↓
activate cluster
      ↓
activate workspace
      ↓
activate kubeeye Wujie adapter
      ↓
Runtime Ready
```

---

# 23. Activation 失败语义

如果 Plugin C 是 Critical Plugin：

```text
Plugin A
  ↓ success

Plugin B
  ↓ success

Plugin C
  ↓ failure

Plugin D
  ↓ not started
```

则：

```text
立即停止后续 Plugin Activation
```

Runtime 不进入：

```text
Ready
```

Kernel 应报告：

```text
Activation failed:

plugin-c
```

以及：

```text
Already activated:

plugin-a
plugin-b

Not activated:

plugin-d
```

第一版不尝试：

```text
自动 deactivate A/B

自动 rollback 整个 Runtime

自动 retry
```

因为当前 Runtime 已经被认为初始化失败。

最安全的恢复路径仍然是：

```text
修复问题
   ↓
Reload
```

如果 Plugin C 是 Non-critical / Restricted Plugin：

```text
Plugin A
  ↓ success

Plugin B
  ↓ success

Plugin C
  ↓ failure / mark FAILED

Plugin D
  ↓ continue activation

Runtime Ready
  └── Inspector reports Plugin C failure
```

Restricted Plugin 永远不能成为 Critical Plugin。

---

# 24. Extension Point

Extension Point 用于解决：

> 一个 Plugin 如何扩展另一个 Plugin 的 UI。

例如 Workload Plugin 提供：

```text
workload.detail.tabs
```

页面中：

```tsx
<ExtensionSlot
  name="workload.detail.tabs"
/>
```

Trusted Direct Monitoring Plugin：

```ts
ctx.extensions.register(
  "workload.detail.tabs",
  {
    id: "monitoring",
    order: 200,
    component: MonitoringTab,
  },
);
```

Restricted KubeEye Plugin 则不调用上述接口，而是在 Manifest 中声明：

```json
{
  "contributions": {
    "sandboxSurfaces": [
      {
        "slot": "workload.detail.tabs",
        "id": "kubeeye",
        "surfaceId": "workload-detail",
        "order": 200
      }
    ]
  }
}
```

该记录由 Host 注册，KubeEye Runtime 不通过 Bridge 再注册一次。

---

# 25. Extension 不产生 Dependency

KubeEye：

```text
contributes
    ↓
workload.detail.tabs
```

不应该意味着：

```text
KubeEye requires Workload Plugin
```

Extension Registry 可以先保存：

```text
workload.detail.tabs
    └── kubeeye
```

如果本次 Runtime 没有任何 Plugin 消费：

```text
workload.detail.tabs
```

则该 contribution：

```text
保持未使用
```

即可。

因此：

```text
Extension Contribution
```

不会参与：

```text
Dependency DAG
```

只有：

```text
Capability requires
```

才会产生 Activation Dependency。

---

# 26. Extension 顺序必须显式声明

Extension Registry 不能使用：

```text
Plugin Activation Order
```

作为 UI 顺序。

因为：

```text
Extension 不产生 Dependency
```

而插件 Activation Order 可能由于其他 Capability Dependency 改变。

因此 Extension Metadata 至少包含：

```ts
export interface Extension {
  id: string;

  order?: number;
}
```

例如：

```ts
ctx.extensions.register(
  "workload.detail.tabs",
  {
    id: "monitoring",
    order: 200,
    component: MonitoringTab,
  },
);
```

---

# 27. Extension 排序规则

ExtensionSlot 获取到多个 Contribution 时：

```text
首先按 order ASC

order 相同时
按 contributorPluginId ASC

仍相同时
按 extensionId ASC
```

例如：

```text
100 overview

200 kubeeye

200 monitoring

300 events
```

这样 Extension 顺序是：

```text
Deterministic
```

而不是依赖：

```text
哪个 Plugin 先 activate
```

原则：

> **Extension 的视觉顺序由 Extension Metadata 决定，不能由 Runtime Activation Order 隐式决定。**

# 28. Extension Registry

可以定义：

```ts
interface ExtensionRecord<T = unknown> {
  slot: string;

  id: string;

  order: number;

  contributorPluginId: string;

  value: T;
}
```

API：

```ts
interface ExtensionRegistry {
  register<T>(
    slot: string,
    extension: {
      id: string;
      order?: number;
      value: T;
    },
  ): void;

  get<T>(
    slot: string,
  ): ExtensionRecord<T>[];
}
```

该 `register` 是 Host 内部与 Direct Plugin Context 的接口，不暴露为 Restricted Plugin Bridge Action。

Restricted Plugin 的静态 Contribution 由 Host 的 Manifest Registrar 调用同一个 Registry seam，因此排序、Ownership 与诊断逻辑仍集中在一处。

Registry 内部统一补：

```text
pluginId

default order
```

并执行稳定排序。

虽然第一版不支持动态卸载，但所有 Registry 都应该记录 Ownership。

例如 Capability：

```text

  providerPluginId: cluster
```

Extension：

```text

  id: kubeeye
  contributorPluginId: kubeeye
```

Route：

```text

  ownerPluginId: workload
```

Navigation：

```text

  ownerPluginId: workload
```

这不会增加运行时复杂度，却对：

```text
debug

冲突诊断

日志

错误报告

未来 Hot Unload
```

非常有价值。

```text
fail-fast / fail-soft
```

# 33. Runtime Loader

Runtime Loader 只负责：

```text
Plugin Manifest
      ↓
加载代码
      ↓
Plugin Adapter
```

统一接口：

```ts
interface RuntimeLoader {
  supports(
    manifest: PluginManifest,
    policy: PluginExecutionPolicy,
  ): boolean;

  load(
    manifest: PluginManifest,
    policy: PluginExecutionPolicy,
  ): Promise<PluginAdapter>;
}
```

例如：

```ts
const adapter =
  await runtimeLoader.load(
    manifest,
    executionPolicy,
  );
```

支持的 Runtime 可以包括：

```text
Builtin

ESM

Module Federation

Wujie

Sandboxed iframe（optional）
```

Runtime Loader 不负责：

```text
Dependency Resolve

Capability Negotiation

Extension Ordering

Plugin Lifecycle

Trust Decision

Permission Grant
```

`PluginAdapter` 隐藏 Direct 与 Bridge Transport 的差异：

```ts
interface PluginAdapter {
  activate(
    host: PluginAdapterHost,
  ): void | Promise<void>;
}
```

```text
DirectPluginAdapter
  └── 调用 plugin.activate(context)

WujiePluginAdapter
  └── 启动 Wujie App + 建立 Bridge

IframePluginAdapter（optional）
  └── 启动 sandboxed iframe + 建立 Bridge
```

Trust Policy 必须先于 Loader Selection 执行。

Loader 不能信任 Plugin 自己选择的 Execution Mode。

# 34. Module Federation 的定位

Module Federation 只负责：

> Plugin JavaScript 如何被动态加载，以及部分 Shared Dependency 如何共享。

它属于 Direct Execution Mode，只允许 Builtin / Trusted Plugin 使用。

Restricted Plugin 不能因为 Artifact 恰好是 Module Federation 格式，就绕过 Trust Policy 进入 Host Realm。

关系：

```text
Plugin Manifest
      ↓
Runtime Loader
      ↓
Module Federation
      ↓
Plugin Module
```

而不是：

```text
Module Federation
      =
Plugin System
```

插件协议仍然由：

```text
Manifest

PluginContext

Capability

Extension
```

定义。

# 35. 信任边界与 Restricted Plugin

External Plugin 不能只按“如何加载”分类。

还必须明确：

```text
平台是否信任这段代码？

它以什么方式执行？

平台主动授予了哪些能力？

当前执行方式实际提供什么安全保证？
```

这四个问题不能混成一个 `runtime.type`。

---

## 35.1 Threat Model

V1 区分三类目标：

| 目标 | 含义 | Wujie 同源模式 |
|---|---|---|
| Runtime Isolation | 减少全局变量、样式、路由和生命周期的意外冲突 | 支持 |
| Capability Governance | 约束平台正式 SDK / Bridge 可以执行的操作 | 支持 |
| Hostile-code Containment | 插件主动绕过 SDK 时仍不能访问 Host 数据与完整性 | 不支持 |

因此本方案中的：

```text
Restricted Plugin
```

表示：

> **没有获得进入 Direct Host Realm 的权限，需要走受控加载与 Bridge 的 Plugin Governance Level。**

`restricted` 描述的是 Host Realm 准入限制，不是对代码是否恶意的判断。

它不表示：

> **Host 可以安全执行任意恶意 JavaScript。**

Wujie V1 假设 Plugin 会遵守平台协议，但可能存在：

```text
实现缺陷

全局变量污染

样式冲突

路由冲突

生命周期泄漏

过量 RPC

异常崩溃
```

Wujie 同源模式不能防御 Plugin 主动读取：

```text
window.parent

Host DOM

Host JavaScript Object

JavaScript-readable Cookie

localStorage / sessionStorage

同源 API
```

所以安装界面、文档和 Inspector 必须显示：

```text
Security Posture:
cooperative-isolation
```

不能显示：

```text
secure sandbox

malicious-code safe
```

---

## 35.2 Trust、Execution 与 Security Posture

三个维度分别建模：

| 维度 | 可选值 | 决定者 |
|---|---|---|
| Trust Level | `builtin` / `trusted` / `restricted` | Platform Installation Policy |
| Execution Mode | `direct` / `wujie` / `iframe` | Trust Policy + Admin Policy |
| Security Posture | `full-trust` / `cooperative-isolation` / `opaque-origin-sandbox` | Runtime 根据实际配置计算 |

默认映射：

| Trust Level | Execution Mode | Security Posture | 是否可为 Runtime Critical |
|---|---|---|---|
| builtin | direct | full-trust | 可以 |
| trusted | direct | full-trust | 不可以 |
| restricted | wujie | cooperative-isolation | 不可以 |
| restricted | iframe（optional） | opaque-origin-sandbox | 不可以 |

必须满足：

```text
restricted -> direct
```

永远非法。

Plugin Manifest 可以声明：

```text
requested runtime

requested permissions
```

但不能声明：

```text
effective trust

effective execution mode

granted permissions

critical
```

这些信息必须由平台侧的 Installation Policy 保存。

建议的运行策略对象至少包含：

```ts
interface PluginExecutionPolicy {
  trustLevel:
    | "builtin"
    | "trusted"
    | "restricted";

  executionMode:
    | "direct"
    | "wujie"
    | "iframe";

  securityPosture:
    | "full-trust"
    | "cooperative-isolation"
    | "opaque-origin-sandbox";

  grantedPermissions: string[];

  critical: boolean;
}
```

`securityPosture` 不能由管理员随意填写。

它必须由 Runtime 根据真实 Execution Mode 与 sandbox 配置推导。

---

## 35.3 Wujie 的定位

Restricted Plugin 的默认执行方式是：

```text
Wujie
```

Wujie 负责：

```text
加载子应用 Artifact

提供独立 iframe Window

隔离 JavaScript 全局环境

通过 Web Component 隔离样式

管理子应用挂载生命周期

承载 Plugin Bridge
```

但 Wujie 默认将子应用 JavaScript 注入与 Host 同源的 iframe，并允许主、子应用通过 `window.parent` 直接通信。

因此：

> **Wujie 是 Micro-frontend Runtime Isolation，不是面向恶意代码的 Security Boundary。**

官方运行原理：

<https://wujie-micro.github.io/doc/guide/>

第一版使用以下受控默认值：

```text
sync = false

alive = false

preload / pre-execute = false

fiber = true
```

含义：

- Host 持有顶层 Route，不让 Wujie 自动同步顶层 URL；
- 默认不保活，优先保证生命周期和资源占用可预测；
- Manifest、Trust Policy 和 Permission Grant 完成前不执行 Plugin Code；
- `fiber` 只改善脚本文件之间的调度，不代表 CPU 隔离，也不能阻止单个无限循环阻塞主线程。

每个 Wujie Plugin Surface 必须使用稳定且唯一的实例名：

```text
plugin identity
+
plugin version
+
surface identity
+
runtime instance identity
```

通过 `props` 注入的数据只能包含：

```text
非敏感 Plugin Metadata

Bridge Bootstrap Descriptor
```

禁止通过 `props` 注入：

```text
Host Store

Host Service Object

React Context

DOM Node

Access Token

Raw API Client
```

Wujie 的 custom fetch 可以用于：

```text
Artifact Allowlist

加载错误归因

资源观测

缓存策略
```

但不能把它当作完整 Network Security Boundary。

同源 Plugin 仍可能直接调用浏览器原生 `fetch`、XHR、Image 或其他网络接口。

---

## 35.4 可选原生 Sandboxed iframe

V1 不支持独立 Plugin Origin。

同时保留一个可选的：

```text
Native Iframe Plugin Adapter
```

它与 Wujie Adapter 并列，不是 Wujie 的一个安全配置开关。

默认 iframe policy：

```html
<iframe sandbox="allow-scripts" />
```

不授予：

```text
allow-same-origin

allow-forms

allow-popups

allow-downloads

allow-top-navigation
```

即使 iframe URL 与 Host 来自同一部署 Origin，未授予 `allow-same-origin` 时，浏览器也会把子文档置于 opaque origin。

此时 Plugin 只能通过：

```text
MessageChannel / RPC
```

使用 Host Capability。

如果某个 Plugin 必须同时使用：

```text
allow-scripts
+
allow-same-origin
```

则它不再获得 `opaque-origin-sandbox` Posture，必须降级为：

```text
cooperative-isolation
```

浏览器对该组合的安全警告：

<https://html.spec.whatwg.org/multipage/iframe-embed-object.html#attr-iframe-sandbox>

Native iframe Adapter 是可选增强，不阻塞 Wujie V1 落地。

如果产品未来要求真正执行敌对代码，则必须：

```text
启用通过验收的 opaque-origin iframe

或

引入独立 Plugin Origin
```

不能只增加 Permission 声明后继续使用同源 Wujie。

---

## 35.5 Permission Model

Permission 分三层：

```text
Requested Permissions
        ∩
Granted Permissions
        ∩
Platform Policy
        ↓
Effective Permissions
```

例如 Manifest：

```json
{
  "permissions": [
    "cluster.read",
    "workload.read"
  ]
}
```

这里的 `permissions` 只表示 Requested Permissions，不定义 Action 与 Permission 的关系。

例如 Host Capability Contract 定义：

```text
kubesphere.workload@1
  action: list
  required permission: workload.read
```

管理员可以只授予：

```text
cluster.read
```

则 Plugin 调用 `kubesphere.workload@1` 的 `list` Action 时，Permission Broker 根据 Host Capability Contract 检查：

```text
required permission = workload.read

workload.read ∈ Effective Permissions
```

条件不成立时返回稳定的：

```text
PERMISSION_DENIED
```

每次 Capability 调用都必须重新检查当前 Plugin Instance 的 Effective Permissions。

不能只在安装时检查一次。

每次 Bridge 调用的固定校验顺序是：

```text
Manifest requires 中包含 capability@major
        ↓
Host Capability Contract 中存在 action
        ↓
Request Schema Valid
        ↓
Required Permissions ⊆ Effective Permissions
        ↓
Invoke Host Capability
        ↓
Result Schema Valid
```

Plugin Manifest 与 Plugin Runtime 都不能覆盖或扩展 Host 定义的 Action、Schema 或 Required Permissions。

但必须明确：

> **Permission Broker 只约束平台提供的正式 Bridge；它不能阻止同源 Wujie Plugin 绕过 Bridge 访问浏览器可见资源。**

后端 API 必须继续执行：

```text
Authentication

Kubernetes / KubeSphere RBAC

Resource Authorization
```

前端 Permission 不能替代后端授权。

---

## 35.6 Plugin Bridge / RPC

Wujie 与可选 iframe 共享同一套 Bridge Contract。

区别只在 Transport：

```text
Wujie
  └── Same-origin MessageChannel

Native iframe
  └── Opaque-origin MessageChannel
```

Bridge Handshake 必须由 Host 发起，并绑定：

```text
Plugin Identity

Plugin Version

Plugin Instance Identity

Protocol Version

Runtime Nonce

MessagePort
```

后续请求至少包含：

```text
requestId

capability

action

payload
```

所有消息必须执行：

```text
Plugin Instance Check

Protocol Version Check

Manifest Capability Requirement Check

Host Capability Action Lookup

Request / Result Schema Validation

Permission Check

Request Deduplication

Timeout / Cancellation

Message Size Limit

Concurrency / Rate Limit

Structured Audit
```

拒绝：

```text
unknown instance

disposed instance

unknown capability

capability not declared in Manifest requires

action not defined by Host Capability Contract

invalid payload

duplicate requestId

oversized message
```

具有权限语义的调用不能依赖 Wujie 全局 Event Bus。

全局 Event Bus 可以承载低风险通知，但不能成为 Privileged RPC Channel。

---

## 35.7 Restricted UI Extension

Trusted Direct Plugin 可以注册：

```text
React Component Contribution
```

Restricted Plugin 不能把 React Component 或 Function Reference 传入 Host Realm。

Restricted UI Extension 采用 Manifest-first 模型。Plugin 只能在 Manifest 中静态声明：

```text
Route Contribution

Navigation Contribution

Sandbox Surface Contribution
```

Sandbox Surface 至少包含：

```text
slot / route

surfaceId

order

layout metadata

initial serializable parameters
```

Route 与 Navigation 必须通过 `surfaceId` 引用同一个 Manifest 中声明的 Sandbox Surface，不能携带运行时 Component 或 Function。

Host 在执行 Restricted Plugin Code 前完成：

```text
读取并校验 Manifest Contribution
        ↓
校验 Route / Navigation / Slot / Surface 引用
        ↓
写入 Host Route、Navigation 与 Extension Registry
        ↓
绑定 contributorPluginId / ownerPluginId
```

Bridge 不提供：

```text
registerExtension

registerRoute

registerNavigation

replaceContribution
```

Restricted Plugin Runtime 只能在 Host 已注册并分配的 `surfaceId` 内启动、渲染和交换结构化状态，不能改变 Extension Registry。

这些 Registry Record 始终关联 Plugin `loadState`。Plugin 进入 FAILED / SKIPPED 后，Host 不再挂载对应 Surface，并显示不可用状态；这属于已声明 Contribution 的状态投影，不是运行时动态注册或卸载。

如果需要条件显隐，只能使用 Manifest 中由 Host 解释的声明式条件，例如 Granted Permission、Capability Availability 或 Feature Flag；V1 不接受 Plugin JavaScript Callback 作为注册条件。

Host 负责：

```text
校验 Manifest 与 Slot Contract

注册 Route / Navigation / Sandbox Surface

创建 Container

控制 Route Ownership

启动 Wujie / iframe Surface

显示 Loading / Error Boundary

清理 Surface 与 Bridge
```

Plugin 通过可序列化的 Snapshot / Event 获取：

```text
Theme

Locale

Current Cluster / Workspace Scope

Host Navigation Command
```

V1 中 Restricted Plugin 可以：

```text
消费 allowlisted Host Capability

通过 Manifest 贡献 Sandbox Surface

通过 Manifest 贡献声明式 Route / Navigation Metadata
```

V1 中 Restricted Plugin 不可以：

```text
向 Global Capability Registry 提供 Capability

成为 Builtin / Trusted Plugin 的启动依赖

向 Host 注入任意 React Component

通过 RPC 动态注册或修改 Extension
```

跨 Realm Capability Provider 需要单独设计 RPC Provider Lifecycle、Failure Propagation 和 Contract Compatibility，不进入当前 V1。

---

## 35.8 Failure Semantics

Restricted Plugin 永远：

```text
critical = false
```

以下失败只影响当前 Plugin：

```text
Manifest Invalid

Permission Invalid

Wujie Resource Load Failed

Bridge Handshake Failed

Plugin Bootstrap Failed

Surface Render Failed

RPC Protocol Violation
```

结果：

```text
Plugin = FAILED / SKIPPED

Host 显示 Plugin Error Boundary

Runtime 继续激活其他 Plugin

Inspector 记录阶段与原因
```

Builtin Critical Plugin 失败仍然：

```text
Runtime Bootstrap Failed
```

V1 只有 Builtin Plugin 可以成为 Runtime Critical；任何 Non-builtin Plugin 的 `critical = true` 都是非法 Policy。

## 35.10 Restricted Plugin 验收矩阵

安全与隔离必须在真实浏览器中验证，不能只测试 Mock Context。

最高测试 Seam 是：

```text
Manifest + Installation Policy + Host Capability Contract
                       ↓
              Host Plugin Runtime
                       ↕
                  Test Plugin
                       ↓
UI / RPC Result / Inspector / Audit
```

| 场景 | 操作 | 预期 |
|---|---|---|
| Trust 提权 | Restricted Manifest 请求 direct | Policy 拒绝，Plugin Code 不执行 |
| 权限缩减 | 请求 A/B，仅授权 A | A 成功，B 返回 PERMISSION_DENIED |
| Action 所有权 | 调用 Host Contract 中不存在的 Action | 请求被拒绝，Manifest 不能补充或覆盖 Action 定义 |
| Manifest-first | Plugin 通过 RPC 请求动态注册 Route / Navigation / Surface | 请求被拒绝，Host Registry 不发生变化 |
| Surface 引用 | Route 引用未声明的 surfaceId | Manifest 校验失败，Plugin Code 不执行 |
| Wujie 加载 | 加载合法 Plugin | Surface 正常显示，Posture=cooperative-isolation |
| Wujie 边界刻画 | Plugin 访问 window.parent | 明确记录该访问在同源模式不可被可靠阻止，不产生虚假安全断言 |
| Host Object 注入 | 检查 props / Bridge | 不包含 Store、DOM、Token、Raw API Client |
| RPC Schema | 发送非法 payload | 请求被拒绝并记录 Audit |
| RPC 重放 | 重复 requestId | 第二次请求被拒绝 |
| RPC 超限 | 超大或高频消息 | 被限流或拒绝，不影响其他 Plugin |
| Bridge teardown | Surface 销毁后继续发消息 | disposed instance 被拒绝 |
| Plugin 崩溃 | Wujie Bootstrap throw | Plugin FAILED，Console Core 仍 Ready |
| Optional iframe | sandbox 不含 allow-same-origin | Plugin 无法读取 parent DOM / Host Storage |
| Backend Authorization | 绕过 Bridge 请求无权 API | Backend 仍拒绝 |

测试 Fixture 至少包括：

```text
Trusted Direct Plugin

Cooperative Wujie Plugin

Boundary / Hostile-behavior Plugin

Opaque-origin iframe Plugin（启用 optional adapter 时）
```

其中 Boundary Fixture 用于暴露真实边界，不用于证明 Wujie 拥有不存在的恶意代码隔离能力。

# 39. 完整 Bootstrap 流程

```text
Page Load
   │
   ▼
Plugin Discovery
   │
   ▼
Plugin Manifests + Installation Policies
   │
   ▼
Validate Manifest Without Executing Plugin Code
   │
   ▼
Resolve Effective Execution Policy
   │
   ├── Trust Level
   ├── Execution Mode
   ├── Security Posture
   ├── Granted Permissions
   ├── Critical Flag
   └── Reject restricted -> direct
   │
   ▼
Collect requires / provides
   │
   └── Restricted cannot provide Global Capability
   │
   ▼
Dependency Resolver
   │
   ├── Missing Capability Check
   ├── Capability Version Check
   ├── Circular Dependency Check
   └── Critical Dependency Closure Check
   │
   ▼
Topological Sort
   │
   ▼
Register Manifest-first Restricted Contributions
   │
   ├── Route
   ├── Navigation
   └── Sandbox Surface
   │
   └── no Plugin Code executed
   │
   ▼
Select Runtime Loader
   │
   ├── Direct Loader
   ├── Wujie Loader
   └── Iframe Loader（optional）
   │
   ▼
Prepare Plugin Adapters
   │
   ├── Direct modules may load in parallel
   ├── Wujie metadata only; no pre-execute
   └── Iframe metadata only; no pre-execute
   │
   ▼
Sequential Critical Direct Activation
   │
   ├── register capability
   ├── register extension
   ├── register route
   └── register navigation
   │
   ▼
Non-critical Plugin Activation
   │
   ├── Trusted Direct Adapter
   ├── Wujie App + Bridge
   ├── Optional Iframe + Bridge
   └── failure is isolated to current Plugin
   │
   ▼
Validate Direct Runtime Declarations
   │
   ├── declared provides actually registered
   ├── no undeclared provides
   └── no undeclared requires
   │
   ▼
Runtime Ready
   │
   └── Inspector may contain FAILED / SKIPPED non-critical Plugins
```

关键顺序：

```text
Manifest + Platform Policy
        ↓
Effective Execution Policy
        ↓
Dependency + Contribution Validation
        ↓
Loader Selection
        ↓
Plugin Code Execution
```

不能让 Plugin Code 在 Trust 与 Permission 决策之前运行。

Restricted Plugin 只允许消费 Direct Plugin 已经提供的 Capability。

因此第一版统一在 Critical Direct Plugin 就绪后，再建立 Wujie Bridge。

# 40. 完整错误模型

第一版坚持：

```text
Fail Early
+
Scope Failure By Criticality
```

错误尽量在更早阶段发现，但不是所有 Plugin Error 都让整个 Console 失败。

规则：

```text
Critical Builtin Failure
  -> Runtime Bootstrap Failed

Non-critical Trusted Failure
  -> Plugin FAILED / Runtime Continues

Restricted Failure
  -> Plugin FAILED / Runtime Continues
```

任何 Non-builtin Plugin 都不能设置：

```text
critical = true
```

Critical Plugin 的传递性 Plugin 依赖闭包只能包含 Critical Builtin Plugin。

该规则按 Resolver 实际选中的 Provider 展开；Host 原生 Capability 根节点不计入 Plugin 闭包。

## Manifest / Policy 阶段

发现：

```text
Invalid Effective Execution Policy

Restricted -> Direct

Invalid / Conflicting Route, Navigation or Sandbox Surface Contribution
```

这些错误都在执行对应 Plugin Code 前发现。

影响 Critical Plugin 时 Runtime Bootstrap Failed；只影响 Non-critical Plugin 时将其标记为 SKIPPED，并且不注册它的 Contribution。

---

## Resolve 阶段

发现：

```text
Missing Capability

Capability Major Version Mismatch

Circular Dependency

Critical Dependency Closure Violation
```

处理方式：

```text
影响 Critical Plugin
  -> Runtime Bootstrap Failed

只影响 Non-critical Plugin
  -> Plugin SKIPPED
  -> 依赖它的 Non-critical Plugin 一并 SKIPPED
  -> Runtime Continues
```

---

## Activate 阶段

发现：

```text
Direct Plugin activate() throws

Wujie Resource Load Failed

Bridge Handshake Failed

Sandbox Surface Bootstrap Failed
```

处理方式：

```text
Critical Plugin
  -> 停止后续 Bootstrap
  -> Runtime 不进入 Ready

Non-critical / Restricted Plugin
  -> 当前 Plugin FAILED
  -> 显示 Host Error Boundary
  -> 继续激活其他无依赖 Plugin
```

---

## Runtime Assertion 阶段

发现：

```text
Declared Capability Not Registered

Undeclared Capability Registered

Undeclared Capability Required
```

处理方式仍按 Criticality 决定：

```text
Critical Plugin Assertion Failed
  -> Runtime 不进入 Ready

Non-critical Plugin Assertion Failed
  -> 当前 Plugin FAILED
  -> Runtime Continues
```

---

## Permission / Bridge 阶段

发现：

```text
Permission Denied

Invalid Request / Result Schema

Bridge Capability Not Present In Manifest requires

Unknown Host Capability Action

Unknown / Unregistered Sandbox Surface Reference

Runtime Extension Registration Requested By Restricted Plugin

Unknown / Disposed Plugin Instance

Duplicate Request ID

Message / Rate Limit Exceeded
```

默认只拒绝当前请求并记录 Audit。

对于持续协议违规，可以：

```text
关闭当前 Bridge

Plugin = FAILED

建议管理员在下次 Reload 禁用 Plugin
```

V1 不尝试在同源 Wujie 中把这套处理描述为恶意代码 containment。

```text
        ▼
```

解决：

```text
      ▲
      │
```

解决：

```text

```


```text

```

```text
PluginAdapter
├── Direct Transport
│   └── PluginContext
└── Bridge Transport
    ├── Wujie
    └── iframe（optional）
```

Bridge 只传输结构化数据，并在 Host 侧按照 Host Capability Contract 执行 Action Lookup、Permission 与 Schema Validation。

# 46. 设计结论

第一版不把浏览器 Runtime 设计成一个持续变化、需要不断 reconcile 的插件操作系统。

而是：

> **一次页面加载构建一个稳定、可验证、可诊断的 Plugin Runtime。**

Plugin Set 变化：

```text
Runtime A
   ↓
Reload
   ↓
Runtime B
```

UI 扩展通过：

```text
Extension Point
```

完成。

插件间能力共享通过：

```text
Capability Contract
```

完成。

Capability 使用：

```text
name@major
```

表达粗粒度 ABI 兼容性。

插件依赖通过：

```text
requires / provides
```

在 Bootstrap 阶段完成一次性解析。

Module Loading：

```text
允许并行
```

Plugin Activation：

```text
默认串行
```

避免在没有 disposer / rollback 机制的情况下制造部分并发失败状态。

Extension 顺序：

```text
由 order + stable tie-breaker 决定
```

绝不依赖 Activation Order。

Manifest 与 Runtime：

```text
必须做双向一致性校验
```

避免 Resolver 基于错误声明构建依赖图。

Trust 与 Execution：

```text
Builtin / Trusted
  -> Direct

Restricted
  -> Wujie by default

Stronger isolation
  -> Native sandboxed iframe（optional）
```

Wujie 在当前不支持独立 Origin 的约束下提供：

```text
cooperative-isolation
```

它解决意外冲突和集成边界，不解决恶意同源代码隔离。

Permission Broker 约束正式 Bridge，但 Backend Authorization 仍是数据安全边界。

Restricted Plugin：

```text
永远 non-critical

失败时 fail-soft

不阻止 Console Core Ready
```

Kernel 最后提供：

```text
kernel.inspect()
```

用于查看当前：

```text
Plugins

Capabilities

Extensions

Routes

Dependencies

Trust Levels

Execution Modes

Security Postures

Granted Permissions

Bridge States
```

因此 V1 最终可以浓缩成：

> **Plugin Set 动态、Runtime 静态；Manifest 描述声明，Installation Policy 决定信任与授权，Capability 描述能力，Extension 描述 UI 扩展，Trusted 走 Direct，Restricted 默认走 Wujie，Reload 重建 Runtime，Inspector 提供事实诊断。**

这套模型保持了足够小的实现复杂度，同时补齐了版本兼容、声明一致性、失败确定性、扩展排序、信任策略、权限治理和线上诊断这些真正会影响工程质量的基础能力。

它同时诚实保留一个边界：

> **没有独立 Origin 时，Wujie 不是恶意代码 Security Sandbox。**
