# 前端插件系统 V1 技术落地方案（最终版）

## 0. 文档状态

本文是前端插件系统 V1 的规范性设计。

设计结论来自 [V1 消融实验报告](<./V1 消融实验报告.md>)。如果本文与早期技术调研或消融前方案冲突，V1 以本文为准。

V1 只为当前已经存在的两条执行路径建模：

```text
Builtin Plugin
  -> 与 Kernel 同包构建
  -> Direct activate

Restricted External Plugin
  -> Installed Manifest
  -> Wujie
  -> Plugin Bridge
```

本文中的“必须”是 V1 不变量；“建议”允许实现阶段在不改变外部行为的前提下调整。

---

# 1. 目标与前提

## 1.1 设计目标

V1 必须解决：

1. Host 提供稳定的 UI 扩展点；
2. Plugin 通过 Capability 共享能力，不依赖彼此内部实现；
3. 根据声明自动计算激活顺序；
4. Capability Major 不兼容时在执行代码前失败；
5. Descriptor / Manifest 与 Runtime 注册行为保持一致；
6. Contribution 顺序稳定且可预测；
7. Core 启动失败 fail-fast，其他 Plugin 失败 fail-soft；
8. Restricted Plugin 通过 Wujie 获得运行时隔离和集成治理；
9. Bridge Action 具备 Schema、Permission、限流和诊断；
10. Runtime 状态可以被低成本检查。

核心约束：

> **Plugin Set 可以变化，但单次页面 Runtime 生命周期内保持不变。**

安装、升级、启用、禁用和卸载只修改下一次 Runtime 的输入：

```text
Plugin Configuration Change
          ↓
      Reload Required
          ↓
Rebuild Plugin Runtime
```

## 1.2 V1 成立的现实前提

本设计依赖三个前提：

1. Restricted Plugin 当前主要来自官方或合作方，不开放任意第三方 JavaScript 市场；
2. Builtin Plugin 与 Kernel 属于同一个 Console 构建产物；
3. 当前不存在真实的 Trusted External Direct Plugin。

任何前提失效时，必须重新评估对应消融结论，不能继续向当前模型硬塞分支。

## 1.3 非目标

V1 不实现：

```text
Hot Install / Hot Unload / Hot Upgrade

deactivate() / Disposer / General Rollback

Runtime Dependency Reconcile

Capability Watch / Provider Switching

Trusted External Direct Plugin

External ESM / Module Federation Loader

Generic RuntimeLoader / PluginAdapter

Native Sandboxed iframe

Independent Plugin Origin

Hostile-code Containment

Generic EventBus

SemVer Solver / Multiple Provider Negotiation

Parallel Activation
```

# 2. 最终核心原则

```text
1. Runtime 生命周期内 Plugin Set immutable

2. Plugin Set 变化统一通过 Reload 生效

3. Builtin 与 Kernel 同包构建并直接 activate

4. External Plugin 在 V1 统一为 Restricted + Wujie

5. Plugin Dependency 只通过 Capability

6. Capability 使用 name@major

7. requires / provides 只在 Bootstrap 解析一次

8. Host Core Roots 的传递性依赖闭包必须全部是 Builtin

9. UI 扩展统一通过 Contribution

10. Contribution 顺序显式且 deterministic

11. Restricted Contribution 必须 Manifest-first

12. Restricted Plugin 不能提供 Global Capability

13. 只有 Bridge-exposed Capability 需要
    Action / Schema / Permission Contract

14. Permission 在每次 Bridge Action 调用时检查

15. Wujie 只承诺 cooperative-isolation

16. Backend Authorization 仍是真正的数据安全边界

17. Core Closure Failure fail-fast

18. Non-core / Restricted Failure fail-soft

19. Inspector 只投影 Runtime Facts

20. 不为未来变化提前建立通用框架
```

---

# 3. 规范术语

| 术语 | 含义 |
|---|---|
| Plugin Kernel | 最小不可插件化 Runtime，负责 Bootstrap、Resolver 和两个 Registry |
| Builtin Plugin | 与 Kernel 同包构建、直接获得 PluginContext 的可信代码 |
| Restricted Plugin | 不允许进入 Direct Host Realm，只能通过 Wujie 与 Bridge 集成的外部插件 |
| PluginDescriptor | Resolver 需要的最小依赖声明 |
| PluginDefinition | Builtin Plugin 的静态定义与 activate 实现 |
| RestrictedPluginManifest | Restricted Plugin 在代码执行前可验证的完整声明 |
| InstalledPluginConfig | 平台保存的安装版本、启用状态和 Granted Permissions |
| Capability | Plugin 之间共享行为的版本化 Contract |
| BridgeCapabilityContract | Host 为可跨 Bridge 使用的 Capability 定义的 Action Contract |
| Contribution | Route、Navigation 或 UI Extension 的声明与 Registry Record |
| Core Root | Host 源码中显式指定、Console Ready 必须依赖的 Builtin Plugin |
| Core Closure | 从 Core Roots 沿 Capability Provider 反向展开得到的传递性 Plugin 集合 |
| Runtime State | Plugin 在当前 Runtime 中的最终事实：ACTIVE、SKIPPED 或 FAILED |

`Restricted` 描述的是 Host Realm 准入限制，不代表 Host 可以安全执行任意恶意 JavaScript。

V1 不存在 `trusted` 外部类型，也不保存通用的 `trustLevel`、`executionMode`、`securityPosture` 或 `critical` 字段。

这些展示信息全部由来源和 Core Closure 派生：

| Runtime 事实 | Execution | Security Posture | Core |
|---|---|---|---|
| Builtin | direct | full-trust | 由 Core Closure 决定 |
| Restricted | wujie | cooperative-isolation | 永远否 |

# 4. 最终架构

```text
Static Builtin Definitions         Installed Plugin Store
            │                       │
            │                       ├── InstalledPluginConfig
            │                       └── RestrictedPluginManifest
            │                                  │
            └──────────────┬───────────────────┘
                           ▼
                    PluginDescriptor[]
                           │
                           ▼
                  DependencyResolver
                    │             │
                    ▼             ▼
               Core Closure   Activation Order
                    └──────┬──────┘
                           ▼
                       Bootstrap
                  ┌────────┴────────┐
                  ▼                 ▼
          Builtin activate    WujiePluginAdapter
                  │                 │
                  │                 ▼
                  │             PluginBridge
                  │                 │
                  └────────┬────────┘
                           ▼
                  CapabilityRegistry

Builtin Context / Restricted Manifest
                  │
                  ▼
             ContributionRegistry
                  │
                  ▼
                UI Host
```

Kernel 只保留四类职责：

```text
Collect + Bootstrap

Dependency Resolution

Capability Registry

Contribution Registry
```

浏览器特有复杂度只存在于：

```text
WujiePluginAdapter

PluginBridge
```

以下内容不是 V1 一级 Module：

```text
PluginDiscovery

TrustPolicy

PluginExecutionPolicy

RuntimeLoader

DirectPluginAdapter

PermissionBroker

ManifestContributionRegistrar

KernelInspector class
```

对应逻辑分别内联到 Bootstrap、PluginBridge 或 Runtime Snapshot 投影中。

# 5. 核心数据模型

## 5.1 基础标识

```ts
type PluginId = string;

type CapabilityId =
  `${string}@${number}`;

type PermissionId = string;

type JsonValue =
  | null
  | boolean
  | number
  | string
  | JsonValue[]
  | { [key: string]: JsonValue };
```

约束：

- Plugin ID 在一个 Runtime 内唯一；
- Builtin Plugin ID 是保留命名空间，Restricted Plugin 不能覆盖同名 Builtin；
- Capability ID 必须包含一个显式 Major；
- V1 不接受版本范围；
- 同一 `CapabilityId` 只能有一个 Provider；
- Route ID 与 Navigation ID 在 Runtime 内分别唯一；
- UI Extension ID 在同一个 Slot 内唯一；
- Restricted `surfaceId` 在当前 Plugin Manifest 内唯一。

## 5.2 PluginDescriptor

```ts
interface PluginDescriptor {
  id: PluginId;

  version: string;

  requires: readonly CapabilityId[];

  provides: readonly CapabilityId[];
}
```

`PluginDescriptor` 是 Resolver 的唯一输入 Contract。

它不包含：

```text
entry

permissions

contributions

activate implementation

execution mode

runtime state
```

## 5.3 Builtin PluginDefinition

```ts
interface PluginDefinition
  extends PluginDescriptor {

  activate(
    context: PluginContext,
  ): void | Promise<void>;
}
```

Builtin Definitions 通过静态 import 收集：

```ts
import consoleShell
  from "./plugins/console-shell";

import cluster
  from "./plugins/cluster";

export const builtinDefinitions = [
  consoleShell,
  cluster,
];
```

Builtin 不生成仅为形式统一而存在的 `plugin-manifest.json`，也不经过动态 Loader。

## 5.4 RestrictedPluginManifest

```ts
interface RestrictedPluginManifest
  extends PluginDescriptor {

  // Restricted V1 固定不能 provide。
  provides: readonly [];

  // V1 必须是平台允许的同源入口。
  entry: string;

  // 例如 kubesphere.console@1。
  hostApi: string;

  // Requested Permissions。
  permissions: readonly PermissionId[];

  contributions: {
    routes?:
      readonly RestrictedRouteContribution[];

    navigation?:
      readonly NavigationContribution[];

    surfaces?:
      readonly SandboxSurfaceContribution[];
  };
}
```

示例：

```json
{
  "id": "kubeeye",
  "version": "1.2.0",
  "entry": "/plugins/kubeeye/1.2.0/",
  "hostApi": "kubesphere.console@1",
  "requires": [
    "kubesphere.cluster@2"
  ],
  "provides": [],
  "permissions": [
    "cluster.read",
    "workload.read"
  ],
  "contributions": {
    "surfaces": [
      {
        "id": "workload-detail",
        "slot": "workload.detail.tabs",
        "surfaceId": "workload-detail",
        "order": 200
      },
      {
        "id": "overview",
        "surfaceId": "overview",
        "order": 100
      }
    ],
    "routes": [
      {
        "id": "overview-route",
        "path": "/kubeeye",
        "target": {
          "kind": "sandbox-surface",
          "surfaceId": "overview"
        }
      }
    ],
    "navigation": [
      {
        "id": "overview-nav",
        "label": "KubeEye",
        "routeId": "overview-route",
        "order": 200
      }
    ]
  }
}
```

Manifest 不允许声明：

```text
trustLevel

runtime.type

requested direct / iframe

critical

Bridge Action

Action Schema

Action -> Permission mapping
```

`hostApi` 同样只比较显式 Major。Host 不支持该 Major 时，Plugin 在 Manifest 阶段 SKIPPED，且不得加载 `entry`。

## 5.5 InstalledPluginConfig

```ts
interface InstalledPluginConfig {
  id: PluginId;

  version: string;

  enabled: boolean;

  grantedPermissions:
    readonly PermissionId[];
}
```

必须满足：

```text
Config.id = Manifest.id

Config.version = Manifest.version

Granted Permissions
  ⊆ Manifest Requested Permissions

```

Restricted Manifest 校验还必须满足：

```text

Every Manifest requires
  -> has Host-owned BridgeCapabilityContract

Requested Permissions
  ⊆ permissions known by required Bridge Contracts
```

Artifact Entry、Requested Permissions 和 Contribution 属于版本化 Manifest；管理员决策只保存在 Installed Config。

安装存储交给 Bootstrap 的记录是一个简单配对：

```ts
interface InstalledPluginRecord {
  manifest: RestrictedPluginManifest;

  config: InstalledPluginConfig;
}
```

## 5.6 Bootstrap 内部输入

Bootstrap 可以使用一个局部 discriminated union：

```ts
type PluginInput =
  | {
      kind: "builtin";
      definition: PluginDefinition;
    }
  | {
      kind: "restricted";
      manifest: RestrictedPluginManifest;
      config: InstalledPluginConfig;
    };
```

`kind` 是从来源得到的 Runtime Fact，不是可由 Plugin 请求的 Trust Policy。

# 6. Runtime 与生命周期

## 6.1 Runtime Immutable

一次页面加载只构建一次 Runtime：

```text
Page Load
   ↓
Collect Inputs
   ↓
Validate
   ↓
Resolve
   ↓
Activate
   ↓
Runtime Ready
```

Ready 后不再：

```text
增加或删除 Plugin

重算 Dependency DAG

替换 Capability Provider

动态注册 Restricted Contribution

重新激活 Consumer
```

## 6.2 唯一 Plugin 生命周期入口

Builtin 只有：

```ts
activate(context)
```

Restricted 由 Host 调用具体的：

```ts
wujiePluginAdapter.activate(...)
```

V1 没有通用 `PluginAdapter` Interface，也没有 Plugin 级 `deactivate()`。

Route 或 Surface 离开页面时，Wujie Adapter 仍必须清理它创建的浏览器资源；这是 Surface Lifecycle，不是 Plugin Set 的动态变更。

## 6.3 激活期注册原子性

为了让 Non-core Plugin 可以 fail-soft，Builtin 激活不能向全局 Registry 留下半完成状态。

Bootstrap 为每个 Builtin 创建绑定 owner 与 descriptor 的 `PluginContext`。该 Context 在激活期间暂存 Capability 和 Contribution 注册：

```text
begin activation
      ↓
PluginContext 暂存注册
      ↓
activate() success
      ↓
validate declared provides
      ↓
atomic commit to Registries
```

Commit 必须先校验 Capability 与 Contribution 两组 staged records，再一次性写入；不能先提交一个 Registry、随后在另一个 Registry 冲突。

任何 throw 或 assertion failure：

```text
discard staged records
```

这只是 Registry 写入缓冲，不是通用 EffectScope、Disposer 或任意副作用 rollback。

Builtin `activate()` 必须只通过 `PluginContext` 修改 Host Plugin Runtime，不应直接修改全局 DOM、全局 Store 或其他 Plugin 内部状态。

# 7. DependencyResolver

## 7.1 输入与输出

输入：

```text
PluginDescriptor[]
+
Plugin kind
+
Core Root IDs
```

输出至少包含：

```ts
interface Resolution {
  order: readonly PluginId[];

  coreClosure: ReadonlySet<PluginId>;

  dependencies: readonly {
    consumer: PluginId;
    capability: CapabilityId;
    provider: PluginId;
  }[];

  skipped: ReadonlyMap<
    PluginId,
    string
  >;
}
```

Resolver 是纯计算 Module，不加载 Artifact、不执行 Plugin Code、不写 Registry。

## 7.2 Resolve 算法

```text
Validate unique Plugin IDs
        ↓
Build capability -> provider index
        ↓
Reject duplicate providers
        ↓
Resolve every requires edge
        ↓
Detect missing capability
        ↓
Build dependency DAG
        ↓
Detect cycles
        ↓
Compute Core Closure
        ↓
Validate Core Closure is all Builtin
        ↓
Stable topological sort
```

稳定拓扑排序的 tie-breaker 使用：

```text
pluginId ASC
```

配置数组顺序不能表达依赖或激活优先级。

如果 Restricted ID 与 Builtin ID 冲突，只将 Restricted Plugin 标记为 SKIPPED，Builtin 永远不会被安装记录覆盖。重复 Builtin ID 属于 Host 构建错误；涉及 Core 时 Runtime Bootstrap Failed。

## 7.3 Capability Provider 规则

V1 不做 Multiple Provider Negotiation。

同一 `CapabilityId` 出现多个 Provider 时：

```text
DUPLICATE_CAPABILITY_PROVIDER
```

Resolver 不选择“第一个”、最高版本或配置优先级。

如果冲突 Provider 或该 Capability 影响 Core Closure，Runtime Bootstrap Failed；否则冲突 Provider 全部 SKIPPED，并递归 Skip Consumer。

Major 不兼容等价于 Missing：

```text
requires kubesphere.cluster@2

only provides kubesphere.cluster@1

=> MISSING_CAPABILITY
```

## 7.4 Core Roots 与 Core Closure

V1 不在 Plugin 上保存 `critical: boolean`。

Host 源码定义 Core Roots：

```ts
const CORE_PLUGIN_IDS = [
  "console-shell",
] as const;
```

Resolver 从 Core Roots 沿实际 Capability Provider 展开传递依赖，得到 Core Closure。

必须满足：

```text
∀ plugin ∈ Core Closure:
  plugin.kind = builtin
```

如果 Core Root 缺失、Core 依赖缺失、Core 依赖形成环，或 Core Closure 包含 Restricted Plugin：

```text
Runtime Bootstrap Failed
```

Resolver 必须输出完整依赖路径，例如：

```text
console-shell
  -> kubesphere.cluster@2
  -> external-cluster-provider
```

## 7.5 Non-core Skip 传播

Descriptor / Manifest 或 Dependency 错误只影响 Non-core 时：

```text
Invalid Provider
      ↓
Provider SKIPPED
      ↓
Consumers recursively SKIPPED
```

如果 Builtin Provider 在 Activation 阶段失败，Bootstrap 在后续顺序中使用相同规则跳过尚未执行的 Consumer。

Restricted Plugin 的 `provides` 固定为空，因此：

- Builtin 不会依赖 Restricted；
- Restricted 之间不会产生 Provider 依赖；
- Restricted 只能消费已成功激活的 Builtin Capability。

# 8. Capability

## 8.1 Capability Contract

Plugin 应依赖：

```text
Capability Contract
```

而不是：

```text
Provider Plugin Implementation

Provider Store

Provider React Context
```

Capability 使用：

```text
capability-name@major
```

只表达 Major Compatibility，不实现 SemVer Range。

## 8.2 CapabilityRegistry

```ts
interface CapabilityRecord<T = unknown> {
  id: CapabilityId;

  providerPluginId: PluginId;

  value: T;
}

type CapabilityMetadata =
  Omit<CapabilityRecord, "value">;

interface CapabilityRegistry {
  get<T>(
    id: CapabilityId,
  ): T | undefined;

  require<T>(
    id: CapabilityId,
  ): T;

  list():
    readonly CapabilityMetadata[];
}
```

`list()` 只返回不可变 Metadata，不暴露 Capability Value。

Global Registry 的写接口仅供 Bootstrap 绑定后的 Context 使用，Plugin 不传入 owner：

```ts
interface PluginCapabilityContext {
  register<T>(
    id: CapabilityId,
    value: T,
  ): void;

  require<T>(
    id: CapabilityId,
  ): T;
}
```

Context 自动使用当前 `pluginId`，并立即执行声明校验：

```text
register(id)
  -> id ∈ descriptor.provides

require(id)
  -> id ∈ descriptor.requires
```

Builtin activate 成功后还必须检查：

```text
descriptor.provides
        ⊆
staged registered capabilities
```

## 8.3 Direct-only Capability

仅供 Builtin 使用的 Capability 只需要 TypeScript Contract：

```ts
interface ClusterInternalCapability {
  getCurrentCluster(): Cluster;
}
```

它不需要：

```text
Action Table

JSON Schema

Permission Mapping
```

## 8.4 Bridge-exposed Capability

只有允许 Restricted Plugin 使用的 Capability 才需要 `BridgeCapabilityContract`：

```ts
interface RuntimeSchema<T> {
  parse(value: unknown): T;
}

interface BridgeActionContract<
  Request extends JsonValue = JsonValue,
  Result extends JsonValue = JsonValue,
> {
  requestSchema:
    RuntimeSchema<Request>;

  resultSchema:
    RuntimeSchema<Result>;

  requiredPermissions:
    readonly PermissionId[];

  invoke(
    capability: unknown,
    payload: Request,
    context: {
      pluginId: PluginId;
      signal: AbortSignal;
    },
  ): Result | Promise<Result>;
}

interface BridgeCapabilityContract {
  id: CapabilityId;

  actions:
    Readonly<
      Record<
        string,
        BridgeActionContract
      >
    >;
}
```

`BridgeCapabilityContract` 由 Host 定义并随 Host 发布。

它只描述跨 Bridge 的调用方式，不是 Capability Provider；对应 `CapabilityId` 仍必须由成功激活的 Builtin 注册到 `CapabilityRegistry`。

Restricted Manifest 只声明：

```text
requires capability@major

requested permissions
```

Manifest 和 Plugin Runtime 都不能新增 Action、替换 Schema 或改变 Action 所需 Permission。

## 8.5 不提供 Generic EventBus

跨 Plugin 状态变化通过 Capability 表达：

```ts
interface ScopeCapability {
  getCurrent(): Scope;

  subscribe(
    listener: (scope: Scope) => void,
  ): () => void;
}
```

Bridge-exposed 版本可以把订阅映射为：

```text
Capability Action
+
Subscription-scoped Event
```

V1 不提供可以绕过 Capability Ownership 的全局 EventBus。

# 9. Contribution

## 9.1 三种业务 Contract

```ts
interface BuiltinRenderTarget {
  kind: "builtin";

  render: unknown;
}

interface SandboxRenderTarget {
  kind: "sandbox-surface";

  surfaceId: string;
}

type HostRenderTarget =
  | BuiltinRenderTarget
  | SandboxRenderTarget;

interface RouteContribution {
  id: string;

  path: string;

  target: HostRenderTarget;
}

type RestrictedRouteContribution =
  Omit<RouteContribution, "target"> & {
    target: SandboxRenderTarget;
  };

interface NavigationContribution {
  id: string;

  label: string;

  parentId?: string;

  routeId?: string;

  order?: number;
}

interface UiExtensionContribution {
  id: string;

  slot: string;

  order?: number;

  target: HostRenderTarget;
}

interface SandboxSurfaceContribution {
  id: string;

  slot?: string;

  surfaceId: string;

  order?: number;

  layout?: JsonValue;

  initialParameters?: JsonValue;
}
```

Route、Navigation 与 UI Extension 的业务语义不同，不能粗暴退化成一个万能 Slot Contract。

## 9.2 ContributionRegistry

底层统一：

```text
Ownership

Indexing

Stable Ordering

Conflict Diagnostics

Inspection
```

对外保留 typed interface：

```ts
interface ContributionRegistry {
  registerRoute(
    ownerPluginId: PluginId,
    contribution: RouteContribution,
  ): void;

  registerNavigation(
    ownerPluginId: PluginId,
    contribution:
      NavigationContribution,
  ): void;

  registerExtension(
    ownerPluginId: PluginId,
    contribution:
      UiExtensionContribution,
  ): void;

  listRoutes():
    readonly OwnedContribution<
      RouteContribution
    >[];

  listNavigation():
    readonly OwnedContribution<
      NavigationContribution
    >[];

  listExtensions(
    slot: string,
  ): readonly OwnedContribution<
    UiExtensionContribution
  >[];
}
```

Builtin 使用的 `PluginContributionContext` 不暴露 `ownerPluginId` 参数，Ownership 由绑定 Context 自动补充。

```ts
interface OwnedContribution<T> {
  ownerPluginId: PluginId;

  contribution: T;
}

interface PluginContributionContext {
  registerRoute(
    contribution: RouteContribution,
  ): void;

  registerNavigation(
    contribution:
      NavigationContribution,
  ): void;

  registerExtension(
    contribution:
      UiExtensionContribution,
  ): void;
}

interface PluginContext {
  capabilities:
    PluginCapabilityContext;

  contributions:
    PluginContributionContext;
}
```

`listRoutes`、`listNavigation` 和 `listExtensions` 返回不可变、已经稳定排序的 Snapshot，不暴露 Registry 内部可变集合。

Restricted Manifest 中的 Route 和 Extension Target 必须使用 `{ kind: "sandbox-surface", surfaceId }`，不得包含 Host-local render value；Builtin Context 可以注册 `{ kind: "builtin", render }`。UI Host 根据显式 `kind` 渲染，不猜测来源。

## 9.3 排序

所有有视觉顺序的 Contribution 使用：

```text
order ASC
    ↓
ownerPluginId ASC
    ↓
contributionId ASC
```

默认 `order` 必须是固定常量，不能使用注册时刻或 Activation Order。

Route 匹配优先级继续由 Host Router Contract 决定；Registry 插入顺序不得改变 Route 语义。Inspector 中的 Route 列表使用稳定 Metadata 排序即可。

## 9.4 Contribution 不产生 Dependency

```text
kubeeye contributes
  -> workload.detail.tabs
```

不等于：

```text
kubeeye requires
  -> workload plugin
```

如果当前 Runtime 没有对应 Slot，Contribution 保持未使用即可。

只有 Capability `requires` 形成 Dependency DAG Edge。

## 9.5 Restricted Manifest-first

Restricted Plugin 的 Route、Navigation 和 Sandbox Surface 必须全部由 Manifest 静态声明。

Bootstrap 在执行 Restricted Plugin Code 前：

```text
Validate Manifest Contributions
        ↓
Validate IDs and collisions
        ↓
Validate Route target -> surfaceId
        ↓
Validate Navigation -> routeId when present
        ↓
Validate Navigation -> parentId when present
        ↓
Register with ownerPluginId
```

PluginBridge 不提供：

```text
registerRoute

registerNavigation

registerExtension

replaceContribution
```

Host 将 Manifest 数据规范化为 Registry Record：带 `slot` 的 Sandbox Surface 变成 `UiExtensionContribution`，Route 使用 `SandboxRenderTarget`，Navigation 保留对 Route ID 的引用。

同一个 Restricted Manifest 的 Contribution 必须先全部验证，再原子提交；任一冲突都丢弃该 Plugin 的整组记录，不能留下部分 Route 或 Navigation。

Restricted Runtime 只能在 Host 已声明并分配的 `surfaceId` 中渲染和交换结构化状态。

如果需要条件显隐，只能使用 Host 可解释的声明式条件；V1 不接受 Plugin JavaScript Callback 作为 Host Contribution 条件。

Manifest 或 Dependency 阶段已经 SKIPPED 的 Restricted Plugin 不注册 Contribution。

成功注册但随后 Activation / Bridge 失败的记录继续保留给 Inspector；UI Host 使用 Runtime State 投影，只消费 owner 状态为 ACTIVE 的 Contribution。已挂载 Surface 后发生失败时，由 Host Error Boundary 替换其内容。

# 10. 两条执行路径

## 10.1 Builtin Direct

Builtin：

- 静态 import；
- 不读取 JSON Manifest；
- 不经过 Loader；
- 不经过 Adapter；
- 按 Resolver 顺序串行调用 `definition.activate(context)`。

Builtin 与 Kernel 同包构建，因此它是 full-trust 代码。PluginContext 是组织依赖和 Ownership 的 Interface，不是 Security Sandbox。

## 10.2 Restricted Wujie

Restricted Plugin 固定：

```text
External Installed Artifact
        ↓
RestrictedPluginManifest
        ↓
WujiePluginAdapter
        ↓
PluginBridge
```

`WujiePluginAdapter` 是具体 Browser Adapter，负责：

```text
Artifact Loading

Wujie App Bootstrap

Stable Instance Naming

Surface Mount / Unmount

Bridge Handshake

Host Loading / Error Boundary

MessagePort and Listener Cleanup
```

V1 建议默认：

```text
sync = false

alive = false

fiber = true

degrade = false

V1 不调用 preloadApp
```

含义：

- Host 持有顶层 Route；
- Surface 离开后清理实例资源；
- 不建立并行预加载或预执行阶段；
- Manifest、Config 和 Dependency 校验完成后，才允许通过 `startApp` 执行 Plugin Code；
- `fiber` 只改善调度，不提供 CPU 隔离；
- Wujie degrade 模式不作为第三条 Runtime 路径，必须由 Console Browser Support Matrix 单独约束。

这些参数语义以 Wujie 官方 [`startApp`](https://wujie-micro.github.io/doc/api/startApp.html) 文档为准。

Wujie `name` 由 Adapter 统一生成，必须在当前 Host 中稳定、唯一，并且不能被不同 Plugin 复用。

每个 Bridge / Surface Instance Identity 至少绑定：

```text
plugin id
+
plugin version
+
surface id
+
runtime instance id
```

传给 Wujie Plugin 的 props 只能包含：

```text
Non-sensitive Plugin Metadata

Bridge Bootstrap Descriptor
```

不得包含：

```text
Host Store

React Context

DOM Node

Function Reference

Access Token

Raw API Client
```

Restricted `entry` 必须通过 Host Artifact Allowlist，并且 V1 只支持平台允许的同源部署路径。

# 11. 信任与安全边界

## 11.1 Threat Model

| 目标 | Restricted Wujie V1 |
|---|---|
| 减少全局变量、样式、路由和生命周期的意外冲突 | 支持 |
| 约束正式 Bridge 可以执行的操作 | 支持 |
| 限制 Buggy Plugin 的重复调用和 RPC 风暴 | 支持 |
| Plugin 主动绕过 Bridge 后仍保护 Host | 不支持 |
| 执行任意敌对 JavaScript | 不支持 |

Wujie 同源模式不能可靠阻止 Plugin 主动访问：

```text
window.parent

Host DOM

Host JavaScript Object

JavaScript-readable Cookie

localStorage / sessionStorage

同源 API
```

Wujie 官方运行原理也明确说明子应用 iframe 与主应用同源，并可直接使用 `window.parent` 通信，参见 [Wujie 运行机制](https://wujie-micro.github.io/doc/guide/)。

因此 UI、文档和 Inspector 必须使用：

```text
cooperative-isolation
```

不能使用：

```text
secure sandbox

malicious-code safe
```

## 11.2 Network 与 Backend Authorization

Wujie custom fetch 可以用于：

```text
Artifact Allowlist

Resource Observability

Loading Error Attribution

Caching
```

它不是 Network Security Boundary。同源 Plugin 仍可能直接使用浏览器原生 `fetch`、XHR、Image 等接口。

后端必须继续执行：

```text
Authentication

Kubernetes / KubeSphere RBAC

Resource Authorization
```

前端 Permission 只约束正式 Bridge，不能替代后端授权。

# 12. Permission 与 PluginBridge

## 12.1 Permission Model

安装阶段：

```text
Manifest Requested Permissions
              +
Platform / Admin Decision
              ↓
       Granted Permissions
```

Runtime 不再计算或保存 `EffectivePermissions`。

每次 Bridge Action 调用检查：

```text
Action.requiredPermissions
          ⊆
Config.grantedPermissions
```

同时必须保证：

```text
Granted Permissions
  ⊆ Requested Permissions
```

Requested Permission 必须是该 Manifest 所需 `BridgeCapabilityContract` 中已知的 Permission；Manifest 不能创造新的 Permission 语义。

## 12.2 Handshake

Handshake 由 Host 发起并绑定：

```text
Plugin ID

Plugin Version

Plugin Instance ID

Surface ID

Bridge Protocol Version

Runtime Nonce

MessagePort
```

Plugin 不能自行声明或切换 Identity、Granted Permissions、Capability Contract。

Privileged Capability 调用只使用 Host 创建的 MessagePort。Wujie 全局 EventBus 不作为 Capability、Permission 或 Extension Channel。

## 12.3 Request / Response Envelope

```ts
interface BridgeRequest {
  type: "request";

  requestId: string;

  capability: CapabilityId;

  action: string;

  payload: JsonValue;
}

type BridgeResponse =
  | {
      type: "response";
      requestId: string;
      ok: true;
      result: JsonValue;
    }
  | {
      type: "response";
      requestId: string;
      ok: false;
      error: {
        code: string;
        message?: string;
      };
    };
```

Message 必须是结构化、可序列化数据。

Request 不携带可用于授权的 `pluginId` 或 Permission；Dispatcher 只使用 MessagePort 绑定的 Host-side Session Identity。

## 12.4 Dispatcher Pipeline

```text
Receive Request
      ↓
Check message size
      ↓
Validate instance / nonce / protocol
      ↓
Reject duplicate requestId
      ↓
Check capability ∈ manifest.requires
      ↓
Lookup BridgeCapabilityContract
      ↓
Lookup action
      ↓
Validate request schema
      ↓
Check required permissions
      ↓
Check concurrency / rate limit
      ↓
Create timeout / cancellation scope
      ↓
Invoke active Capability Provider
      ↓
Validate result schema
      ↓
Record audit
      ↓
Return response
```

成功与失败的每个出口都必须记录 Audit；不能只记录已经调用 Provider 的请求。

这些步骤属于 `PluginBridge` 的实现，不拆成 PermissionBroker、Limiter、AuditService 或 ProtocolEngine 等一级 Module。

## 12.5 必须保留的保护

```text
requestId

duplicate rejection

timeout / cancellation

message size limit

concurrency limit

rate limit

request schema validation

result schema validation

per-call permission check

structured audit
```

这些机制主要提供 Bug Containment，不代表 Hostile-code Containment。

## 12.6 Bridge Error Code

V1 至少稳定定义：

```text
BRIDGE_PROTOCOL_MISMATCH

UNKNOWN_PLUGIN_INSTANCE

DISPOSED_PLUGIN_INSTANCE

UNDECLARED_CAPABILITY_REQUIRE

CAPABILITY_NOT_BRIDGE_EXPOSED

UNKNOWN_ACTION

INVALID_REQUEST

INVALID_RESULT

PERMISSION_DENIED

DUPLICATE_REQUEST

MESSAGE_TOO_LARGE

RATE_LIMITED

CONCURRENCY_LIMITED

TIMEOUT

CAPABILITY_UNAVAILABLE
```

单次错误默认只拒绝当前 Request。

持续、严重协议违规可以关闭当前 Bridge，并把 Restricted Plugin 标记为 FAILED；V1 不自动重启。

# 13. Bootstrap

## 13.1 完整流程

```text
Static Builtin Definitions
          +
Enabled Installed Configs
          +
Restricted Manifests
          ↓
Pair Config with exact Manifest version
          ↓
Validate Descriptor / Manifest / Host API
          ↓
Validate required Bridge Contracts
and requested / granted permissions
          ↓
Normalize PluginDescriptor[]
          ↓
Validate Restricted Contributions
          ↓
Build provider index
          ↓
Resolve requires
          ↓
Missing / Duplicate / Circular Check
          ↓
Compute and validate Core Closure
          ↓
Stable Topological Order
          ↓
Activate Core Closure Builtins serially
          ↓
Activate remaining Builtins serially
          ↓
Propagate skips from failed providers
          ↓
Register eligible Restricted
Manifest Contributions
          ↓
Activate eligible Restricted Plugins serially
          ↓
Wujie + Bridge
          ↓
ACTIVE / FAILED / SKIPPED
          ↓
Runtime Ready
```

## 13.2 顺序不变量

必须满足：

1. Restricted Plugin Code 在 Manifest、Host API、Permission、Contribution 和 Dependency 校验完成前不得执行；
2. Core Closure 必须先于所有 Non-core Plugin 激活；
3. Builtin 必须先于 Restricted 激活；
4. 每个 Builtin 的 Registry 写入只在 activate 与 provides assertion 成功后提交；
5. Restricted Contribution 必须由 Host 注册，不能等待 Runtime RPC；
6. Restricted Bridge 只能消费已经成功提交的 Capability；
7. Runtime Ready 不要求所有 Non-core Plugin 成功，但要求 Core Closure 全部成功。

## 13.3 伪代码

```ts
async function bootstrapPluginRuntime(
  builtins: readonly PluginDefinition[],
  installed:
    readonly InstalledPluginRecord[],
) {
  const inputs =
    collectAndValidateInputs(
      builtins,
      installed,
    );

  const resolution = resolvePlugins(
    inputs,
    ["console-shell"],
  );

  assertCoreClosureIsBuiltin(
    resolution,
    inputs,
  );

  await activateBuiltinsSerially(
    resolution,
  );

  propagateProviderFailures(
    resolution,
  );

  registerEligibleRestrictedContributions(
    resolution,
  );

  await activateRestrictedSerially(
    resolution,
  );

  return createRuntime(
    resolution,
  );
}
```

这里的函数名表达职责，不要求每一步成为独立 class 或文件。

# 14. Runtime State 与失败语义

## 14.1 最小状态

```ts
type PluginRuntimeState =
  | {
      state: "ACTIVE";
    }
  | {
      state: "SKIPPED";

      stage:
        | "manifest"
        | "resolve";

      reason: string;
    }
  | {
      state: "FAILED";

      stage:
        | "activate"
        | "assertion"
        | "bridge";

      error: unknown;
    };
```

语义：

- `SKIPPED`：Plugin Code 从未执行；
- `FAILED`：已经尝试执行或已经建立 Runtime，随后失败；
- `ACTIVE`：当前可参与 Capability、Contribution 或 Surface Runtime。

`DISCOVERED`、`VALIDATED`、`LOADING` 只允许作为瞬时 Bootstrap Log，不保存为 Runtime 生命周期状态。

ACTIVE 可以因不可恢复的 Bridge 协议错误变为 FAILED；除此之外 V1 不提供 Restart、Retry 或 Reactivation。

## 14.2 错误处理矩阵

| 阶段 | 典型错误 | Core Closure | Non-core |
|---|---|---|---|
| Descriptor / Manifest | Invalid Descriptor、Host API Incompatible、Missing Bridge Contract、Invalid Permission、Invalid Contribution | Runtime Bootstrap Failed | Plugin SKIPPED |
| Resolve | Missing、Duplicate Provider、Circular、Core Closure Contains Restricted | Runtime Bootstrap Failed | Plugin SKIPPED，并递归 Skip Consumer |
| Activate | Builtin throw、Wujie Resource Failed、Bridge Bootstrap Failed | Runtime Bootstrap Failed | Plugin FAILED |
| Assertion | Undeclared Require、Undeclared Provide、Declared Provide Missing | Runtime Bootstrap Failed | Plugin FAILED |
| Bridge Request | Unknown Action、Invalid Payload、Permission Denied、Rate Limited | 不适用 | 默认 Reject Request |
| Persistent Bridge Failure | 重复严重协议违规、disposed 后持续发送 | 不适用 | Plugin FAILED |

Core Closure 失败后 Runtime 不进入 Ready。

Non-core 失败后 Runtime 可以 Ready，Inspector 必须保留失败阶段和原因。

## 14.3 稳定错误标识

Bootstrap 与 Registry 至少稳定定义：

```text
INVALID_PLUGIN_DESCRIPTOR

INVALID_RESTRICTED_MANIFEST

PLUGIN_ID_COLLISION

HOST_API_INCOMPATIBLE

INVALID_CONTRIBUTION

MISSING_CAPABILITY

DUPLICATE_CAPABILITY_PROVIDER

CIRCULAR_DEPENDENCY

CORE_DEPENDENCY_NOT_BUILTIN

UNDECLARED_CAPABILITY_REQUIRE

UNDECLARED_CAPABILITY_PROVIDE

DECLARED_CAPABILITY_MISSING

PLUGIN_ACTIVATION_FAILED

WUJIE_RESOURCE_FAILED

BRIDGE_BOOTSTRAP_FAILED
```

错误对象必须包含 `pluginId`、`stage` 和可用的 Dependency / Contribution 路径，不能只返回自由文本。

## 14.4 不做通用 Rollback

V1 只保证：

- Builtin Registry 写入在 commit 前可丢弃；
- Wujie Adapter 清理自己创建的 Surface、MessagePort、Pending RPC 和 Listener；
- Reload 可以重建整个 Runtime。

V1 不尝试撤销 Plugin 私自执行的任意外部副作用，因此 Builtin activate 必须遵守 PluginContext 写入约束。

# 15. Runtime Inspection 与 Audit

## 15.1 inspect 是事实投影

```ts
function inspect(
  runtime: PluginRuntime,
): RuntimeSnapshot;
```

不需要 `KernelInspector` class。

Snapshot 至少包含：

```text
runtime ready / bootstrap error

plugins

capabilities + provider ownership

dependencies

contributions + owner ownership

core closure

bridge connection facts
```

Plugin 记录示例：

```json
{
  "id": "kubeeye",
  "version": "1.2.0",
  "kind": "restricted",
  "executionMode": "wujie",
  "securityPosture": "cooperative-isolation",
  "core": false,
  "state": "ACTIVE",
  "requestedPermissions": [
    "cluster.read",
    "workload.read"
  ],
  "grantedPermissions": [
    "cluster.read"
  ],
  "bridge": {
    "connected": true,
    "instanceId": "..."
  }
}
```

`executionMode`、`securityPosture` 和 `core` 是派生展示字段，不写回 Manifest 或 Config。

Inspector 不暴露：

```text
Access Token

Raw RPC Payload

Sensitive Capability Result

Host Internal Object
```

`error: unknown` 只保存在内部 Runtime Fact；Snapshot 必须投影为稳定 error code 和经过清理的 message，生产环境不默认暴露任意对象或完整 stack。

## 15.2 Bridge Audit

每条 Privileged Bridge Action 至少记录：

```text
pluginId

pluginInstanceId

capability

action

resultCode

duration

timestamp
```

Audit 由 PluginBridge 写入现有日志或观测出口；V1 不为它建立独立 Audit Subsystem。

# 18. 验收矩阵

## 18.1 Resolver 与 Core

| 场景 | 预期 |
|---|---|
| Capability Major 匹配 | 建立正确 Provider Edge |
| Major 不匹配 | Consumer SKIPPED；涉及 Core 时 Runtime Bootstrap Failed |
| Duplicate Provider | 不选择任一 Provider，返回明确错误 |
| Circular Dependency | 输出完整 Cycle；Non-core Cycle SKIPPED |
| Core Root 缺失 | Runtime Bootstrap Failed |
| Core Closure 包含 Restricted | Plugin Code 不执行，Runtime Bootstrap Failed |
| 相同 DAG、不同输入数组顺序 | 得到相同 Activation Order |
| Provider Activation 失败 | 尚未执行的 Consumer 递归 SKIPPED |

## 18.2 Builtin Registry 一致性

| 场景 | 预期 |
|---|---|
| require 未声明 Capability | 立即返回 UNDECLARED_CAPABILITY_REQUIRE |
| register 未声明 Capability | 立即返回 UNDECLARED_CAPABILITY_PROVIDE |
| activate 后缺少 declared provide | Assertion Failed |
| activate 中途 throw | 暂存 Registry Record 全部丢弃 |
| activate 成功 | Capability 与 Contribution 一次性提交并带正确 owner |

## 18.3 Contribution

| 场景 | 预期 |
|---|---|
| order 相同 | 按 ownerPluginId、contributionId 稳定排序 |
| Slot 不存在 | Contribution 保持未使用，不形成 Dependency |
| Route / Navigation 冲突 | Manifest 或注册阶段返回可归因错误 |
| Route 引用未知 surfaceId | Restricted Manifest Invalid，代码不执行 |
| Navigation 引用未知 routeId | Restricted Manifest Invalid，代码不执行 |
| Restricted 通过 RPC 注册 UI | UNKNOWN_ACTION，Registry 不变 |
| Restricted Activation 失败 | Inspector 保留记录，UI 默认不暴露其 Contribution |

## 18.4 Bridge

| 场景 | 预期 |
|---|---|
| Capability 未列入 requires | UNDECLARED_CAPABILITY_REQUIRE |
| Restricted requires Direct-only Capability | Manifest 阶段 CAPABILITY_NOT_BRIDGE_EXPOSED，Plugin Code 不执行 |
| Unknown Action | UNKNOWN_ACTION |
| Invalid payload | INVALID_REQUEST |
| Host 返回不合 Schema 结果 | INVALID_RESULT 并记录 Host-side error |
| 缺少 Granted Permission | PERMISSION_DENIED |
| 重复 requestId | DUPLICATE_REQUEST |
| 超大消息 | MESSAGE_TOO_LARGE |
| 超过并发或频率 | CONCURRENCY_LIMITED / RATE_LIMITED |
| 超时 | TIMEOUT，并触发 AbortSignal |
| Surface 销毁后请求 | DISPOSED_PLUGIN_INSTANCE |
| 持续严重协议违规 | Bridge 关闭，Plugin FAILED |

## 18.5 Wujie 与安全边界

这些场景必须在真实浏览器中验证：

| 场景 | 预期 |
|---|---|
| 合法 Restricted Plugin | Wujie Surface 与 Bridge 正常工作 |
| Host Object 注入检查 | props 不包含 Store、DOM、Token、Raw Client |
| Wujie Bootstrap throw | Plugin FAILED，非 Core Runtime 继续 Ready |
| Surface unmount | MessagePort、Pending RPC、Listener 被清理 |
| Plugin 访问 window.parent | 测试明确暴露同源可访问事实，不产生错误安全断言 |
| Plugin 绕过 Bridge 请求 API | Backend Authorization 仍拒绝无权请求 |
| 安装后未 Reload | 当前 Runtime Plugin Set 不变化 |
| Reload 后 | 根据新 Installation Store 重建 Runtime |

测试的最高 seam 是：

```text
PluginDefinition / Restricted Manifest
                 +
Installed Config / Bridge Contract
                 ↓
          Plugin Runtime
                 ↕
            Test Plugin
                 ↓
Registry / UI / RPC / Snapshot / Audit
```

Resolver 使用纯输入输出测试；PluginBridge 通过同一个 Dispatcher Interface 测试；Wujie 隔离结论必须使用 Browser Integration Test，不以 Mock Context 代替。

# 20. 重新引入抽象的触发条件

| 抽象 | 只有出现以下真实需求时重新引入 |
|---|---|
| RuntimeLoader / Generic PluginAdapter | 出现第二种真实 External Runtime |
| PluginExecutionPolicy | 同一个 External Plugin 可以被选择为 Direct 或 Sandbox |
| Trusted External | 出现 External Artifact + Direct Host Realm 的正式需求 |
| External ESM / Module Federation | Trusted External 需要远程 Direct 加载或 Shared Dependency Negotiation |
| Native iframe | 产品开始执行 Hostile Third-party Code |
| Independent Origin | 需要真正的浏览器 Origin Security Boundary |
| Artifact Signature / Marketplace Trust | 开放第三方发布、分发和安装来源 |
| Generic Discovery | 来源扩展为 Marketplace、Remote Repository、Workspace 或 Cluster Scope |
| PermissionBroker | 多个独立 Transport 都需要共享同一套 Permission Enforcement |
| Runtime State Machine | 出现 Restart、Hot Unload、Provider Rebinding 或 Reconcile |

未来安全路径不是在同源 Wujie 上继续增加 Permission，而是：

```text
Hostile Third-party Code
          ↓
Independent Plugin Origin
          +
Production-ready Sandboxed iframe
```

# 21. 最终核心对象

V1 一级概念只有：

```text
PluginDefinition

RestrictedPluginManifest

DependencyResolver

CapabilityRegistry

BridgeCapabilityContract

ContributionRegistry

WujiePluginAdapter

PluginBridge
```

以及两类普通数据：

```text
InstalledPluginConfig

RuntimeState
```

最终模型可以概括为：

> **Builtin 以静态 PluginDefinition 参与统一依赖解析并直接执行；External Plugin 以 Restricted Manifest 参与同一依赖和 Contribution 模型，通过 Wujie + Bridge 运行；Capability 负责插件间能力共享，Contribution 负责 UI 扩展，requires / provides 在 Bootstrap 阶段一次性解析，Core Builtin 失败 fail-fast，Restricted Plugin 失败 fail-soft，Runtime 变化统一通过 Reload 重建。**

这套 V1 保留了依赖确定性、版本兼容、声明一致性、稳定 UI 扩展、权限治理、失败边界和线上诊断，同时不为尚未存在的 Runtime、Trust 或 Security 变化提前建立框架。
