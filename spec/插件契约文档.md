# Console 插件契约与文档自动生成设计

状态：最小方案已冻结（2026-09-08）；尚未实现生成器。  
范围：当前仓库内的契约参考文档生成。  
依据：[实现可行性评估](../docs/validation/plugin-contract-feasibility.md)。

## 1. 问题与目标

插件开发者需要查到 Runtime 支持的 Kind、Profile、Ref Contract，各插件声明的 Extension Point，以及指向这些 Point 的 Contribution。结构化表格应从实际声明生成，语义说明、示例和使用限制继续人工维护。

当前已经有 Point/Profile/Ref Contract 常量、Restricted Manifest、Point Compiler 和 Runtime Inspector。主要缺口是文档没有消费这些声明，以及部分 Builtin 注册数据仍写在 activate 中。

本设计遵循：**某个需求成立，不代表承载该需求的新抽象必须成立。每项事实维护一次，优先复用现有声明和编译规则。** 不要求所有事实合并到一个 Plugin Declaration。

本轮目标：

- 在本仓库生成 Kind/Profile/Ref、Point、单插件 API 参考内容。
- Runtime 注册与文档引用同一份结构化数据。
- 生成结果明确覆盖范围，区分声明关系与实际可用性。
- 增加最小生成检查，避免重复维护表格和产生静默缺失。

本轮不做：跨仓库聚合及发布协议、发行锁文件、Marketplace、IDE 集成、独立工具包、自动语义兼容判定、新 Runtime Inspector、热安装机制、Manifest 发布流水线。跨仓库需求不影响本轮接口、产物或验收。

## 2. 当前权威来源

| 事实 | 当前来源 | 文档消费方式 |
| --- | --- | --- |
| Kind | Runtime ExtensionKind、校验器及执行实现 | 五种固定 Kind 的参考说明；展示映射由 ExtensionKind 做穷尽类型检查，不建立可注册目录 |
| Profile | console-core-api 的 CONSOLE_PROFILES | 读取现有 PointProfile 常量 |
| Ref Contract | console-core-api / cluster-api 的 RefContract 常量 | 读取领域 Schema、traits、predicates |
| Builtin Point | CONSOLE_EXTENSION_POINTS / CLUSTER_EXTENSION_POINTS | 读取原数组；owner 关联现有 owner ID |
| Restricted Point/Contribution | RestrictedPluginManifest | 直接读取 extensionPoints 与 contributions |
| Builtin Contribution | PluginDefinition.activate 中的注册参数 | 按需提取为原有类型常量，注册和文档共享 |
| Plugin 身份与 Capability 依赖 | PluginDescriptor | 复用 id/version/requires/provides，禁止从 Point 引用反推 |
| 实际接纳与执行 | Runtime 和 Host 的 registry、关系模型、执行状态 | 留在现有 inspect；不成为静态文档的数据入口 |

源码入口：[协议定义](../packages/plugin-runtime/src/ui/definitions.ts)、[Descriptor](../packages/plugin-runtime/src/plugin.ts)、[Manifest](../packages/plugin-runtime/src/manifest.ts)、[Console API](../packages/console-core-api/src/index.ts)、[Cluster API](../packages/cluster-api/src/index.ts)。

`provides` 表示 Capability ID，不能改为 Point 数组。Restricted Manifest 的 provides 必须为空，但仍允许声明 extensionPoints。PluginKind（builtin/restricted）与 ExtensionKind 是不同概念。

## 3. 复用现有协议模型

Kind 固定为 route/navigation/action/tab/surface。Profile 可选；有 Profile 的 Point 绑定其参数，无 Profile 的 Point 使用内联 Schema。Slot 是运行时 occurrence，不是新的静态发布实体。Contribution 引用 Point，也允许 owner 自己贡献。

以下是已有字段形状的示例，不是新增作者 DSL：

```ts
import type {
  ExtensionPointDefinition,
  ActionContributionDefinition,
} from '@nexus/plugin-runtime';
import { PLUGIN_DETAILS_ACTIONS_POINT } from '@nexus/console-core-api';

const point = {
  id: 'plugin-details.actions',
  kind: 'action',
  contractMajor: 1,
  profile: 'detail.actions@1',
  bindings: { itemRefContract: 'console-core.plugin-ref@1' },
} as const satisfies ExtensionPointDefinition;

const contribution = {
  id: 'plugin-contract-check',
  kind: 'action',
  actionId: 'plugin-contract-check',
  label: 'Check plugin contract',
  point: PLUGIN_DETAILS_ACTIONS_POINT,
} as const satisfies ActionContributionDefinition;
```

这里的 point 是字段示例，实际使用时引用已有 Point 常量，不重新声明相同 Point。handler 仍由现有 actions.register 路径提供。

必须保留的区别：

- Point 版本是 contractMajor；插件 version、Profile/Ref 的 ID major、目标 contributionContractVersion 各自独立。
- Point 通过 profile/bindings 选定契约。expectedProfile/expectedRefContract 只能拒绝不匹配，不能选择另一份契约或提供授权。
- Contribution 的目标是结构化 point；RouteContribution.target 已表示渲染目标，不改成字符串 Point ID。
- contributions 保留 routes/navigation/extensions 分组；extensions 保留 kind、actionId/surfaceId/tabId、条件和排序字段。
- profiled Point 不能重写 Schema。最终 Context/Payload Schema 来自现有编译器；没有独立的 Context ID registry。
- owner 来自声明所属插件，Runtime 仍由激活上下文赋予，文档不得提供可覆盖 owner 的声明。

## 4. 最小数据入口

生成入口放在仓库 scripts，输出交给 apps/docs。入口显式引用本仓库纯数据模块和选定的 Manifest，不能扫描并执行任意 activate，也不能启动 BrowserHost。

本地输入列表只连接“来源模块/导出、所属插件、覆盖状态”，不再复制 Point/Contribution 字段，不推导当前安装集合。插件身份复用已有 Descriptor 或共享身份常量；若身份只存在于有副作用的实现模块，随静态数据一起小范围提取。

### 4.1 Builtin

现有 Point 数组直接复用。需要生成完整插件 Contribution 表时，只提取已存在注册参数的纯数据部分：

- 使用现有 ExtensionPointDefinition、NavigationContribution、ExtensionContributionDefinition 等类型。
- 路由元数据可用 Omit<RouteContribution, 'target'>；原 activate 将它与实际 target 组合。render、闭包和 handler 不进入文档输入。
- 注册逻辑继续引用这些常量；不复制一份仅供文档使用的声明数组。
- 不要求新增 definePlugin、defineContribution 或更改 PluginDefinition 接口。
- 不要求为文档枚举全部内部执行对象。未提取的部分标为“未纳入静态文档”，不能显示为“无贡献”。

### 4.2 Restricted

直接复用 RestrictedPluginManifest。当前 KubeEye 的来源是 Host 中 kubeeye-installation.ts，插件构建尚不输出 Manifest，也没有 TS/JSON 两份 Manifest 要去重。

若现有模块混合 Bridge 实现等非文档内容，仅提取原 Manifest 数据，让原安装记录构造与文档共同引用；config、Bridge 回调和部署逻辑保持原路径。不新增通用 Plugin Declaration，也不要求先生成 Manifest 文件。

### 4.3 说明文字

复用已有 *_EXTENSION_POINT_CATALOG 的 title/description。Point 的 kind、major、profile、bindings 和 Schema 始终来自 Point 声明。

初次接入时，在对应插件版本范围内逐条校验 Catalog 的完整 PointRef：ownerPluginId 必须等于声明所属插件，id 和 contractMajor 必须分别等于 Point 的 id 和 contractMajor。kind 不属于 PointRef，须另行比较。无法匹配、字段不一致或重复的 Catalog 引用均报错，不能只检查查找成功的条目。暂不为消除少量文字重复强制改造整个 Catalog。Point/Contribution 顶层不添加 description，因为当前闭合校验不接受该字段。

## 5. 编译与投影

```text
现有 API 常量 + Manifest + 已提取 Builtin 数据
                 │
                 ▼
      现有校验器 / createPointCompiler
                 │
                 ▼
       单次生成过程内的关联与展示投影
                 │
                 ▼
       apps/docs 的生成 Markdown

原声明 ── 原激活/安装路径 ── Runtime / Host 接纳与执行
```

不增加 plugin-contract.json、console-core-contract.json、extension-registry.json，不建立持久 Contract Registry。生成中可以使用 Map 关联数据，生命周期止于一次构建；它不是公共协议或可写服务。

createPointCompiler 已负责 Profile 查找、Ref 参数替换、约束收窄和最终 Schema 生成，直接复用。它目前是内部模块；默认由本仓库生成入口集中按明确源码路径导入，文档页面和业务代码不导入 Runtime 内部。

保留构建边界的调整出口：若实际构建工具无法可靠加载该源码入口，或明确的包边界要求禁止这种导入，允许在现有 plugin-runtime 包中增加最窄的构建入口，导出同一个 Compiler 实现。启用时须记录具体问题，并验证导入方式变化不改变编译结果与校验行为。此出口不要求预先实现，不允许复制 Compiler、新建 Contract 包或放宽业务侧内部导入规则，也不以未来可能存在的外部消费者为启用理由。

原始 Point 用于身份与绑定展示；编译后 Point 用于最终 Schema、有效约束展示。编译结果不回灌 Manifest，因为它含原始声明不接受的展开字段。

生成只需确定性排序和 Markdown 转义，不需要独立 Contract Schema/normalize 框架。Kind 展示映射仅提供标题和说明，并由现有 ExtensionKind 类型检查完整性，不从 Profile 实例集合反推 Runtime Kind。

## 6. 文档输出与覆盖范围

所有页面标记“本仓库选定声明的参考，非当前安装或可用状态”。

| 输出 | 内容 |
| --- | --- |
| Kind/Profile/Ref Reference | 固定 Kind；Profile 模板、参数位、允许约束/策略维度；领域 Ref Schema |
| Point Reference | owner/id/contractMajor、kind、profile、bindings、有效 Schema/约束、已收录贡献的反向引用 |
| Plugin Extension API | Descriptor 声明、extensionPoints、按原分组展示 contributions、已知的 Point 引用关系 |

冻结的首个输入范围：Console/Cluster API 声明、console-core/cluster/extension-demo 的现有固定注册元数据、现有 KubeEye v1/v2 Manifest。测试 fixtures 不收录。KubeEye v1/v2 分版本展示，不能混成一个已安装集合。接入过程中允许分步生成，但完整交付需覆盖这三个 Builtin 的固定贡献；执行对象不要求序列化。

实现必须在输出中逐插件标明 Point/Contribution 的收录范围；页面只有在该插件相关注册数据均被共享静态数据覆盖后，才能标注“完整”。未收录 Builtin Contribution 不参与零贡献或孤立引用的结论。当前 9 个正式 API Point、7 个 Profile、2 个 Ref 是调查快照，不作为永不变化的硬编码验收数字。

`coverage: complete` 属于生成器元数据，描述选定来源、插件版本和声明分组的收录完整性，不属于 Contract 事实，也不代表运行期可用。它只存在于生成输入说明或文档投影中，不进入 Manifest、Point、Contribution，不参与契约身份、major 冻结或兼容性判断。Builtin 的 complete 标记须有相关注册数据均被共享静态数据覆盖的依据，不能根据数组非空或生成成功自动推断；无法确认时保留不完整或未确认说明。

人工保留业务指南、示例、限制和 Kind 执行语义解释；只替换与本轮生成范围重叠的结构化表格。暂不改造现有 Demo Gallery 或 Runtime Inspector。

## 7. 静态验证边界

| 检查 | 本轮处理 |
| --- | --- |
| Point/Profile/Ref 形状、参数绑定、约束 | 调用现有 createPointCompiler 和原校验器；失败则不生成成功页面 |
| Manifest 形状 | 复用现有 Manifest 校验路径；已有验证记录可直接读 manifest，不伪造管理员 grants |
| Catalog 与 Point 对应 | 在对应插件版本内比较完整 PointRef（ownerPluginId/id/contractMajor），另验 kind；无法匹配或重复引用报错，文案不能覆盖协议字段 |
| 本地声明身份冲突 | 遵守 Runtime 的作用域；同版本 Point owner/id 唯一，route/navigation 各自全局 ID，UI 扩展按 owner/id；不同插件版本分组 |
| Point 引用 | 关联已收录目标并展示 major/断言不匹配；缺失目标标为未解析，不推断插件整体安装失败 |
| Capability | 展示 Descriptor requires/provides 和已声明条件；不推断新依赖或权限 |
| 实际授权/可见性/执行 | 不静态承诺；继续由 Host policy、实际 Context、权限与执行实现判断 |
| 兼容性 | 本轮不实现完整 Contract Diff；保留现有冻结与运行校验 |

KubeEye 当前包含指向 console-core/unavailable 的 kubeeye-unused。生成文档应保留并诊断这条引用，不把它悄悄丢弃，也不为了文档生成改变安装语义。未解析引用是可见诊断；非法声明、身份冲突、编译失败是生成失败。关联预检不能用“允许全部”的 Host policy 冒充实际接纳。

check:plugin-contract 当前只是目标协议版本的特性 gate，不复用它的成功状态来宣称完整校验通过。普通 Contributor 元数据若需要验证，复用已有形状函数；不要另写通用 Admission 或路由治理引擎。

## 8. Manifest 与 Runtime 的边界

Restricted Manifest 本身已是声明来源，Host 从其注册贡献。无需先设计“Declaration → Manifest”转换层。

未来若单独需要生成发布 Manifest，可以组合现有数据与 entry/hostApi/permissions 等显式输入，但本轮不实现该能力。enabled/grantedPermissions 属于安装配置，不能由贡献推断。Builtin 不产生 Restricted Manifest。

运行顺序分层：Bootstrap 校验并原子提交声明，返回 ready；BrowserHost 随后构建 route/UI/action 关系模型，再进入挂载和调用。静态文档不影响任何层。安装变更继续 reloadRequired，Runtime inspection 保持已有独立诊断结构，不要求与文档投影共用外层 Schema。

## 9. 最小实施与验收

先接入现有 API 常量和 Manifest 的文档投影，再按完整插件 API 页的需要提取 Builtin 数据；每一步都明确覆盖范围。无需等待所有 Builtin 静态化才生成已知 Point 参考，也不能因此提前声称所有贡献都已覆盖。

在现有 scripts 增加一个仓库级生成入口，并由 apps/docs 构建前调用。生成 Markdown 放在独立生成目录，不提交生成内容；CI 验证生成和 Docs build 成功，不增加 git diff 同步义务。具体命令尚未实现，不能把命令名存在视为验收。

每次生成必须先全量清空生成器独占的输出目录，再全量重建，避免删除或改名后的声明留下旧页面。清理范围仅限该专用目录，其中不得混放人工文档；不得清空 apps/docs 的整个文档根目录。生成失败必须阻断 Docs build，不得继续消费残缺结果。

必要验收：

1. 不启动 Host、不调用插件 activate、不读取安装存储即可生成。
2. 修改已有 Point/Profile/Ref 或共享 Contribution 数据，参考内容随之变化，不再同步手工表格。
3. Profile 参数替换与有效约束使用原编译结果；非法绑定不能伪装成成功文档。
4. 相同输入得到相同页面；排序与转义稳定，不写入时钟等易变内容。
5. 局部覆盖、版本和未解析引用明确可见；不把未知数量渲染为零。
6. Builtin 数据提取后，现有注册行为不变；按提取范围运行已有相关测试，不要求本轮新建全套契约测试框架。
7. 不改变安装、授权、执行与 Runtime Inspector，不增加第二套协议类型或可写 Registry。
8. 删除或改名声明后重新生成，旧页面不再存在；专用目录以外的人工内容不受影响，生成失败时 Docs build 不继续执行。
9. 分别错配 Catalog 的 ownerPluginId、id、contractMajor 或 kind 均报错；未匹配和重复引用不能被静默忽略。
10. coverage 仅出现在生成器元数据或文档展示中，不进入契约数据；complete 有收录依据，改变 coverage 不改变契约身份和编译结果。
11. 若启用 Compiler 构建入口，验证同一声明经两种导入方式得到相同编译结果，非法声明得到相同校验结果；未触发调整条件时不预先新增入口。

停止标准：本仓库开发者能从原声明得到准确、注明覆盖范围的契约参考，且新增一个已支持类型的声明只需修改原事实源。满足后不继续追加 JSON 产物、独立包或管理服务。

## 10. 小范围架构消融与冻结

本轮只比较文档生成所需的局部结构，不消融 Runtime 授权、执行寿命等无关机制。

实验使用现有 9 个 Point 的临时静态投影探针，每个变体执行同一组 5 项检查。没有修改生产代码，没有实现或测试完整 Docs Generator。

| 消融 | 实测结果 | 冻结决策 |
| --- | --- | --- |
| 基线 | 5 通过 | 比较基线成立 |
| 去掉 JSON 往返 | 5 通过，完整投影不变 | 不生成中间 Contract JSON |
| 去掉无行为 envelope | 5 通过，完整投影不变 | 不增加统一声明包装；新 DSL 也没有当前需求依据 |
| 注释去掉重复 kind | 5 通过，kind 来自 Point | 协议以 Point 为源；旧 Catalog 先做一致性检查 |
| 绕过原 Point Compiler | 2 通过、3 失败 | 必须复用 Compiler；它提供最终 Schema 和非法绑定拒绝 |

完整方法、限制、结果及源码哈希见[小范围消融记录](../docs/validation/plugin-contract-minimal-ablation.md)和[原始实验数据](../docs/validation/plugin-contract-ablation-results.json)。envelope 是探针包装，不是一个已实现的 Declaration DSL；实验只支持当前范围内的简化判断。

冻结主线：**现有本地声明 → 原校验/Point Compiler → 单次内存投影 → 生成 Markdown。**

仅增加仓库生成脚本、文档构建接入，以及完整插件页所需的共享静态数据提取。不增加新的协议模型、持久 Registry 或发布流水线；默认不增加公共 SDK 入口，仅允许第 5 节规定的实际构建边界问题触发最小构建导出。覆盖说明和声明/运行事实分层根据源码检查保留，未将其伪装成实测变异。

补充冻结约束：专用生成目录每次清空重建；Catalog 比较完整 PointRef 并另验 kind；coverage 只属于生成器元数据；Compiler 内部导入保留有条件的构建出口。这四项是设计边界与后续验收要求，不是本轮消融已执行的新增测试。

若后续实现确有无法满足的验收条件，先提供具体反例再重开对应决策；不以未来可能需要为由扩大范围。
