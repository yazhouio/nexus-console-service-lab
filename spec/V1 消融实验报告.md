# 前端插件系统 V1 消融实验报告

## 1. 实验目的

当前插件系统已经建立了比较完整的 Reload、Capability、Extension、Trust Model、Bridge、Permission、Inspector 等模型。

V1 的目标并不是构建一个完整的浏览器插件操作系统，而是优先解决以下实际问题：

1. Host 如何提供稳定扩展点，Plugin 如何扩展 UI
2. Plugin 如何共享能力而不依赖彼此内部实现
3. 如何避免人工维护 Plugin 加载顺序
4. Capability 不兼容时如何 fail-fast
5. Manifest 声明与 Runtime 行为如何保持一致
6. Extension 顺序如何保持稳定
7. 如何提供最低成本的运行时诊断
8. 如何根据 Plugin 信任级别选择不同执行方式
9. 如何在没有独立 Origin 的情况下运行 Restricted Plugin
10. 如何明确 Wujie 的安全边界，避免错误安全承诺

这些目标已经在当前设计中明确。

本次消融实验的目标是：

> **逐个移除或合并设计中的抽象，判断在不破坏上述 V1 目标的前提下，哪些设计是真正必要的，哪些只是为尚未出现的需求提前建模。**

核心原则：

```text
删掉一个抽象
     ↓
V1 目标是否仍然成立？
     ↓
Yes -> 删除或内联
No  -> 保留
```

重点减少：

```text
Premature Generalization

Future-only Abstraction

Derived State

Duplicate Registry

Unused Runtime Branch

Subsystem-shaped Utility
```

而不是单纯追求文件数量减少。

---

# 2. 消融实验前提

本报告依赖三个现实假设。

如果其中任何一项不成立，对应的消融结论应重新评估。

## 2.1 Restricted Plugin 当前主要是官方或合作插件

例如：

```text
KubeEye
Observability
Monitoring Extension
```

短期内不开放一个允许任意第三方上传并执行 JavaScript 的公开插件市场。

因此：

```text
Restricted
≠
Arbitrary Hostile Code
```

当前 Restricted 的主要目标是：

```text
Runtime Isolation
+
Integration Governance
+
Capability Governance
```

而不是：

```text
Hostile-code Containment
```

现有设计本身也已经明确，Wujie 同源模式无法阻止插件主动访问 `window.parent`、Host DOM、JS-readable Cookie、Storage 和同源 API。

---

## 2.2 Builtin Plugin 与 Kernel 属于同一构建产物

Builtin Plugin 当前不是：

```text
Kernel
  ↓ network
Builtin Plugin Artifact
```

而是：

```text
src/
├── kernel/
├── console-shell/
├── cluster/
├── workspace/
└── ...
```

最终进入同一个 Console Bundle。

因此 Builtin Plugin 不需要：

```text
Dynamic Runtime Loader

Module Federation

Remote Entry

Artifact Negotiation
```

只需要：

```ts
import consoleShell from "./plugins/console-shell";
import cluster from "./plugins/cluster";
```

即可。

---

## 2.3 当前没有真实的 Trusted External Direct Plugin

即当前没有明确需求：

```text
External Artifact
+
Trusted
+
Direct Host Realm
```

目前真实执行模型实际上只有：

```text
Builtin
  -> Direct

Restricted External
  -> Wujie
```

因此：

```text
trusted + direct + external artifact
```

虽然未来可能存在，但不是当前 V1 的实际需求。

---

# 3. 消融结果概览

当前架构图把 Kernel 拆成了 Discovery、Trust Policy、Dependency Resolver、Runtime Loader、Capability Registry、Permission Broker、Extension Registry、Inspector 等多个一级模块，同时还存在 Direct / Wujie / iframe 多条 Runtime 分支。

经过消融后，V1 可以缩减为以下核心：

```text
PluginDefinition
RestrictedPluginManifest

DependencyResolver

CapabilityRegistry
BridgeCapabilityContract

ContributionRegistry

WujiePluginAdapter
PluginBridge
```

另外保留两类普通数据：

```text
InstalledPluginConfig
RuntimeState
```

以下不再作为独立架构子系统：

```text
PluginDiscovery

TrustPolicy

PluginExecutionPolicy

RuntimeLoader

DirectPluginAdapter

IframePluginAdapter

PermissionBroker

ManifestContributionRegistrar

KernelInspector class

Generic EventBus
```

---

# 4. Runtime Loader 消融

## 原设计

现有设计定义：

```ts
interface RuntimeLoader {
  supports(
    manifest: PluginManifest,
    policy: PluginExecutionPolicy,
  ): boolean;

  load(
    manifest: PluginManifest,
    policy: PluginExecutionPolicy,
  ): Promise<PluginAdapter>;
}
```

用于统一支持：

```text
Builtin
ESM
Module Federation
Wujie
iframe
```

## 消融实验

删除 RuntimeLoader 后：

Builtin：

```ts
await builtin.activate(ctx);
```

Restricted：

```ts
await startWujiePlugin(manifest, config);
```

即可。

V1 没有第三种真实路径。

## 结论

**删除 RuntimeLoader 通用接口。**

同时删除：

```text
supports()

loader selection framework

Module Federation runtime

runtime loader registry
```

V1 直接：

```ts
if (plugin.source === "builtin") {
  await plugin.definition.activate(ctx);
} else {
  await wujieAdapter.activate(plugin);
}
```

如果未来出现：

```text
Trusted External ESM
Module Federation Plugin
Iframe Plugin
```

再提炼 Loader 接口。

---

# 5. Module Federation 消融

当前设计已经说明 Module Federation 只是 JavaScript 动态加载方式，本身不等于 Plugin System。

在假设 2 和假设 3 下：

```text
Builtin -> static import
Restricted -> Wujie artifact
```

因此当前没有任何必须使用 Module Federation 的路径。

## 结论

V1 删除：

```text
runtime.type = module-federation

MF manifest

remote loading abstraction

shared dependency negotiation
```

整节 Module Federation 定位可以移入：

```text
Future Evolution
```

---

# 6. Native iframe 消融

原设计将 iframe 定义成 optional execution mode：

```text
restricted
  ├── wujie
  └── iframe
```

并进一步引入：

```text
opaque-origin-sandbox

allow-same-origin rules

IframePluginAdapter

iframe test fixture
```

但 V1 同时明确：

```text
Independent Plugin Origin 不进入 V1

Hostile-code Containment 不由 Wujie 提供

Native iframe 不是 mandatory
```

## 结论

从 V1 类型系统彻底删除：

```text
executionMode = iframe

securityPosture = opaque-origin-sandbox

IframePluginAdapter

iframe acceptance tests
```

只在未来演进中保留：

```text
Hostile Plugin Execution
        ↓
Independent Plugin Origin
        +
Production-ready Sandboxed iframe
```

V1 执行模式只剩：

```text
Builtin
  -> Direct

Restricted
  -> Wujie
```

---

# 7. SecurityPosture 消融

原设计：

```ts
securityPosture:
  | "full-trust"
  | "cooperative-isolation"
  | "opaque-origin-sandbox";
```

但删除 iframe 后：

```text
Builtin
  -> full-trust

Restricted Wujie
  -> cooperative-isolation
```

已经是确定映射。

## 结论

`securityPosture` 不再作为：

```text
stored state

Installation Policy field

Runtime configuration
```

而只是：

```ts
function getSecurityPosture(plugin) {
  return plugin.kind === "builtin"
    ? "full-trust"
    : "cooperative-isolation";
}
```

Inspector 展示时动态计算即可。

---

# 8. Trust Policy 消融

原架构中：

```text
Trust Policy
```

是 Kernel 一级模块。

但在当前 V1：

```text
Builtin source
  -> builtin

Installed external artifact
  -> restricted
```

不存在复杂 Policy Solver。

## 结论

删除：

```text
TrustPolicy subsystem
```

保留简单 Bootstrap 校验。

例如：

```ts
function validateInstalledPlugin(plugin) {
  if (plugin.source !== "builtin") {
    // external V1 plugins always use Wujie
  }
}
```

Trust 仍然是一个重要概念，但暂时不需要一个：

```text
Trust Policy Engine
```

---

# 9. Plugin Execution Policy 消融

原设计：

```ts
interface PluginExecutionPolicy {
  trustLevel;
  executionMode;
  securityPosture;
  grantedPermissions;
  critical;
}
```

现有设计实际上需要维护多字段之间的合法组合。

例如：

```text
restricted + direct = illegal

restricted + iframe = optional

trusted + direct = valid

builtin + direct = valid
```

但三个前提成立后，V1 只有：

```text
BuiltinDefinition
  -> builtin/direct

InstalledPlugin
  -> restricted/wujie
```

## 结论

**删除 `PluginExecutionPolicy`。**

外部插件只保存：

```ts
interface InstalledPluginConfig {
  id: string;
  version: string;

  enabled: boolean;

  grantedPermissions: string[];
}
```

Execution Mode 根据来源决定，不需要存储：

```text
BuiltinDefinition
  -> Direct

InstalledPlugin
  -> Wujie
```

未来出现 Trusted External Plugin 时，再引入真正的：

```text
ExecutionPolicy
```

---

# 10. Plugin Discovery 消融

原设计把：

```text
Plugin Discovery
```

作为独立 Kernel 子系统。

当前 Runtime 来源实际上只有两种：

```text
staticBuiltinDefinitions

installedRestrictedPlugins
```

因此：

```ts
const plugins = [
  ...builtinDefinitions,
  ...loadInstalledPlugins(),
];
```

已经足够。

## 结论

删除：

```text
discovery.ts
PluginDiscovery
Discovery abstraction
```

Discovery 只是 Bootstrap 的第一步。

---

# 11. Manifest 模型消融

这里需要特别区分：

```text
Manifest 数据模型
```

和：

```text
plugin-manifest.json 文件
```

## 原设计

Manifest 对所有 Plugin 都描述：

```text
Identity

Runtime Entry

Host API

requires

provides

permissions

contributions
```

## 消融结论

Builtin 不需要真正生成：

```text
plugin-manifest.json
```

但 Resolver 仍然需要 Builtin 的：

```text
id

version

requires

provides
```

因此建议拆成：

```ts
interface PluginDescriptor {
  id: string;
  version: string;

  requires: string[];
  provides: string[];
}
```

Builtin：

```ts
interface PluginDefinition extends PluginDescriptor {
  activate(
    ctx: PluginContext,
  ): void | Promise<void>;
}
```

Restricted：

```ts
interface RestrictedPluginManifest
  extends PluginDescriptor {

  entry: string;

  hostApi: string;

  permissions: string[];

  contributions: RestrictedContributions;
}
```

Resolver 最终统一消费：

```text
PluginDescriptor[]
```

这样：

```text
Dependency Contract
```

仍然统一，但 Builtin 不再为了形式一致性生成无必要 JSON artifact。

---

# 12. requested runtime 消融

如果外部 Plugin 在 V1：

```text
只能 Wujie
```

那么 Manifest 不需要：

```json
{
  "runtime": {
    "type": "wujie"
  }
}
```

也不存在：

```text
Plugin requests direct
Host rejects direct
```

这种当前没有实际选择空间的流程。

## 结论

Restricted Manifest 只需要：

```json
{
  "entry": "/plugins/kubeeye/"
}
```

外部 Plugin 默认：

```text
Wujie
```

未来引入：

```text
trusted external
iframe
other sandbox
```

时再恢复 execution request。

# 13. DirectPluginAdapter 消融

原设计 Kernel 实际统一激活：

```text
PluginAdapter
├── DirectPluginAdapter
├── WujiePluginAdapter
└── IframePluginAdapter
```

消融后：

```text
Builtin Direct
```

只需要：

```ts
await definition.activate(context);
```

没有需要“适配”的不同 Runtime。

## 结论

删除：

```text
PluginAdapter common interface

DirectPluginAdapter
```

只保留：

```text
WujiePluginAdapter
```

因为 Wujie 确实承担：

```text
Artifact Loading

Surface Lifecycle

Bridge Bootstrap

Error Boundary

Resource Cleanup
```

# 14. Module Loading 与 Activation 分离消融

原设计强调：

```text
Module Loading
  -> 可以并行

Plugin Activation
  -> 默认串行
```

删除 Runtime Direct Loading 后：

Builtin：

```text
已经随 bundle 加载
```

Restricted：

```text
Wujie Resource Loading
```

本身就是 Wujie Activation 的组成部分。

因此：

```text
Module Loading
```

不再是插件系统需要显式建模的阶段。

## 结论

删除：

```text
Parallel Module Loading
Module Loading Stage
Load vs Activate architecture chapter
```

只保留：

```text
Plugin Activation 默认串行
```

未来如果加载性能成为真实问题，可以增加 preload，但它只是优化，不改变 Plugin Protocol。

---

# 15. EventBus 消融

原 PluginContext：

```ts
interface PluginContext {
  capabilities;
  extensions;
  routes;
  navigation;
  events;
}
```

Restricted 同时又通过 Bridge：

```text
Snapshot / Event
```

获得：

```text
Theme

Locale

Cluster Scope

Workspace Scope
```

这形成两套通知系统：

```text
Direct
  -> EventBus

Restricted
  -> Bridge Event
```

## 消融结论

删除通用：

```text
EventBus
```

跨 Plugin 状态变化统一通过 Capability。

例如：

```ts
interface ScopeCapability {
  getCurrent(): Scope;

  subscribe(
    listener: (scope: Scope) => void
  ): () => void;
}
```

Direct 使用 TS API。

Bridge-exposed 时映射为：

```text
Snapshot
+
Event
```

这样：

```text
Capability
```

成为唯一跨 Plugin Runtime Contract。

---

# 16. Capability 保留

Capability 是整个设计中不应消融的核心之一。

它解决：

```text
Consumer Plugin
    ↓
Capability Contract
    ↑
Provider Plugin
```

而不是：

```text
Consumer
   ↓
Provider Implementation
```

同时保留：

```text
capability-name@major
```

例如：

```text
kubesphere.cluster@2
```

V1 不需要 SemVer Solver。

只需要：

```text
@major
```

即可提供非常低成本的 ABI fail-fast。

---

# 17. HostCapabilityContract 局部化

原设计容易让人理解为：

> 所有 Capability 都必须同时定义 Action、Request Schema、Result Schema 和 Permission。

消融后应区分：

## Direct-only Capability

只需要：

```ts
interface ClusterInternalCapability {
  getCurrentCluster(): Cluster;
}
```

无需：

```text
JSON Schema

Action Table

Permission Mapping
```

## Bridge-exposed Capability

才需要：

```ts
interface BridgeCapabilityContract {
  id: "kubesphere.cluster@2";

  actions: {
    list: {
      requestSchema;
      resultSchema;
      requiredPermissions;
    };
  };
}
```

## 结论

规则改成：

> **只有暴露给 Restricted Plugin Bridge 的 Capability 才要求完整 Bridge Capability Contract。**

从而避免大量 Builtin Capability 的 Schema 样板代码。

---

# 18. requires / provides 保留

这部分不消融。

原因：

```text
CapabilityRegistry
```

只能回答：

```text
现在有没有这个 Capability？
```

不能回答：

```text
谁应该先 activate？
```

因此：

```text
requires
provides
```

仍然用于 Bootstrap Dependency DAG。

保留：

```text
Missing Capability

Circular Dependency

Topological Sort
```

这些都属于低成本、高收益逻辑。

---

# 19. Runtime 一致性校验简化

当前设计存在独立：

```text
Runtime Assertion Stage
```

检查：

```text
Declared Capability Missing

Undeclared Capability Registered

Undeclared Capability Required
```

无需独立 Assertion 子系统。

## require 时检查

```ts
ctx.capabilities.require(name)
```

立即验证：

```text
name ∈ descriptor.requires
```

否则直接：

```text
UNDECLARED_CAPABILITY_REQUIRE
```

## register 时检查

```ts
ctx.capabilities.register(name, value)
```

立即验证：

```text
name ∈ descriptor.provides
```

## activate 后检查

只需一次：

```text
descriptor.provides
        ⊆
actuallyRegisteredCapabilities
```

## 结论

保留双向一致性规则。

删除：

```text
独立 Runtime Assertion subsystem
```

# 20. Critical 模型消融

当前设计规定：

```text
只有 Builtin Plugin 可以 Critical
```

并要求：

```text
Critical Plugin 传递性依赖闭包
只能包含 Critical Builtin Plugin
```

该安全规则应该保留，但 `critical` 字段本身可以继续消融。

## 原模型

每个 Plugin：

```ts
critical: boolean;
```

然后 Resolver 校验：

```text
critical plugin
    ↓
dependencies must also be critical
```

## 简化模型

Host 只定义 Core Roots：

```ts
const corePluginIds = [
  "console-shell",
];
```

Resolver 自动展开：

```text
Core Roots
   ↓
Capability Dependencies
   ↓
Core Dependency Closure
```

要求整个 closure：

```text
全部为 Builtin
```

于是：

```text
Core Closure Plugin Failure
  -> Runtime Bootstrap Failed

Other Plugin Failure
  -> Plugin FAILED / SKIPPED
```

## 结论

保留：

```text
Core Dependency Closure Rule
```

删除：

```text
Plugin critical field

critical Installation Policy

critical combination validation
```

---

# 21. Extension / Route / Navigation Registry 合并

原系统存在：

```text
Extension Registry

Route Registry

Navigation Registry
```

三者共享很多机制：

```text
Ownership

Stable Ordering

Conflict Diagnostics

Inspection
```

Registry Ownership 本身是低成本、高价值信息，应继续保留。

## 不建议完全统一业务语义

Route：

```text
path

route hierarchy

collision
```

Navigation：

```text
parent

visibility

order
```

Extension：

```text
slot

component/surface

order
```

并不是完全一样。

因此不建议把：

```text
host.routes
host.navigation
```

粗暴地当普通 Extension Slot。

## 建议

统一底层：

```ts
class ContributionRegistry {
  ...
}
```

但提供 typed API：

```ts
registry.registerExtension(...);

registry.registerRoute(...);

registry.registerNavigation(...);
```

统一：

```text
Ownership

Indexing

Inspection

Conflict Metadata

Stable Ordering
```

保留：

```text
Route semantics

Navigation semantics

Extension semantics
```

# 22. Extension 稳定排序保留

显式：

```text
order ASC
    ↓
ownerPluginId ASC
    ↓
contributionId ASC
```

属于低成本高价值设计。

当前设计已经明确 Extension 顺序不能依赖 Activation Order。

这条不应消融。

# 23. Manifest-first Restricted Contribution 保留

Restricted Plugin 不应该通过 Bridge：

```text
registerRoute

registerNavigation

registerExtension
```

而应该由 Manifest 静态声明：

```text
Route

Navigation

Sandbox Surface
```

Host 在执行 Plugin Code 前完成验证与注册。

这能够：

```text
Fail Early

Avoid Runtime Mutation

Prevent Arbitrary Host UI Injection

Keep Registry Deterministic
```

因此继续保留。

# 24. Permission Model 简化

原设计：

```text
Requested Permissions
        ∩
Granted Permissions
        ∩
Platform Policy
        ↓
Effective Permissions
```

实际上：

```text
Platform Policy
```

在安装阶段就已经参与生成 Granted。

因此 Runtime 没必要再维护：

```text
EffectivePermissions
```

## 建议

安装阶段：

```text
Requested Permissions
        +
Platform/Admin Decision
        ↓
Granted Permissions
```

Runtime：

```text
Action.requiredPermissions
        ⊆
Granted Permissions
```

即可。

## 结论

保留：

```text
Requested Permissions

Granted Permissions
```

删除：

```text
EffectivePermissions runtime state
```

---

# 25. Permission Broker 合并

每次 Bridge Action 调用仍必须：

```text
Permission Check
```

这条不能消融。

但不需要一个 Kernel 一级：

```text
PermissionBroker
```

Bridge Dispatcher 可以直接：

```text
Request
  ↓
Capability Contract Lookup
  ↓
Request Schema Validation
  ↓
Required Permissions Check
  ↓
Invoke
```

## 结论

保留：

```text
per-call permission enforcement
```

删除：

```text
PermissionBroker subsystem/class requirement
```

Permission Enforcement 是 Bridge Dispatcher 的职责。

---

# 26. Bridge 安全机制消融结果

Bridge 当前设计包含：

```text
Instance Check

Protocol Version

Manifest Capability Check

Action Lookup

Request / Result Schema

Permission Check

Request Deduplication

Timeout / Cancellation

Message Size Limit

Concurrency / Rate Limit

Audit
```

本轮不建议因为 Restricted Plugin 数量少而全部砍掉。

原因是：

```text
Buggy Plugin
```

即使不是恶意 Plugin，也可能：

```text
重复调用

无限重试

RPC 风暴

卡死请求

重复 mutation
```

因此保留：

```text
requestId

dedup

timeout

rate/concurrency limit

schema validation

permission check
```

这些保护针对：

```text
bug containment
```

而不是：

```text
hostile-code security boundary
```

两者应明确区分。

---

# 27. Bridge 可以继续简化的部分

虽然上述机制保留，但不必做成大量独立 subsystem。

推荐内部 pipeline：

```text
PluginBridge
   ↓
validate instance/protocol
   ↓
lookup capability/action
   ↓
validate schema
   ↓
check permission
   ↓
dedup / rate-limit / timeout
   ↓
invoke
   ↓
record result
```

实现上全部可以位于：

```text
plugin-bridge.ts
```

V1 不需要：

```text
permission-broker.ts

rpc-limiter.ts

rpc-audit-service.ts

protocol-engine.ts
```

等多个独立抽象。

# 28. Inspector 简化

原设计暴露：

```text
DISCOVERED

VALIDATED

LOADING

ACTIVE

FAILED

SKIPPED
```

但 Inspector 本质已经被定义为：

```text
Read-only Snapshot
```

而不是 Runtime Orchestrator。

Runtime Ready 后真正需要的状态只有：

```text
ACTIVE

FAILED

SKIPPED
```

错误定位额外记录：

```ts
failedAtStage:
  | "manifest"
  | "resolve"
  | "activate"
  | "assertion"
  | "bridge";
```

例如：

```ts
{
  id: "kubeeye",

  state: "FAILED",

  failedAtStage: "bridge",

  error: "BRIDGE_HANDSHAKE_FAILED"
}
```

## 结论

删除：

```text
DISCOVERED

VALIDATED

LOADING
```

作为持久 Inspector State。

如果 Bootstrap 日志需要，可以作为瞬时日志字段，而不是 Runtime 状态机。

# 29. KernelInspector class 消融

Inspector 功能必须保留。

但无需：

```ts
new KernelInspector(...)
```

这种独立生命周期对象。

可以简单：

```ts
kernel.inspect = () => createRuntimeSnapshot(
  runtimeState,
);
```

或：

```ts
inspect(runtime)
```

Inspector 只是 Runtime Facts 的投影。

# 44. 最终核心原则

消融后，V1 可以浓缩为以下原则：

```text
1. Runtime 生命周期内 Plugin Set immutable

2. Plugin Set 变化统一 Reload

3. Builtin 与 Kernel 同包构建并直接 activate

4. External Plugin V1 统一 Restricted + Wujie

5. Plugin Dependency 只通过 Capability

6. Capability 使用 name@major

7. requires / provides 只在 Bootstrap 解析一次

8. Core dependency closure 必须全部是 Builtin

9. UI 扩展通过 Contribution

10. Contribution 顺序显式且 deterministic

11. Restricted Contribution 必须 Manifest-first

12. Restricted 不能提供 Global Capability

13. Bridge-exposed Capability 才需要
    Action / Schema / Permission Contract

14. Permission 每次 Bridge 调用检查

15. Wujie 只承诺 cooperative-isolation

16. Backend Authorization 仍是真正的数据安全边界

17. Core Failure fail-fast

18. Restricted Failure fail-soft

19. Inspector 只暴露 Runtime Facts

20. 不为未来需求提前建立动态 Runtime 状态机
```

# 46. 结论

当前原始设计的方向没有问题。

真正需要消融的是：

> **为了未来可能存在的执行模式、插件来源和安全等级而提前建立的通用框架。**

在当前三个现实假设下，V1 实际只有：

```text
Builtin
  -> Direct

Restricted External
  -> Wujie
```

因此没有必要现在就维护：

```text
Discovery Framework

Trust Policy Engine

Execution Policy Matrix

Runtime Loader Framework

Module Federation

Iframe Adapter

Generic PluginAdapter

Six-state Runtime Model
```

消融后的系统仍然完整保留原设计最重要的五条主线：

```text
Reload
+
Capability
+
Dependency
+
Contribution
+
Restricted Bridge
```

最终模型可以概括为：

> **Builtin 以静态 PluginDefinition 参与统一依赖解析并直接执行；External Plugin 以 Restricted Manifest 参与同一依赖和 Contribution 模型，通过 Wujie + Bridge 运行；Capability 负责插件间能力共享，Contribution 负责 UI 扩展，requires/provides 在 Bootstrap 阶段一次性解析，Core Builtin 失败 fail-fast，Restricted Plugin 失败 fail-soft，Runtime 变化统一通过 Reload 重建。**

这比当前版本更符合 V1 的核心原则：

> **只为已经存在的变化维度建立抽象；为未来需求保留可重构的 seam，而不是提前实现完整框架。**

当前设计最后强调的“一次页面加载构建一个稳定、可验证、可诊断的 Plugin Runtime”仍然完全成立。
